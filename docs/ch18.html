第 18 章　使用 Hibernate OGM

数据库的世界极其多样和复杂。除了与不同关系数据库系统打交道的挑战外，NoSQL 世界还会再添一层。持久化框架的目标之一就是保证代码的可移植性——本章看 Hibernate OGM 这个方案，以及它如何让 JPA 解决方案支持 NoSQL 数据库。本章的高潮是：写一遍 JPA 代码，只改配置就从 MongoDB 切到 Neo4j。

本章的源码工程

只有一个：Ch18/hibernate-ogm。先用 MongoDB 跑通，然后把 pom.xml 里的依赖和 persistence.xml 里的配置一换，同一份代码就跑在 Neo4j 上了。没有 .sql 脚本。

18.1 Hibernate OGM 简介

NoSQL 数据库的四种类型

NoSQL 数据库是指以不同于关系表的格式保存数据的数据库。一般来说，NoSQL 数据库的优势在于灵活的模式——数据库设计者不必在持久化数据之前就确定好 schema。在需求快速变化的应用中，这对开发速度可能是一个重要优势。

可移植性从关系数据库延伸到 NoSQL

前面大部分演示用 JPA 和 Hibernate 与关系数据库交互，这让我们能写出可移植、不依赖关系数据库厂商的应用，把厂商之间的差异交给框架管理。

Hibernate OGM 把可移植性的概念从关系数据库延伸到了 NoSQL 数据库。可移植性可能会以影响执行速度为代价，但总体上它带来的优势多于缺点。

18.2 构建一个简单的 MongoDB Hibernate OGM 应用

18.2.1 配置

在 Maven 的 pom.xml 里，先往 dependencyManagement 部分加 org.hibernate.ogm:hibernate-ogm-bom。

BOM 是什么

BOM 是 bill of materials（物料清单）的缩写。把一个 BOM 加进 dependencyManagement 块并不会真的把依赖加进项目，它只是一个意图声明：后面在 dependencies 部分出现的传递依赖，版本都由这份初始声明来控制。这样你就不用给每个 hibernate-ogm-* 依赖单独写版本号了。

Ch18/hibernate-ogm/pom.xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.hibernate.ogm</groupId>
            <artifactId>hibernate-ogm-bom</artifactId>
            <type>pom</type>
            <version>4.2.0.Final</version>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.hibernate.ogm</groupId>
        <artifactId>hibernate-ogm-mongodb</artifactId>       <!-- 与 MongoDB 打交道所需 -->
    </dependency>
    <dependency>
        <groupId>org.jboss.jbossts</groupId>
        <artifactId>jbossjta</artifactId>                     <!-- JTA 实现，OGM 支持事务需要它 -->
    </dependency>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.24</version>
    </dependency>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter-engine</artifactId>
        <version>5.8.2</version>
        <scope>test</scope>
    </dependency>
</dependencies>
为什么需要 JTA？

org.jboss.jbossts:jbossjta 是一个 JTA（Java Transaction API）实现，Hibernate OGM 需要它来支持事务。回忆第 11 章：JPA 的所有操作都要在事务边界内进行——即使底层是不支持 ACID 事务的 NoSQL 数据库，这套 API 契约仍然要成立。

接下来是持久化单元的标准配置文件：

Ch18/hibernate-ogm/src/main/resources/META-INF/persistence.xml
<persistence-unit name="ch18.hibernate_ogm">                          <!-- A -->
    <provider>org.hibernate.ogm.jpa.HibernateOgmPersistence</provider>  <!-- B -->
    <properties>
        <property name="hibernate.ogm.datastore.provider" value="mongodb"/>   <!-- C -->
        <property name="hibernate.ogm.datastore.database"
                  value="hibernate_ogm"/>                                    <!-- D -->
        <property name="hibernate.ogm.datastore.create_database"
                  value="true"/>                                            <!-- E -->
    </properties>
</persistence-unit>
A 配置名为 ch18.hibernate_ogm 的持久化单元。
B API 的厂商特定 provider 实现是 Hibernate OGM。这一行是全章的枢纽。
C 数据存储 provider 是 MongoDB。
D 数据库名是 hibernate_ogm。
E 如果数据库不存在就创建它。

18.2.2 创建实体

现在创建表示应用实体的类：User、Bid、Item 和 Address。它们之间的关系是一对多、多对一或嵌入式——注意这些术语，它们全部来自 JPA，与底层是不是关系数据库无关。

Ch18/hibernate-ogm/.../model/User.java
@Entity
@NoArgsConstructor
public class User {

    @Id
    @GeneratedValue(generator = "ID_GENERATOR")                             // A
    @GenericGenerator(name = "ID_GENERATOR", strategy = "uuid2")
    @Getter
    private String id;

    @Embedded                                                            // B
    @Getter @Setter
    private Address address;

    @OneToMany(mappedBy = "user", cascade = CascadeType.PERSIST)         // C
    private Set<Bid> bids = new HashSet<>();
}
A id 字段由 ID_GENERATOR 生成器生成，用的是 uuid2 策略——产生一个唯一的 128 位 UUID。生成器策略请回顾 5.2.5 节。
B address 没有自己的身份标识，它是可嵌入的（embeddable）。
C User 与 Bid 之间是一对多关系，由 Bid 一侧的 user 字段来映射。CascadeType.PERSIST 表示 persist 操作会从父 User 传播到子 Bid。
为什么用 uuid2 而不是自增序列？

回顾 5.2.5 节的生成器策略表：identity 依赖数据库的自增列、enhanced-sequence 依赖数据库序列——这两样 NoSQL 数据库都没有。uuid2 完全在应用端生成，因此是跨存储范式最安全的选择。这是从关系型迁移到 NoSQL 时必须改的少数几个地方之一。

Address（可嵌入）

@Embeddable
@NoArgsConstructor
public class Address {
    // 带 Lombok 注解的字段、构造器
}

Address 类没有自己的持久化身份，它是可嵌入的。

Item

@Entity
@NoArgsConstructor
public class Item {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    @GenericGenerator(name = "ID_GENERATOR",
                      strategy = "uuid2")
    @Getter
    private String id;

    @OneToMany(mappedBy = "item",
               cascade = CascadeType.PERSIST)
    private Set<Bid> bids = new HashSet<>();
}

18.2.3 用 JPA 操作 MongoDB

要把应用中的实体持久化到 MongoDB，我们写的代码使用的是常规的 JPA 类和 JPQL。这意味着我们的应用既能与关系数据库工作，也能与各种 NoSQL 数据库工作——只需要改一些配置。

Ch18/hibernate-ogm/src/test/.../HibernateOGMTest.java
public class HibernateOGMTest {

    private static EntityManagerFactory entityManagerFactory;

    @BeforeAll
    static void setUp() {
        entityManagerFactory =
              Persistence.createEntityManagerFactory("ch18.hibernate_ogm");
    }

    @AfterAll
    static void tearDown() {
        entityManagerFactory.close();
    }
}
停下来看一眼这段代码

Persistence.createEntityManagerFactory("ch18.hibernate_ogm")——这是第 2 章开始就一直在写的那一行。底下现在是 MongoDB，代码却完全没变。这就是 Hibernate OGM 的整个卖点。

每个测试执行前，往 MongoDB 里持久化几个实体。我们的代码用 JPA 完成这些操作，而 JPA 并不知道自己在和关系型还是非关系型数据库交互：

@BeforeEach
void beforeEach() {
    EntityManager entityManager =
                 entityManagerFactory.createEntityManager();          // A
    try {
        entityManager.getTransaction().begin();                       // B 操作必须是事务性的

        john = new User("John", "Smith");                          // C
        john.setAddress(new Address("Flowers Street", "12345", "Boston"));

        bid1 = new Bid(BigDecimal.valueOf(1000));
        bid2 = new Bid(BigDecimal.valueOf(2000));

        item = new Item("Item1");

        bid1.setItem(item);   item.addBid(bid1);       // 双向关联的两端都要设（第 3 章）
        bid2.setItem(item);   item.addBid(bid2);
        bid1.setUser(john);   john.addBid(bid1);
        bid2.setUser(john);   john.addBid(bid2);

        entityManager.persist(item);                                 // D
        entityManager.persist(john);

        entityManager.getTransaction().commit();                     // E
    } finally {
        entityManager.close();                                       // F
    }
}
D 持久化 Item 和 User 实体。由于 Item 和 User 里的 Bid 用 CascadeType.PERSIST 引用，persist 操作会从父传播到子——所以不用单独 persist 两个 Bid。

查询也一样用 entityManager.find。注意：与数据库的每一次交互都应该发生在事务边界内，哪怕只是读数据：

@Test
void testCRUDOperations() {
    EntityManager entityManager = entityManagerFactory.createEntityManager();
    try {
        entityManager.getTransaction().begin();

        User fetchedUser = entityManager.find(User.class, john.getId());     // C
        Item fetchedItem = entityManager.find(Item.class, item.getId());
        Bid  fetchedBid1 = entityManager.find(Bid.class,  bid1.getId());
        Bid  fetchedBid2 = entityManager.find(Bid.class,  bid2.getId());

        assertAll(
            () -> assertNotNull(fetchedUser),
            () -> assertEquals("John",  fetchedUser.getFirstName()),
            () -> assertEquals("Smith", fetchedUser.getLastName()),
            () -> assertNotNull(fetchedItem),
            () -> assertEquals("Item1", fetchedItem.getName()),
            () -> assertNotNull(fetchedBid1),
            () -> assertEquals(new BigDecimal(1000), fetchedBid1.getAmount()),
            () -> assertNotNull(fetchedBid2),
            () -> assertEquals(new BigDecimal(2000), fetchedBid2.getAmount()));

        entityManager.getTransaction().commit();
    } finally {
        entityManager.close();
    }
}

执行完这个测试后，可以在 MongoDB Compass 里检查数据库内容：会看到创建了三个集合。这证明了用 JPA 写的代码借助 Hibernate OGM 成功地与 NoSQL 的 MongoDB 交互了。展开集合还能看到测试持久化进去的文档（要在 afterEach() 方法删掉它们之前看）——比如 Bid 集合里有两个文档。

18.2.4 用 JPQL 查询

JPQL（Jakarta Persistence Query Language）是一种与平台无关的面向对象查询语言。之前我们用 JPQL 查询关系数据库、不依赖它们的 SQL 方言；现在我们用 JPQL 来和 NoSQL 数据库交互。

@Test
void testJPQLQuery() {
    EntityManager entityManager = entityManagerFactory.createEntityManager();
    try {
        entityManager.getTransaction().begin();

        List<Bid> bids = entityManager.createQuery(
             "SELECT b FROM Bid b ORDER BY b.amount DESC", Bid.class)   // C
            .getResultList();

        Item item = entityManager.createQuery(
             "SELECT i FROM Item i", Item.class).getSingleResult();      // D

        User user = entityManager.createQuery(
             "SELECT u FROM User u", User.class).getSingleResult();      // E

        assertAll(
            () -> assertEquals(2, bids.size()),
            () -> assertEquals(new BigDecimal(2000), bids.get(0).getAmount()),
            () -> assertEquals(new BigDecimal(1000), bids.get(1).getAmount()),
            () -> assertEquals("Item1", item.getName()),
            () -> assertEquals("John",  user.getFirstName()),
            () -> assertEquals("Smith", user.getLastName()));

        entityManager.getTransaction().commit();
    } finally {
        entityManager.close();
    }
}
这才是最惊人的部分

"SELECT b FROM Bid b ORDER BY b.amount DESC"——一句标准 JPQL，被翻译成了 MongoDB 的查询。回想第 17 章你要手写的那些 {"$gte": ...} 过滤器，对比一下就明白 OGM 抽象的分量了。当然，代价也在这里：你放弃了对底层查询的直接控制，也放弃了 MongoDB 特有的能力（聚合管道、地理索引等）。

最后清理，保持数据库干净、测试相互独立：

@AfterEach
void afterEach() {
    EntityManager entityManager = entityManagerFactory.createEntityManager();
    try {
        entityManager.getTransaction().begin();

        User fetchedUser = entityManager.find(User.class, john.getId());
        Item fetchedItem = entityManager.find(Item.class, item.getId());
        Bid  fetchedBid1 = entityManager.find(Bid.class,  bid1.getId());
        Bid  fetchedBid2 = entityManager.find(Bid.class,  bid2.getId());

        entityManager.remove(fetchedBid1);
        entityManager.remove(fetchedBid2);
        entityManager.remove(fetchedItem);
        entityManager.remove(fetchedUser);

        entityManager.getTransaction().commit();
    } finally {
        entityManager.close();
    }
}

18.3 切换到 Neo4j

Neo4j 也是一个 NoSQL 数据库，具体说是面向图的数据库。与用类 JSON 文档存数据的 MongoDB 不同，Neo4j 用图来存：图由保存数据的节点和表示关系的边组成。Neo4j 可以以桌面版或嵌入式版运行（我们的演示用嵌入式）。

Hibernate OGM 的高效之处在于：我们仍然可以使用之前展示的 JPA 代码来定义实体、描述与数据库的交互——那些代码保持不变。我们只需要在配置层面做改动。

Ch18/hibernate-ogm/pom.xml（改后）
<dependency>
    <groupId>org.hibernate.ogm</groupId>
    <artifactId>hibernate-ogm-neo4j</artifactId>
</dependency>
Ch18/hibernate-ogm/src/main/resources/META-INF/persistence.xml（改后）
<persistence-unit name="ch18.hibernate_ogm">                          <!-- A：名字都没变 -->
    <provider>org.hibernate.ogm.jpa.HibernateOgmPersistence</provider>  <!-- B：provider 也没变 -->
    <properties>
        <property name="hibernate.ogm.datastore.provider"
                  value="neo4j_embedded" />                              <!-- C：嵌入式 Neo4j -->
        <property name="hibernate.ogm.datastore.database"
                  value="hibernate_ogm" />                                   <!-- D -->
        <property name="hibernate.ogm.neo4j.database_path"
                  value="target/test_data_dir" />                            <!-- E -->
    </properties>
</persistence-unit>
C 数据存储 provider 是 Neo4j，且数据库是嵌入式的（跑在同一个 JVM 里，不需要单独装服务）。
E 数据库路径在 Maven 创建的 target 目录下的 test_data_dir 里。

应用的功能在 Neo4j 上和在 MongoDB 上完全一样。使用 Hibernate OGM，代码原封不动，JPA 就能访问不同种类的 NoSQL 数据库——改动只发生在配置层面。

别忘了那个代价

18.1 节提过：可移植性可能以影响执行速度为代价。你还放弃了每种 NoSQL 数据库的原生特性——MongoDB 的聚合管道、Neo4j 的 Cypher 图遍历，用 JPQL 都表达不出来。所以真正的选择是：

  • 用 Hibernate OGM：需要在多种存储间保持可移植、或团队只想维护一套 JPA 技能栈时
  • 用 Spring Data MongoDB（第 17 章）：确定用 MongoDB 且想榨干它的原生能力时

本章小结

  • 可以创建一个使用 MongoDB 的简单 Hibernate OGM 应用，并设置好与数据库交互所需的 Maven 依赖：BOM（版本统一管理）+ hibernate-ogm-mongodb + JTA 实现。
  • 可以用 MongoDB provider 和一个 MongoDB 数据库来配置持久化单元——关键是 <provider>org.hibernate.ogm.jpa.HibernateOgmPersistence</provider> 和 hibernate.ogm.datastore.provider。
  • 可以创建只使用 JPA 注解和功能的实体（@Entity / @Embedded / @OneToMany），把它们持久化到 MongoDB，并验证插入结果。注意标识符要用 uuid2 策略，因为 NoSQL 没有自增列和序列。
  • 可以从面向文档的 MongoDB 切换到面向图的 Neo4j，只改 Maven 依赖和持久化单元配置——这是本章的核心结论。
  • 可以把之前创建的、只使用 JPA 注解的实体持久化到 Neo4j 数据库，完全不碰已有代码。JPQL 查询也照旧工作。
  • 代价是执行速度可能受影响，以及放弃各数据库的原生特性。要不要接受这个交换，取决于你更看重可移植性还是极致性能。
