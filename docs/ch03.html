第 3 章　领域模型与元数据

本章引入贯穿全书的例子 CaveatEmptor（在线拍卖系统，拉丁文「买家当心」），并回答两个工程问题：可持久化的 Java 类该长什么样，以及映射元数据写在哪里。

JPA 2 的两个重要新特性（本章会用到）

① JPA 提供者会自动集成 Bean Validation 提供者 —— 存数据时自动校验持久化类上的约束。
② 新增 Metamodel API —— 可以取到持久化单元中各个类的名字、属性和映射元数据。

3.1示例应用：CaveatEmptor

3.1.1　分层架构

任何非平凡应用都应按关注点（concern）组织类。持久化是一种关注点，展现、工作流、业务逻辑是另一些。分层架构在这些关注点之间定义接口，让一层的实现方式改变时不至于严重冲击其他层。

3.1.2　分析业务域

这一步要和领域专家一起，识别相关的主要实体及其交互。实体通常是系统用户能理解的概念：支付、客户、订单、商品、出价……有些是抽象一些的东西（如定价算法），但用户一般也能理解。这些实体存在于业务的概念视图中，有时称为信息模型（information model）。

对象模型 vs 数据模型：谁先谁后不重要

工程师可以从 UML 类图（对象模型）出发，也可以从 E-R 图（数据模型）出发。就持久化而言，两者差别很小，只是起点不同。我们真正关心的是：业务实体的结构与关系、保证数据完整性所需的规则（如关系的多重性）、以及操纵数据的代码过程（通常不在模型中）。

3.1.3　CaveatEmptor 领域模型

业务规则：拍卖采用英式拍卖策略 —— 用户对某商品不断出价，直到该商品的竞价期结束，出价最高者胜出。商品按类别分层组织，可浏览可搜索；商品可挂图片；用户信息含姓名、地址、账单信息。

领域模型的实体应当同时封装状态与行为

例如 User 实体既定义客户的姓名地址，也应包含「计算运往该客户的运费」这类逻辑。业务规则并非不重要，只是它们大多与持久化问题正交，所以本书不深入。

什么时候不需要领域模型

完整 ORM 最适合富领域模型的应用。如果你的应用没有复杂业务规则、实体之间也没有复杂交互，或者实体很少，那么面向表的方案（围绕数据库数据模型设计、逻辑放存储过程里）往往更合适。还要考虑学习曲线：一旦你精通了 Hibernate 和 Spring Data，你会想在所有应用里用它 —— 但对一个平凡的用例来说，这份时间和开销未必值得。

3.2实现领域模型

3.2.1　关注点泄漏（leakage of concerns）

当持久化、事务管理、授权这类关注点开始出现在领域模型类里，就发生了关注点泄漏。领域模型实现是被反复复用的核心代码，不应依赖任何正交的 API——比如领域模型里的代码不该直接（或经由某个中间抽象）调用数据库。

3.2.2　透明持久化与自动持久化

透明（transparent）领域模型的持久化类与持久化层之间完全分离关注点。持久化类不知道也不依赖持久化机制；从类内部看不到任何指向外部持久化机制的引用。
自动（automatic）持久化方案（你的注解化领域 + 持久化层 + 机制）把你从底层机械细节中解放出来 —— 不用写大部分 SQL，不用摆弄 JDBC API。
没有完全透明的持久化

每个自动持久化层（JPA 与 Hibernate 也不例外）都会对持久化类提出一些要求：

  • 集合类型的属性必须声明为接口（java.util.Set、List），不能是 HashSet 这种具体实现（这本来就是好实践）。
  • JPA 实体类必须有一个特殊属性：数据库标识符（限制很小，而且通常很方便）。

3.2.3　编写可持久化的类（POJO）

规则说明
可以是抽象类可以继承非持久化类、可以实现接口
必须是顶层类不能嵌套在另一个类里面
不能是 final类和访问持久化字段的方法都不能 final —— 这是 JPA 规范的要求。Hibernate 没这么严格，但 final 会阻止它用代理模式做性能优化。想保持在不同 JPA 提供者之间可移植，就守规范。
无参构造器Hibernate/JPA 要求每个持久化类有无参构造器（或者你干脆一个构造器都不写，用 Java 默认的）。Hibernate 通过反射调用它创建实例。不必 public，但至少要包可见，否则无法用运行期生成的代理做优化。
属性 = 字段 + 访问器通常私有/受保护字段 + 公有/受保护的 getter/setter。遵循 JavaBean 命名约定（getXxx / setXxx，boolean 可用 isXxx），Hibernate 这类通用工具才好发现和操纵属性值。
访问器不是必须的Hibernate 既能直接访问字段，也能调用访问器方法。你可以把某些访问器改成非 public 甚至删掉，然后配置 Hibernate 对这些属性走字段访问。
…/ch03/ex01/User.java　—— 最简 POJO
public class User {
    private String username;

    public String getUsername() {
        return username;
    }
    public void setUsername(String username) {
        this.username = username;
    }
}
…/ch03/ex02/User.java　—— 访问器里放逻辑
public class User {
    private String firstname;
    private String lastname;

    // 数据库只有一列 NAME，但类里有两个字段
    public String getName() {
        return firstname + ' ' + lastname;
    }
    public void setName(String name) {
        StringTokenizer t = new StringTokenizer(name);
        firstname = t.nextToken();
        lastname  = t.nextToken();
    }
}
为什么偏爱 JavaBean 风格访问器：封装

你可以在不改变公有接口的前提下修改属性的内部实现。如果配置 Hibernate 走方法访问，就把类的内部数据结构（实例变量）从数据库设计中抽象出来了。不过后面你会看到，这类场景更好的解法是持久化服务里的自定义类型转换器（第 6 章）—— 多一个选择总是好的。

脏检查的三个细节

getter 返回新实例是安全的Hibernate 按值而非对象标识来比较，判断属性的持久状态是否需要更新。所以 return new String(firstname); 不会引发多余的 UPDATE。
但集合 setter 会item.setBids(bids); em.persist(item); item.setBids(bids); 会导致一条不必要的 UPDATE，因为 Hibernate 有自己的集合实现（PersistentSet / PersistentList / PersistentMap），你把它替换掉了。为整个集合提供 setter 本来就不是好实践。
访问器抛异常怎么办抛 RuntimeException（非受检）→ 当前事务回滚，异常交由调用 JPA/Hibernate API 的代码处理。抛受检的应用异常 → Hibernate 把它包装进 RuntimeException。

3.2.4　实现 POJO 关联：双向链接的两个动作

Item 与 Bid 之间是一对多/多对一。关联相关的属性和操纵它们的方法称为脚手架代码（scaffolding code）：

…/ch03/ex03/Bid.java
public class Bid {
    private Item item;                // 多对一

    public Item getItem() { return item; }
    public void setItem(Item item) {
        this.item = item;
    }
}
…/ch03/ex03/Item.java
public class Item {
    private Set<Bid> bids = new HashSet<>();

    public Set<Bid> getBids() {
        return Collections.unmodifiableSet(bids);
    }
}
为什么用 Set 并初始化为 new HashSet<>()

① JPA 要求集合属性用接口类型（Set/List/Collection）。② 应用不允许重复出价，所以选 Set。③ 初始化能避免 NullPointerException —— 访问一个新建 Item 的 bids 时会得到空集合。JPA 提供者也必须给映射的集合属性设置非空值（比如从数据库加载一个没有出价的 Item 时）；具体实现由提供者决定，Hibernate 用的是自己带脏检查能力的集合实现。

出价难道不该用 List 保序吗？

第一反应往往是想保留用户录入的顺序。但展示顺序不该被持久化：数据完整性不受展示顺序影响。你会存每次出价的金额（随时能找最高价）和创建时间戳（随时能找最新出价）。拿不准时保持系统灵活 —— 排序应发生在从数据存储取出时（查询里）或展示给用户时（Java 代码里），而不是存储时。

链接一个 Bid 与一个 Item：必须做两件事

三条配套的防御措施
  1. 让 addBid()（也许再加个 removeBid()）成为 bids 的唯一对外可见变更入口 → 考虑把 Bid#setItem() 降为包可见。
  2. Item#getBids() 不要返回可修改集合。用 Collections.unmodifiableSet(s) 包一层：客户端直接往集合里加的 Bid 虽然属于该 Item，却没有指回该 Item 的引用，按数据库约束就是不一致状态。
  3. 把「用指针网络模型」和「用外键声明式约束」对比一下就明白：关系模型一条声明式约束能保证的东西，对象模型里你得写过程式代码来保证。

另一条路：不可变实例 + 构造器强制完整性

…/ch03/ex04/Bid.java
public class Bid {
    private Item item;

    public Bid() { }                  // ← Hibernate 需要它，至少包可见

    public Bid(Item item) {
        this.item = item;
        item.bids.add(this);         // 同时维护双向；Item#bids 改为包私有
    }
    public Item getItem() { return item; }   // 没有 setItem()
}
这条路的代价
  • Hibernate 调不了这个有参构造器 → 必须补一个至少包可见的无参构造器。
  • 没有 setItem() → 必须配置 Hibernate 直接访问字段。
  • 于是字段不能是 final → 类并不能真正保证不可变。

要包几层便捷方法由你决定，但请保持一致，对所有领域模型类用同一套策略。

3.3领域模型元数据

元数据是关于数据的数据。ORM 工具需要元数据来指定：类↔表、属性↔列、关联↔外键、Java 类型↔SQL 类型……创建并维护这些信息是工程师的职责。JPA 标准化了两种元数据方式：

3.3.1　基于注解的元数据

import javax.persistence.Entity;

@Entity
public class Item { }   // 所有属性自动按默认策略变为持久化状态的一部分
我的类现在依赖 JPA 了吗？

编译领域模型源码时 classpath 上需要 JPA 库。但创建实例时不需要（比如一个不执行任何 JPA 代码的客户端应用）。只有当运行期通过反射访问这些注解时（Hibernate 内部读元数据就是这么干的）才需要这些包在 classpath 上。

厂商扩展

@Entity
@org.hibernate.annotations.Cache(
    usage = org.hibernate.annotations.CacheConcurrencyStrategy.READ_WRITE
)
public class Item { }
好实践：Hibernate 注解写全限定包名

用 org.hibernate.annotations. 前缀，你能一眼看出哪些元数据来自 JPA 规范、哪些是厂商特有的；而且全局搜索 org.hibernate.annotations 就能一次列出应用里所有非标准注解。换 JPA 提供者时，你只需替换这些厂商扩展。

全局注解元数据

@Entity 映射的是某个具体类。但像 @NamedQuery 这种是全局作用域的，放哪儿？作者建议放在包级注解文件 package-info.java 里 —— 集中一处，不用翻遍源文件。

Ch03/domainmodel/src/main/java/…/ch03/ex05/package-info.java　（注意 package 声明在最下面）
@org.hibernate.annotations.NamedQueries({
    @org.hibernate.annotations.NamedQuery(
        name  = "findItemsOrderByName",
        query = "select i from Item i order by i.name asc"
    ),
    @org.hibernate.annotations.NamedQuery(
        name    = "findItemBuyNowPriceGreaterThan",
        query   = "select i from Item i where i.buyNowPrice > :price",
        timeout = 60,                     // 秒！
        comment = "Custom SQL comment"
    )
})

3.3.2　给 Java 对象加约束：Bean Validation

核心思想：声明「这个属性不能为 null」「这个数必须在某范围内」，比反复写 if-then-else 更容易、更不易错。而且把规则声明在应用的中心组件（领域模型）上，系统的每一层都能用上这些完整性检查。

Ch03/validation/src/main/java/…/ch03/validation/Item.java
import javax.validation.constraints.Future;
import javax.validation.constraints.NotNull;
import javax.validation.constraints.Size;

public class Item {
    @NotNull
    @Size(min = 2, max = 255,
           message = "Name is required, maximum 255 characters.")
    private String name;      // 必填、可读（一个字的名字没意义）、不过长

    @Future
    private Date auctionEnd;  // 拍卖结束时间显然应该在未来
}
注解在字段上校验引擎直接访问字段。
注解在 getter 上走访问器调用。注意：setter 上的注解不被支持。放 getter 的好处是约束成为类 API 的一部分，会出现在 Javadoc 里，让领域模型更易理解。
互相独立约束属于类 API 这件事，与 JPA 提供者用哪种访问方式无关 —— Hibernate Validator 可能调访问器，而 Hibernate ORM 可能直接读字段。
不限于内置注解你可以自定义约束和注解。类级的自定义约束还能一次校验实例上的多个属性值。
Ch03/validation/src/test/java/…/ch03/validation/ModelValidation.java　（手工校验，实际很少这么写）
ValidatorFactory factory = Validation.buildDefaultValidatorFactory();
Validator validator = factory.getValidator();

Item item = new Item();
item.setName("Some Item");
item.setAuctionEnd(new Date());          // ← 「现在」不是未来！

Set<ConstraintViolation<Item>> violations = validator.validate(item);
ConstraintViolation<Item> violation = violations.iterator().next();
String failedPropertyName =
        violation.getPropertyPath().iterator().next().getName();

assertAll(() -> assertEquals(1, violations.size()),
          () -> assertEquals("auctionEnd", failedPropertyName),
          () -> { if (Locale.getDefault().getLanguage().equals("en"))
                      assertEquals(violation.getMessage(), "must be a future date"); });

3.3.3　用 XML 文件外置元数据

Ch03/metadataxmljpa/src/test/resources/META-INF/orm.xml　（放这个路径会被自动识别）
<entity-mappings version="2.2" …>
  <persistence-unit-metadata>                          ❶ 全局元数据
      <xml-mapping-metadata-complete/>                  ❷ 完全忽略所有映射注解！
      <persistence-unit-defaults>
          <delimited-identifiers/>                      ❸ 转义所有 SQL 名字（表名叫 "USER" 这种关键字时有用）
      </persistence-unit-defaults>
  </persistence-unit-metadata>

  <entity class="com.manning…metadataxmljpa.Item" access="FIELD">   ❹ 声明为实体，字段访问
     <attributes>
         <id name="id"><generated-value strategy="AUTO"/></id>
         <basic name="name"/>
         <basic name="auctionEnd"><temporal>TIMESTAMP</temporal></basic>
     </attributes>
  </entity>
</entity-mappings>

想用别的文件名或多个文件，就在 META-INF/persistence.xml 里声明：

<persistence-unit name="persistenceUnitName">
    <mapping-file>file1.xml</mapping-file>
    <mapping-file>file2.xml</mapping-file>
</persistence-unit>

不是「替换」而是「覆盖」：去掉 complete 标记

<entity class="com.manning…metadataxmljpa.Item">
    <attributes>
        <basic name="name">
            <column name="ITEM_NAME"/>      默认会映射到 NAME 列，这里改成 ITEM_NAME
        </basic>
    </attributes>
</entity>
覆盖的精确语义（很容易搞错）
  • Hibernate 会忽略 Item#name 属性上所有 javax.persistence.annotation 和 org.hibernate.annotations 的注解。
  • 但不会忽略 Bean Validation 注解 —— 依然用于自动校验和 schema 生成。
  • Item 类上其他所有注解仍然生效。
  • 这段映射没有指定访问策略，因此按 Item 中 @Id 注解的位置决定走字段还是访问器。

3.3.4　运行期访问元数据：动态 vs 静态元模型

两种口味，都是只读的，运行期不能修改元数据。

动态 Metamodel API

Ch03/metamodel/src/test/java/…/ch03/metamodel/MetamodelTest.java
Metamodel metamodel = emf.getMetamodel();       // 也可 em.getMetamodel()
Set<ManagedType<?>> managedTypes = metamodel.getManagedTypes();
ManagedType<?> itemType = managedTypes.iterator().next();

assertAll(() -> assertEquals(1, managedTypes.size()),
          () -> assertEquals(Type.PersistenceType.ENTITY, itemType.getPersistenceType()));

// 再往下挖每个属性
SingularAttribute<?,?> idAttribute = itemType.getSingularAttribute("id");
assertFalse(idAttribute.isOptional());          // 主键，不可为 NULL

SingularAttribute<?,?> nameAttribute = itemType.getSingularAttribute("name");
assertAll(() -> assertEquals(String.class, nameAttribute.getJavaType()),
          () -> assertEquals(Attribute.PersistentAttributeType.BASIC,
                             nameAttribute.getPersistentAttributeType()));

SingularAttribute<?,?> auctionEndAttribute = itemType.getSingularAttribute("auctionEnd");
assertAll(() -> assertEquals(Date.class, auctionEndAttribute.getJavaType()),
          () -> assertFalse(auctionEndAttribute.isCollection()),
          () -> assertFalse(auctionEndAttribute.isAssociation()));
动态 API 的软肋

属性是用字符串访问的。这显然不类型安全 —— 一旦你改了属性名，这段代码就失效且过时，而且 IDE 的重构操作不会自动包含这些字符串。

静态元模型：把类型安全找回来

✗ 字符串版：类型安全在这里断掉
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Item> query = cb.createQuery(Item.class);
Root<Item> fromItem = query.from(Item.class);
query.select(fromItem);

Path<String> namePath = fromItem.get("name");   ← 字符串
query.where(cb.like(namePath,
        cb.parameter(String.class, "pattern")));

List<Item> items = em.createQuery(query)
        .setParameter("pattern", "%Item 1%")
        .getResultList();
// 等价于 select i from Item i where i.name like :pattern
✓ 静态元模型版：编译期就能发现不匹配
query.where(
    cb.like(
        fromItem.get(Item_.name),          ← 类型安全
        cb.parameter(String.class, "pattern")
    )
);
Ch03/metamodel/pom.xml
<dependency>
    <groupId>org.hibernate</groupId>
    <artifactId>hibernate-jpamodelgen</artifactId>
    <version>5.6.9.Final</version>
</dependency>
为什么值得

用字符串时，你可以放心地用 IDE 重构工具重命名 Item 实体类（查询仍然工作），但一旦动了 Item#name 属性就必须手工调整 —— 只能寄望测试失败时能发现。静态元模型把这个错误从运行期提前到编译期。

本章小结

  • 先分析了信息模型、数据模型这些抽象概念，再落到 JPA/Hibernate 上，以便从 Java 程序操作数据库。
  • 持久化类的实现应不含任何横切关注点（日志、授权、事务边界）。
  • 持久化类只在编译期依赖 JPA。
  • 持久化相关的关注点不应泄漏进领域模型实现。
  • 要想让业务对象能被独立执行和测试，透明持久化很重要。
  • POJO 概念与 JPA 实体编程模型有诸多共同点，都源自老的 JavaBean 规范：属性实现为私有/受保护字段，访问器方法一般是公有/受保护的。
  • 元数据可用注解（推荐）、XML 描述符（可替换或覆盖注解）表达；Bean Validation 约束也可视为一种 ORM 元数据。
  • 运行期访问元数据有两条路：动态元模型（字符串，灵活但不安全）与静态元模型（Item_，由 hibernate-jpamodelgen 生成，类型安全、重构友好）。
