第 10 章　管理数据

前面九章解决的是静态的失配问题（结构映射）。但高效的应用还需要更多：运行期的数据管理策略。本章剖析实体实例的生命周期 —— 一个实例如何变成持久的、又如何不再被视为持久的，以及触发这些转换的方法调用。

JPA 2 的重要新特性

① EntityManager#unwrap() 可拿到厂商特有的持久化管理器 API（如 org.hibernate.Session）；用前面演示过的 EntityManagerFactory#unwrap() 取 SessionFactory（§2.5）。
② 新的 detach() 操作提供对持久化上下文的细粒度管理，可逐出单个实体实例。
③ 可从已有 EntityManager 用 getEntityManagerFactory() 拿到创建它的工厂。
④ 新的静态帮助方法 PersistenceUtil 与 PersistenceUnitUtil 可判断某实体实例（或其某个属性）是已完全加载还是未初始化的引用（Hibernate 代理或未加载的集合包装器）。

本章不用 Spring Data JPA，甚至不用 Spring 框架

后续示例用 JPA、有时用 Hibernate API，不做任何 Spring 集成 —— 因为它们粒度更细，更适合演示与分析。运行前先执行 Ch10/Ch10.sql；源码在 managing-data 和 managing-data2 目录。

10.1持久化生命周期

JPA 是透明的持久化机制：类不知道自己有持久化能力，因此可以写出不关心数据是持久状态还是仅存于内存的临时状态的应用逻辑。例如调用 Item#calculateTotalPrice() 业务方法时，完全不必考虑持久化（比如在单元测试里）。

三个必须掌握的术语
持久化生命周期实体实例一生中经历的各种状态。
工作单元 unit of work一组（可能）改变状态的操作，被视作一个（通常是原子的）组。
持久化上下文持久化服务提供的一项服务，记住某个工作单元中对数据所做的一切修改与状态变更（这个说法有点简化，但是个好起点）。

10.1.1　四种实体实例状态

状态含义与要点
Transient
瞬时		用 new 创建，不再被引用就丢失并被 GC。Hibernate 不为瞬时实例提供任何回滚能力 —— 改了瞬时 Item 的价格，无法自动撤销。转为持久态需要：调 persist()，或被一个已持久实例引用且该关联开启了级联
Persistent
持久		在数据库中有对应表示（或工作单元结束时将被存入）。有数据库标识，其标识符被设为数据库表示的主键值。持久实例总是关联着一个持久化上下文
Removed
已删除		调 remove()，或从开启了 orphan removal 的映射集合中移除引用。提供者会在工作单元结束时删除它。用完之后应丢弃应用中持有的任何引用（例如渲染完给用户看的删除确认页之后）
Detached
游离		加载一个实例、结束工作单元、关闭持久化上下文之后，应用仍持有对它的引用 —— 它现在处于游离态，数据正在变陈旧。可以丢弃让 GC 回收，也可以继续在游离态操作数据，之后在新工作单元里调 merge() 保存修改

10.2EntityManager 接口

10.2.1　典型的工作单元

managing-data/src/test/java/…/ch10/SimpleTransitionsTest.java
EntityManagerFactory emf = Persistence.createEntityManagerFactory("ch10");
// EntityManagerFactory 代表一个持久化单元（一个逻辑数据库），全应用共享；
// EntityManager 用于单线程中的单个工作单元，创建成本很低
EntityManager em = emf.createEntityManager();
try {
    em.getTransaction().begin();
    // …
    em.getTransaction().commit();
} catch (Exception ex) {
    // 事务回滚、异常处理（不要写空的 catch 块！第 11 章细讲）
} finally {
    if (em != null && em.isOpen())
        em.close();          // 必须放在 finally 块里
}
Hibernate 什么时候才真正碰数据库？
  • 创建 EntityManager 就开启了持久化上下文，但 Hibernate 不到必要时不访问数据库 —— 要执行 SQL 时才从池里取 JDBC Connection。可以创建并关闭一个 EntityManager 而完全不碰数据库。
  • 它在查找/查询数据时、以及把上下文检测到的变更刷新到数据库时执行 SQL。
  • 创建 EntityManager 时它加入正在进行的系统事务并等待提交；收到提交通知后对上下文做脏检查并同步数据库。也可以随时调 flush() 手动强制同步。
  • 你通过决定何时 close() 来决定持久化上下文的作用域。下文示例假设：这是一个服务端，多线程环境下每个客户端请求用一个持久化上下文 + 一个系统事务处理（想象把这段代码嵌进 servlet 的 service() 方法）。

10.2.2　让数据变持久：persist()

Item item = new Item();
item.setName("Some Item");
em.persist(item);                // 现在由当前持久化上下文管理并关联
Long ITEM_ID = item.getId();
三个实践要点

① 最好（但非必需）在纳入上下文管理之前把 Item 完全初始化好。SQL INSERT 里的值是调 persist() 那一刻实例持有的值。若在变持久前没设 name，可能违反 NOT NULL 约束。persist() 之后再改也可以，改动会通过一条额外的 UPDATE 传播到数据库。

② 刷新时若 INSERT/UPDATE 失败，Hibernate 会在数据库层回滚本事务对持久实例所做的更改，但不会回滚内存中的修改。如果你在 persist() 之后改了 Item#name，提交失败不会把名字回滚成旧值。这是合理的：事务失败通常不可恢复，你必须立刻丢弃失败的持久化上下文和 EntityManager。

用标识符判断实体状态
PersistentEntityManager#contains(e) 返回 true
TransientPersistenceUnitUtil#getIdentifier(e) 返回 null
Detached不是持久态，且 getIdentifier(e) 返回实体标识符属性的值

两个坑：① 标识符值可能要到上下文被刷新后才可用；② 如果标识符属性是基本类型（long 而非 Long），Hibernate（与某些其他 JPA 提供者不同）永远不会从 getIdentifier() 返回 null。PersistenceUnitUtil 从 EntityManagerFactory 获取。

10.2.3　检索并修改持久数据：find()

Item item = em.find(Item.class, ITEM_ID);   // 若不在上下文中就打库；泛型方法，无需强制转换
if (item != null)
    item.setName("New Name");              // 上下文自动检测改动并记录到数据库

// 可重复读 + 对象标识保证
Item itemA = em.find(Item.class, ITEM_ID);  // ❶ 打库，用 SELECT 取回
Item itemB = em.find(Item.class, ITEM_ID);  // ❷ 在持久化上下文中解析，返回同一个缓存实例
assertTrue(itemA == itemB);
assertTrue(itemA.equals(itemB));
assertTrue(itemA.getId().equals(itemB.getId()));
行为说明
找不到时返回 null
是否打库上下文缓存里没有对应类型+标识符的命中，find() 就一定打库（除非开启了可选的二级缓存）
是否完全初始化加载期间实体实例总是被完全初始化。因此可以放心地在游离态使用它的全部值（例如关闭上下文后渲染页面）
UPDATE 包含哪些列默认 Hibernate 把映射表的所有列都写进 UPDATE，未变的列更新为旧值 —— 因此这些基础 SQL 可以在启动时生成而非运行时。想只含变更列，开启动态 SQL（§5.3.2）
脏检查怎么做把 Item 与加载时拍下的快照副本比较。快照消耗内存；刷新时要把上下文中所有实例与快照逐一比较，也可能耗时
写库时机Hibernate 尽可能晚地把状态变更传播到数据库（靠近事务末尾）—— DML 语句通常会在数据库产生持有到事务结束的锁，这样能把锁持有时间压到最短

10.2.4　获取引用：getReference()

Item item = em.getReference(Item.class, ITEM_ID);
PersistenceUnitUtil persistenceUtil = emf.getPersistenceUnitUtil();
assertFalse(persistenceUtil.isLoaded(item));   // 检测是否是未初始化代理

// assertEquals("Some Item", item.getName());   ← 这会触发 SELECT
// Hibernate.initialize(item);                  ← 或者显式加载代理数据

em.getTransaction().commit();
em.close();                                    // item 现在是游离态
assertThrows(LazyInitializationException.class,
             () -> item.getName());            // 上下文关了就没法按需加载了

代理（proxy）的语义

① 上下文里已有该标识符的 Item → 直接返回它，不打库。

② 当前没有被管理的该实例 → Hibernate 造一个空壳占位符：代理。所以 getReference() 不访问数据库，也不会像 find() 那样返回 null。

③ 一旦调用代理上的任何方法（如 getName()），就执行 SELECT 完全初始化它。例外是被映射的数据库标识符 getter（如 getId()） —— 代理看着像真货，其实只是个携带标识符值的占位符。

④ 代理初始化时若数据库记录已不存在 → 抛 EntityNotFoundException。注意这个异常可能在调 getName() 时才抛出。

解法很简单

在关闭持久化上下文之前把数据加载好。更多关于代理、懒加载和按需抓取的内容在第 12 章。

10.2.5　让数据变瞬时：remove()

Item item = em.find(Item.class, ITEM_ID);   ❶ 执行 SELECT 加载 Item
em.remove(item);                            ❷ 排队等待工作单元结束时删除 → removed 态
assertFalse(em.contains(item));             ❸ removed 态不再「在持久化上下文中」
// em.persist(item);                        ❹ 可以撤销删除，让它重新变持久
assertNull(item.getId());                   ❺ 仅当开启 use_identifier_rollback 时才为 null
em.getTransaction().commit();               ❻ 同步状态转换，执行 SQL DELETE
em.close();
对代理调 remove()Hibernate 会执行 SELECT 加载数据 —— 实体实例在生命周期转换期间必须被完全初始化：可能启用了生命周期回调方法或实体监听器（§13.2），实例必须经过这些拦截器才能走完完整生命周期。
标识符值不会被清空默认情况下 Hibernate 不会改动已删除实例的标识符值，所以 item.getId() 仍返回那个已过时的值。有时这有用（比如用户点「撤销」时想把删掉的 Item 重新存回去）。在 persistence.xml 里设 hibernate.use_identifier_rollback=true，Hibernate 就会在删除后重置标识符值（本例会重置为 Long 的默认值 null），此时 Item 就和瞬时态一样，可以在新的上下文中重新保存。

10.2.6　刷新数据：refresh()

Item item = em.find(Item.class, ITEM_ID);
item.setName("Some Name");
// 此时别人在数据库里把这行改成了 "Concurrent UpdateName"
em.refresh(item);           // 执行 SELECT 读取并组装整个结果集，覆盖内存里已做的修改
em.close();
assertEquals("Concurrent UpdateName", item.getName());
什么时候真的需要它

大多数应用不必手工刷新内存状态 —— 并发修改通常在事务提交时解决。最佳用例是「扩展的持久化上下文」：它可能跨越多个请求/响应周期或多个系统事务。当我们保持上下文打开、等待用户输入时，数据会变陈旧，视会话时长和人机对话情况可能需要选择性刷新。如果用户取消对话，刷新还能用来撤销会话期间在内存中所做的修改。

如果数据库行已不存在（被别人删了），refresh() 会抛 EntityNotFoundException。

10.2.7　复制数据：replicate()（仅 Hibernate Session API）

EntityManager emA = getDatabaseA().createEntityManager();
emA.getTransaction().begin();
Item item = emA.find(Item.class, ITEM_ID);
emA.getTransaction().commit();

EntityManager emB = getDatabaseB().createEntityManager();
emB.getTransaction().begin();
emB.unwrap(Session.class)
   .replicate(item, org.hibernate.ReplicationMode.LATEST_VERSION);
Item item1 = emB.find(Item.class, ITEM_ID);
assertEquals("Some Item", item1.getName());
emB.getTransaction().commit();
ReplicationMode行为
IGNORE目标库已有同标识符的行时，忽略该实例
OVERWRITE覆盖任何同标识符的已有行
EXCEPTION目标库已有同标识符的行时抛异常
LATEST_VERSION数据库中行的版本更旧就覆盖，否则忽略。要求开启带实体版本的乐观并发控制（§11.2.2）

用途：从一个数据库取数据存进另一个（通常来自两个不同的 EntityManagerFactory 配置，代表两个逻辑数据库；实体必须在两套配置里都映射）。典型场景是产品升级 —— 新版本需要新的数据库（schema）时，一次性迁移并复制既有数据。

10.2.8　持久化上下文中的缓存：OutOfMemoryError 的常见原因

很多 Hibernate 用户因为忽略这个简单事实而遇到 OutOfMemoryError

每个持久态的实体实例都关联着持久化上下文。典型场景是：一个工作单元里加载了成千上万个实体实例但根本不打算修改它们 —— Hibernate 仍然必须为每一个在上下文缓存里创建快照，从而耗尽内存。（显然，要改动成千上万行时应该用批量数据操作。）

持久化上下文缓存永不自动收缩，所以应把它的大小保持在必要的最小值。很多时候，上下文里的持久实例是意外进来的 —— 比如只需要几个 item 却查出了一大堆。超大的对象图会有严重的性能后果，并为状态快照占用大量内存。检查你的查询是否只返回了需要的数据。

控制手段效果
em.detach(i)手工把一个持久实例从上下文中逐出
em.clear()游离所有持久实体实例，留下一个空的上下文
em.unwrap(Session.class).setDefaultReadOnly(true)把整个上下文设为只读：禁用状态快照与脏检查，Hibernate 不会把修改写库 —— 因此 flush() 不会更新数据库
em.unwrap(Session.class).setReadOnly(item, true)对单个实体实例禁用脏检查
query.setReadOnly(true)（org.hibernate.query.Query）查询返回只读结果，Hibernate 不检查其修改
em.createQuery(q).setHint(QueryHints.READ_ONLY, true)用查询提示在标准 javax.persistence.Query 上禁用脏检查
小心只读实体实例

你仍然可以删除它们，而且对集合的修改很棘手！如果要把这些设置用在映射集合上，请先阅读 Hibernate 手册里那一长串特殊情形。

10.3处理游离（detached）状态

当一个引用离开了「保证的标识作用域」，我们就称它是对游离实体实例的引用。持久化上下文一关闭，它就不再提供标识映射服务，处理游离实例时会遇到别名（aliasing）问题。

10.3.1　游离实例的标识

SimpleTransitionsTest.java – scopeOfIdentity()
em = emf.createEntityManager();  em.getTransaction().begin();
Item a = em.find(Item.class, ITEM_ID);
Item b = em.find(Item.class, ITEM_ID);
assertTrue(a == b);                      // 同一上下文取得 → Java 标识相同
assertTrue(a.equals(b));                   // 默认 equals() 依赖 Java 标识比较
assertEquals(a.getId(), b.getId());
em.getTransaction().commit();  em.close();  // a、b 现在都是游离态

em = emf.createEntityManager();  em.getTransaction().begin();
Item c = em.find(Item.class, ITEM_ID);      // 在另一个上下文中加载
assertTrue(a != c);                      // 不是同一个实例
assertFalse(a.equals(c));                 // equals() 没被重写 → 用 == 判断
assertEquals(a.getId(), c.getId());        // 但数据库标识测试仍然为 true

10.3.2　实现相等性方法：业务键（business key）

一个看似聪明、实则严重错误的做法：用数据库标识符比较

「两个 Item 的 getId() 相同就是同一个；返回 null 就是尚未保存的瞬时 Item。」

这个方案有一个巨大问题：标识符值直到实例变持久时才由 Hibernate 赋予。如果在保存之前把一个瞬时实例加进了 Set，那么保存时它的哈希值会在仍被 Set 持有的情况下改变 —— 这违反了 java.util.Set 的契约，破坏了这个集合。尤其是，这个问题会让基于 set 的映射关联的级联持久化变得毫无用处。我们强烈不建议用数据库标识符做相等性判断。

业务键的定义

一个属性或若干属性的组合，对每个具有相同数据库标识的实例都是唯一的。本质上，它就是「如果不用代理主键的话我们会用的那个自然键」。

与自然主键不同，业务键并非绝对不能变 —— 只要变得很少就够了。

作者主张：基本上每个实体类都该有一个业务键，哪怕它包含类的所有属性（对某些不可变类这是合适的）。如果用户在屏幕上看到一列 item，他们靠什么区分 A、B、C？那同一个属性或属性组合就是我们要的业务键。业务键是用户心目中唯一标识一条记录的东西，而代理键是应用和数据库系统依赖的东西。业务键属性在数据库 schema 里很可能带 UNIQUE 约束。

为 User 实体写自定义相等性 —— username 是绝佳的业务键候选
@Entity
@Table(name = "USERS",
        uniqueConstraints = @UniqueConstraint(columnNames = "USERNAME"))
public class User {
    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (other == null) return false;
        if (!(other instanceof User)) return false;      // ← 不要用 getClass() 比较！
        User that = (User) other;
        return this.getUsername().equals(that.getUsername());  // ← 一定要用 getter！
    }
    @Override
    public int hashCode() { return getUsername().hashCode(); }
}
两个至关重要的细节

① 永远通过 getter 访问 other 的属性。因为传进来的 other 可能是一个 Hibernate 代理，而不是真正持有持久状态的实例。你无法直接访问 User 代理的 username 字段；要初始化代理并取到属性值，必须用 getter。这是 Hibernate 不完全透明的一处，不过用 getter 代替直接访问实例变量本来就是好实践。

② 用 instanceof 检查类型，而不是比较 getClass() 的值。同样因为 other 可能是代理 —— 它是 User 在运行期生成的子类，所以 this 和 other 可能不是完全相同的类型，而是有效的父类型或子类型。

③ 在子类上重写 equals() 并加入另一个属性进行比较，极少是正确的。这种情况下要同时满足对称性与传递性很微妙；更重要的是，业务键可能并不对应数据库中任何定义良好的候选自然键（子类属性可能映射到不同的表）。

寻找业务键的五条线索

① 用户如何区分想想应用的用户在现实中要识别一个对象时会引用哪些属性。如果它们显示在屏幕上，用户靠什么分辨？这多半就是你要找的业务键。
② 不可变属性每个不可变属性都可能是好候选。可变属性也可以，只要它很少更新，或你能控制更新时机（比如确保更新时实例不在 Set 里）。
③ UNIQUE 约束每个带数据库 UNIQUE 约束的属性都是好候选。记住业务键的精度必须足够高，避免重叠。
④ 时间属性要小心创建时间戳这类基于日期/时间的属性通常是业务键的好组成部分，但 System.currentTimeMillis() 的精度取决于虚拟机和操作系统。作者建议的安全缓冲是 50 毫秒 —— 如果时间属性是业务键的唯一属性，这个精度可能不够。
⑤ 可以用关联实体的数据库标识符这看似与前面的说法矛盾，但我们说的不是本实体的标识符值，而是关联实体实例的标识符。例如 Bid 的候选业务键是「它所属 Item 的标识符 + 出价金额」；甚至可能在 schema 中就有对应的唯一约束。可以用 Item 的标识符值，因为它在 Bid 的整个生命周期中永不改变 —— Bid 的构造器可以要求传入一个已经持久化的 Item。

遇到难例时，抛开 Hibernate 去想 —— 这纯粹是个面向对象问题。更多关于定制相等性比较的内容，见 Joshua Bloch 的 Effective Java 第三版（Java 程序员的必读书）。

10.3.3　手工游离实例：detach()

User user = em.find(User.class, USER_ID);
em.detach(user);                      // 不必等到上下文关闭，可手工逐出
assertFalse(em.contains(user));       // contains() 判断实例是否处于受管持久态

很多应用只是在持久化上下文关闭之后读取并渲染数据。上下文关闭后再修改已加载的 user，对它在数据库中的持久表示没有任何影响。但 JPA 允许在新的持久化上下文里把这些改动合并回数据库。

10.3.4　合并实体实例：merge()

detachedUser.setUsername("johndoe");         // 在游离态修改
em = emf.createEntityManager();
em.getTransaction().begin();
User mergedUser = em.merge(detachedUser);      // ← 注意：要用返回值
mergedUser.setUsername("doejohn");            // 继续在受管实例上修改
em.getTransaction().commit();                  // 刷新时执行一条 UPDATE
em.close();
基于「游离 + 合并」的架构，最重要的是引用切换

这样的应用架构可能根本不调 persist() —— 新实例和游离实例都可以用 merge 来存。关键差别在于返回的当前状态，以及你在应用代码里如何处理这次引用切换：必须丢弃 detachedUser，从此引用 mergedUser。应用中其他任何仍持有 detachedUser 的组件，也都必须切换到 mergedUser。

能不能「重新附着」一个游离实例？

Hibernate 的 Session API 有个重新附着的方法 saveOrUpdate()：它接受瞬时或游离实例，不返回任何东西；操作后给定实例即处于持久态，所以不必切换引用。传入瞬时实例时执行 INSERT，游离实例时执行 UPDATE。

但作者建议仍然依赖 merge：因为它是标准化的，更容易与其他框架集成；而且如果游离数据没有被修改，merge 可能只触发一条 SELECT 而不是 UPDATE。（顺带一提，Session 的 saveOrUpdateCopy() 就等同于 EntityManager#merge()。）

想删除一个游离实例？先 merge 它，再对 merge 返回的持久实例调 remove()。

本章小结

  • 实体实例的生命周期包括 transient（瞬时）、persistent（持久）、detached（游离）、removed（已删除） 四种状态。
  • JPA 中最重要的接口是 EntityManager，它代表一个持久化上下文，界定了一个工作单元。
  • 用 EntityManager 可以：让数据持久化（persist）、检索与修改持久数据（find）、获取引用（getReference 返回代理）、让数据变瞬时（remove）、刷新（refresh）与复制（replicate）数据、控制上下文中的缓存、刷新上下文（flush）。
  • 持久化上下文提供三大服务：自动脏检查、永远开启的一级缓存、保证的对象标识作用域。它永不自动收缩 —— 加载过多实体是 OutOfMemoryError 的常见原因。
  • 可以在游离状态下工作。此时必须理解游离实例的标识问题，并用业务键（而非数据库标识符）实现 equals()/hashCode()；用 merge() 把改动合并回新的持久化上下文，并切换到它返回的引用。
