第 5 章　映射持久化类

Part 2 开始进入 ORM 的正题：从类和属性到表和列。本章打地基 —— 实体 vs 值类型的根本区分，以及数据库标识与主键该怎么设计。所有映射示例都用 JPA 注解，因此 Hibernate 和 Spring Data JPA 两边都能用。

工程师的角色

把应用域（问题所在的环境，由「应用领域模型」表示，即现实中的实体）与解域（构建系统的软件与技术，由「系统模型」表示，即软件里的对象）连接起来。本章讲的就是这条连线上最基础的一段。

5.1理解实体与值类型

5.1.1　细粒度领域模型

细粒度（fine-grained）直白地说就是：类比表多。数据库里 USERS 表有 HOME_STREET、HOME_CITY、HOME_ZIPCODE 三列；领域模型里你当然可以照抄三个 String 属性，但更好的做法是建一个 Address 类，让 User 有个 homeAddress 属性 —— 内聚更好、复用更多，也比 SQL 那套僵硬的类型系统更易理解。

细粒度还带来类型安全与行为

很多人把 email 建模成 User 的一个 String 属性。更成熟的做法是定义 EmailAddress 类，加入更高层的语义与行为。它可以提供 prepareMail()，但不该有 sendMail() —— 你不希望领域模型类依赖邮件子系统（回顾第 3 章的「关注点泄漏」）。

5.1.2　定义应用概念：John 和 Jane 住在同一间房

两个人住同一栋房子，各自在 CaveatEmptor 注册了账号。User 显然是实体（能独立加载、保存、删除）。那 homeAddress 呢？

5.1.3　区分实体与值类型：给 UML 加构造型

Bid 是个难题（也是最有教学价值的例子）

面向对象建模里 Item—Bid 被标为组合（实心菱形）：容器销毁，被包含对象也销毁。看起来 Bid 该是值类型。

但是：如果将来领域模型需要 User#bids 集合（某用户的全部出价）呢？现在 Bid→User 是单向的（只有 bidder 引用）；一旦双向，就要面对对 Bid 的共享引用，Bid 就必须是实体 —— 它生命周期依赖别人，却必须有自己的标识来支持共享引用。

作者的判断法则：先把一切都当值类型，只在绝对必要时才提升为实体。这里把 Bid 定为值类型（它的标识由 Item 和 User 定义），这并不意味着它不会有自己的表。同时简化关联：与其映射 Item#bids 和 User#bids 两个持久化集合（常常只增加复杂度而无好处），不如写查询去拿某 Item 的全部出价、某 User 的全部出价。

把领域模型落成 POJO 时要处理的三件事

共享引用 Shared references避免对值类型实例的共享引用。比如确保只有一个 User 能引用某个 Address：把 Address 做成不可变、不提供 setUser()，用一个带 User 参数的公有构造器强制这层关系。当然仍需一个（大概是 protected 的）无参构造器，好让框架也能创建实例。
生命周期依赖User 被删除时，它依赖的 Address 也必须删掉。持久化元数据里会为这类依赖写级联规则（第 13 章）。你的应用流程和 UI 也必须预期并尊重这种依赖。
标识 Identity实体类几乎总是需要标识符属性；值类型（以及 String、Integer 这样的 JDK 类）没有 —— 它们通过拥有者实体来被识别。

5.2映射带标识的实体

5.2.1　三种「同一性」，务必分清

概念判定方式由谁定义
对象同一性
object identity		a == b：占据 JVM 中同一内存位置Java 虚拟机
对象相等性
object equality		a.equals(b)：状态相同。不重写就继承 Object 的实现（即用 ==）。须满足自反、对称、传递；这意味着若 a == b，则 a.equals(b) 与 b.equals(a) 都应为 true类的 equals() 方法
数据库标识
database identity		存于关系数据库的对象，若同表且主键值相同则是同一个关系数据库

5.2.2　第一个实体类与它的映射

Ch05/generator/src/main/java/…/ch05/model/Item.java
@Entity
public class Item {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;

    public Long getId() { return id; }   // 只有 getter，没有 setter
}
四条必须记住的规则
  1. 每个实体类都必须有 @Id 属性 —— 这是 JPA 把数据库标识暴露给应用的方式。好实践：所有实体类都把它命名为 id；不额外指定的话，它映射到表中名为 ID 的主键列。
  2. 访问方式由 @Id 的位置决定：@Id 在字段上 ⇒ JPA 提供者直接访问字段，并默认把所有字段都当作持久化状态的一部分。作者的经验是：字段访问往往优于访问器访问，因为它给了你设计访问器方法的自由。
  3. 应该有公有 getter 吗？应该。应用常把数据库标识符当作方便的「句柄」，即便在持久化层之外 —— 比如 Web 应用列出搜索结果摘要，用户点选某项时按标识符查回来。
  4. 应该有 setter 吗？绝对不要。主键值永不改变。Hibernate 不会更新主键列，你也不应在实体上暴露公有的标识符 setter。

5.2.3　选择主键

主键必须不可变吗？

关系模型只要求候选键唯一且不可约；选哪个当主键是品味问题。但 Hibernate 与 Spring Data 期待作为主键的候选键是不可变的 —— 它们的 API 不支持更新主键值；硬绕的话会撞上 Hibernate 的缓存与脏检查引擎。如果你的 schema 依赖可更新主键（甚至用了 ON UPDATE CASCADE），必须先改 schema。「期望你的数据库 schema 存活几十年，即便应用不会。」

5.2.4　配置主键生成器

@Id 只标记标识符属性。不加 @GeneratedValue，JPA 提供者就假定由你在保存前创建并赋值 —— 称为应用赋值标识符，处理遗留数据库或自然主键时才需要。通常你会希望系统在保存时生成主键值。

JPA 标准化的四种策略

GenerationType行为
AUTOHibernate 询问你配置的数据库方言，自行挑一个合适策略。等价于不带参数的 @GeneratedValue()
SEQUENCE期待（用工具的话会创建）数据库里有名为 HIBERNATE_SEQUENCE 的序列。每次 INSERT 之前单独调用它，产生递增数值
IDENTITY期待（并在建表 DDL 中创建）一个特殊的自增主键列，在数据库 INSERT 时自动生成数值
TABLE用一张额外的表保存下一个主键值，每个实体类一行。INSERT 前先读再更新这张表。默认表名 HIBERNATE_SEQUENCES，列为 SEQUENCE_NAME 与 NEXT_VALUE
为什么本书不用 AUTO，而用具名生成器

AUTO 看着方便，但你常常需要更多控制。多数应用用数据库序列，而你可能想自定义序列名和其他设置。于是把标识符映射成 @GeneratedValue(generator = "ID_GENERATOR") —— 一个具名标识符生成器，这样 ID_GENERATOR 的配置就独立于实体类了。

JPA 内置 @SequenceGenerator 与 @TableGenerator 两个注解可以配置具名生成器，但只能放在类顶部（哪怕那是个空类），不能放在 package-info.java 里，而且给不到 Hibernate 的全部能力。因此作者偏爱原生的 @org.hibernate.annotations.GenericGenerator。

Ch05/generator/src/main/java/…/ch05/package-info.java　—— 推荐配置
@org.hibernate.annotations.GenericGenerator(
   name = "ID_GENERATOR",
   strategy = "enhanced-sequence",                    ❶ 产生递增数值
   parameters = {
      @org.hibernate.annotations.Parameter(
         name = "sequence_name", value = "JPWHSD_SEQUENCE"),   ❷ 自定义序列名
      @org.hibernate.annotations.Parameter(
         name = "initial_value", value = "1000")               ❸ 给测试数据留出空间
})
❶ enhanced-sequence方言支持序列 → 用真正的数据库序列；DBMS 不支持 → Hibernate 自己管理一张「序列表」模拟序列行为。这带来真正的可移植性：生成器总能在 INSERT 之前被调用；而自增标识列是在 INSERT 时产生值、之后才返回给应用。
❸ initial_value=1000集成测试跑起来时，测试代码新插入的数据 id 都 > 1000；测试前想导入的种子数据可以用 1–999，于是你能在测试里引用稳定的标识符值：「加载 id 为 123 的 item 并对它做些测试」。这是生成 schema 时的 DDL 选项。
可以全局共享一个序列

所有领域模型类都写 @GeneratedValue(generator = "ID_GENERATOR") 是无害的。某个实体的主键值不连续没关系 —— 只要在一张表内唯一即可。

Hibernate JPA 侧（HelloWorldJPATest）
em.getTransaction().begin();
Item item = new Item();
item.setName("Some Item");
item.setAuctionEnd(Helper.tomorrow());
em.persist(item);
em.getTransaction().commit();
Spring Data JPA 侧（HelloWorldSpringDataJPATest）
Item item = new Item();
item.setName("Some Item");
item.setAuctionEnd(Helper.tomorrow());
itemRepository.save(item);

两种写法运行后结果一样：ITEM 表插入一行，id = 1000（生成器指定的第一个值），下一次要生成的值保存在 JPWHSD_SEQUENCE 里。主键值由框架层管理，程序员从不去碰它。

标识符的 Java 类型该选什么

Long vs long都能完美对应数值序列生成器。区别在于：对一个尚未存库的新 item 调 getId()，前者返回 null，后者返回 0。要判断「是不是新对象」，null 检查对读代码的人更易懂。
不要用 int / short它们能撑一段时间（也许好几年），但随着数据库变大你会撞上取值范围上限。作者的算法：每毫秒生成一个 id 且不留空隙，Integer 撑约两个月，Long 能撑约 3 亿年。

5.2.5　标识符生成器策略全表

不想读完整列表？三句话版本
  1. 打开 GenerationType.AUTO，看看 Hibernate 对你的方言默认选了什么 —— 多半是 sequence 或 identity，都是不错的选择，但未必最高效或最可移植。
  2. 总体上，优先选「预插入」生成策略：在 INSERT 之前独立产生标识符值。常见做法是用一个共享、可并发访问的数据库序列。
  3. 若要一致、可移植、且 INSERT 前就能拿到标识符值，就用 enhanced-sequence。
INSERT 前生成 vs INSERT 后生成，差别在哪？

ORM 会优化 INSERT（比如在 JDBC 层做批处理），所以 SQL 执行发生在工作单元中尽可能晚的时刻，而不是你调 entityManager.persist(someItem) 的那一刻 —— 这只是把插入排进队列，并在可能的情况下赋上标识符值。因此如果引擎没能在 INSERT 前生成标识符，你此时调 someItem.getId() 可能拿到 null。自增列、列默认值、触发器生成的键，都只有在 INSERT 之后才可用。

策略说明对应的 JPA 策略
native按配置的 SQL 方言自动选择（如 sequence 或 identity）。要确定选了哪个，得去看方言的 Javadoc 甚至源码AUTO（旧映射）
sequence使用名为 HIBERNATE_SEQUENCE 的原生数据库序列，每次插入新行前调用。可自定义序列名与额外 DDL 设置（见 org.hibernate.id.SequenceGenerator）—
enhanced-sequence
推荐		支持序列就用原生序列，否则退化为一张单列单行的表来模拟序列（默认表名 HIBERNATE_SEQUENCE）。无论 DBMS 是否支持真序列，行为一致：总在 INSERT 前调用。还支持 org.hibernate.id.enhanced.Optimizer 来避免每次 INSERT 都打数据库（默认不优化）SEQUENCE，以及新映射下的 AUTO
enhanced-table用一张名为 HIBERNATE_SEQUENCES 的额外表，默认一行代表序列并保存下一个值；需要生成时 select 再 update。可配置成多行（每个生成器一行）。替代了过时的 MultipleHiLoPerTableGeneratorTABLE（新映射）
identity支持 DB2、MySQL、MS SQL Server、Sybase 的 IDENTITY / 自增列，值在 INSERT 行时生成。无选项。由于 Hibernate 代码的一个怪癖，无法用 @GenericGenerator 配置它（那样 DDL 不会带上自增选项）—— 唯一用法是 GenerationType.IDENTITYIDENTITY（新旧皆是）
increment启动时读取每个实体表的最大数值主键，之后每插一行加一。仅当非集群的 Hibernate 应用独占数据库时高效，其他场景一律别用—
selectHibernate 不生成键值、INSERT 也不含主键列，指望 DBMS 自己赋值（schema 默认值或触发器），插入后再用 SELECT 取回主键。必填参数 key。效率不高，只适合无法直接返回生成键的老 JDBC 驱动—
uuid2在应用层产生 128 位 UUID。适合需要跨数据库全局唯一的场景（如每晚把多个生产库的数据合并进归档库）。可编码为 String、byte[16] 或 java.util.UUID。取代了遗留的 uuid / uuid.hex—
guid由数据库产生全局唯一标识符，用 Oracle、Ingres、MS SQL Server、MySQL 上的 SQL 函数；Hibernate 在 INSERT 前调用该函数，值映射到 String 属性—
两套映射：old 与 new

Hibernate 是有机生长起来的，标准策略与原生策略之间存在两套映射关系。用 persistence.xml 里的 hibernate.id.new_generator_mappings 切换，默认 true（用新映射）。作者的吐槽：「软件的陈化，可没有葡萄酒那么优雅。」

想要完全掌控生成？把 @GenericGenerator 的 strategy 设成实现 org.hibernate.id.IdentityGenerator 接口的类的全限定名。

别把标识符暴露到业务逻辑之外

比如不要通过 API 对外暴露它 —— 这个标识符没有任何业务含义，只与持久化相关。

5.3实体映射选项

以下都是可选项，可以先跳过，遇到具体问题再回来查。

5.3.1　控制名字

默认表名与 @Table

默认规则只写 @Entity 时，表名 = 类名。Item → ITEM；驼峰会转成蛇形：BidItem → BID_ITEM。
Ch05/mapping/src/main/java/…/ch05/model/User.java
@Entity
@Table(name = "USERS")      // USER 在多数 SQL DBMS 中是保留字
public class User { … }

@javax.persistence.Table 还有 catalog 与 schema 选项，用作命名前缀。

给 SQL 标识符加引号

实现命名约定：PhysicalNamingStrategy

假设 CaveatEmptor 要求所有表名遵循 CE_<table name> 模式。给每个实体类手写 @Table 既耗时又容易漏 —— 用命名策略一次搞定：

Ch05/mapping/src/main/java/…/ch05/CENamingStrategy.java
public class CENamingStrategy extends PhysicalNamingStrategyStandardImpl {
    @Override
    public Identifier toPhysicalTableName(Identifier name, JdbcEnvironment context) {
        return new Identifier("CE_" + name.getText(), name.isQuoted());
    }
}

PhysicalNamingStrategy 接口还提供了自定义列名、序列名等构件的方法。启用方式两边不同：

Hibernate JPA：persistence.xml
<persistence-unit name="ch05.mapping">
  <properties>
    <property
      name="hibernate.physical_naming_strategy"
      value="com.manning…ch05.CENamingStrategy"/>
  </properties>
</persistence-unit>
Spring Data JPA：SpringDataConfiguration
properties.put(
    "hibernate.physical_naming_strategy",
    CENamingStrategy.class.getName());

为查询命名实体

默认所有实体名都被自动导入查询引擎的命名空间，所以 JPQL 里能用不带包前缀的短类名：

List<Item> items = em.createQuery("select i from Item i", Item.class).getResultList();

但这只在持久化单元里只有一个 Item 类时成立。若另一个包里也有 Item，就得改名：

package my.other.model;

@javax.persistence.Entity(name = "AuctionItem")
public class Item { … }

// 现在这个类的短查询形式变成：select i from AuctionItem i
// 当然，你也可以永远用带包前缀的全限定长名

5.3.2　动态 SQL 生成

开启后：UPDATE 只包含被改动的列，INSERT 只包含非空列。

5.3.3　让实体不可变

CaveatEmptor 里，对某商品的一次 Bid 是不可变的，因此永远不需要对 BID 表执行 UPDATE。Hibernate 还能做额外优化，比如跳过脏检查：

@Entity
@org.hibernate.annotations.Immutable
public class Bid { … }
POJO 何时算不可变

不暴露任何属性的公有 setter，所有值都在构造器里设置。Hibernate 加载和存储实例时应直接访问字段 —— 这正是本章前面说的：@Id 放在字段上，Hibernate 就走字段访问，你可以自由设计 getter/setter。注意：并非所有框架都能处理没有 setter 的 POJO。

5.3.4　把实体映射到子查询

DBA 不让你改 schema，甚至连加视图都不行。你想要一个「商品 id + 该商品的出价数」的视图 —— 用 Hibernate 注解创建一个应用级视图：映射到 SQL SELECT 的只读实体类。

Ch05/subselect/src/main/java/…/ch05/model/ItemBidSummary.java
@Entity
@org.hibernate.annotations.Immutable
@org.hibernate.annotations.Subselect(
    value = "select i.ID as ITEMID, i.NAME as NAME, " +
            "count(b.ID) as NUMBEROFBIDS " +
            "from ITEM i left outer join BID b on i.ID = b.ITEM_ID " +
            "group by i.ID, i.NAME"
)
@org.hibernate.annotations.Synchronize({"ITEM", "BID"})   ← 关键！
public class ItemBidSummary {
    @Id
    private Long itemId;
    private String name;
    private long numberOfBids;

    public ItemBidSummary() { }
    // 只有 getter
}
为什么必须写 @Synchronize

你要把 SELECT 里引用的所有表名列进 @Synchronize。这样框架才知道：在对 ItemBidSummary 执行查询之前，必须先刷新（flush）Item 和 Bid 实例的修改。如果内存里有尚未持久化、却会影响该查询的改动，Hibernate 会检测到并在执行查询前刷新；否则结果会是陈旧状态。

根因：ItemBidSummary 类上没有 @Table 注解，框架无从知道执行查询前该自动刷新哪些表。

Hibernate JPA 用法（ItemBidSummaryTest）
TypedQuery<ItemBidSummary> query = em.createQuery(
    "select ibs from ItemBidSummary ibs where ibs.itemId = :id",
    ItemBidSummary.class);
ItemBidSummary s = query.setParameter("id", 1000L)
                        .getSingleResult();
Spring Data JPA 用法：先加一个 repository
public interface ItemBidSummaryRepository
        extends CrudRepository<ItemBidSummary, Long> { }

// ItemBidSummarySpringDataTest
Optional<ItemBidSummary> s =
        itemBidSummaryRepository.findById(1000L);

本章小结

  • 实体是系统中较粗粒度的类：实例有独立生命周期和自己的标识，可被许多其他实例引用。
  • 值类型依附于某个特定实体类：实例绑定在拥有它的实体上，只能被一个实体实例引用，没有独立标识。
  • Java 同一性、对象相等性、数据库标识是三个不同概念：前两个属于面向对象世界，最后一个属于关系数据库世界。
  • 好的主键：永不为 null、唯一、永不改变。优先使用代理键而非自然键。
  • 主键生成器可用不同策略配置。推荐 @GenericGenerator + enhanced-sequence 写在 package-info.java 里，全局共享。优先「预插入」生成。
  • 实体、映射选项与命名策略在 Hibernate JPA 和 Spring Data JPA 两边都能用。
  • 其他实体级选项：@Table 改名与加引号、PhysicalNamingStrategy 统一约定、@DynamicInsert/@DynamicUpdate 动态 SQL、@Immutable 不可变实体、@Subselect+@Synchronize 应用级视图。
