Part 2 · 映射策略

第 7 章　映射继承

「一个持久化实体类对应一张表」这个朴素策略，一碰到继承就崩了。因为面向对象模型同时提供 is a 和 has a 关系，而基于 SQL 的模型只有 has a——SQL DBMS 不支持类型继承，即便有也通常是私有的或不完整的。

§四种策略总览

视角

本章采取自顶向下的视角：假设你从领域模型出发，推导一个新的 SQL schema。但如果你是自底向上（从既有表出发），这些策略同样适用 —— 途中会介绍一些应付不理想表结构的技巧。运行示例前先执行 Ch07/Ch07.sql。

7.1每具体类一张表 + 隐式多态

源码目录 mapping-inheritance-mappedsuperclass

默认情况下超类的属性会被忽略、不会被持久化！

必须给超类加 @MappedSuperclass，才能把它的属性嵌入到各具体子类的表里。

…/ch07/model/BillingDetails.java
@MappedSuperclass
public abstract class BillingDetails {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;

    @NotNull
    private String owner;
}

标识符属性可以像这样声明在超类（所有子类共享列名与生成器策略），也可以在每个具体类里各写一遍。

…/ch07/model/CreditCard.java
@Entity
@AttributeOverride(name = "owner",
    column = @Column(name = "CC_OWNER", nullable = false))
public class CreditCard extends BillingDetails {
    @NotNull private String cardNumber;
    @NotNull private String expMonth;
    @NotNull private String expYear;
}

用 @AttributeOverride 覆盖超类的列映射：把 CREDITCARD 表中的 OWNER 改名为 CC_OWNER。JPA 2.2 起可在同一个类上写多个；2.1 及以前要用 @AttributeOverrides 包起来。

Spring Data 侧：@NoRepositoryBean 的用法

…/ch07/repositories/BillingDetailsRepository.java
@NoRepositoryBean                                ← 关键
public interface BillingDetailsRepository<T extends BillingDetails, ID>
                  extends JpaRepository<T, ID> {
    List<T> findByOwner(String owner);
}

// 两个具体 repository
public interface BankAccountRepository extends BillingDetailsRepository<BankAccount, Long> {
    List<BankAccount> findBySwift(String swift);
}
public interface CreditCardRepository extends BillingDetailsRepository<CreditCard, Long> {
    List<CreditCard> findByExpYear(String expYear);
}
为什么必须加 @NoRepositoryBean

它阻止这个接口被实例化成 Spring Data JPA 的 repository 实例。因为这套 schema 下根本没有 BILLINGDETAILS 表。它的用途只是被子 repository 继承，所以泛型化为 T extends BillingDetails。它含有的 findByOwner 之所以可行，是因为 owner 字段会被同时包含进 CREDITCARD 和 BANKACCOUNT 两张表。

这个策略的四个问题

① 不支持多态关联数据库里关联通常表示为外键。子类各自映射到不同表时，指向超类的多态关联无法表示为简单外键 —— 根本没有 BILLINGDETAILS 这张表可引用。在领域模型里 BillingDetails 与 User 关联，就意味着 CREDITCARD 和 BANKACCOUNT 都要有指向 USERS 的外键。这些问题都不好解决。
② 多态查询要拆成多条 SQLselect bd from BillingDetails bd 会变成两条语句（每个具体子类一条），Hibernate 再在内存里合并结果集。反过来，针对具体类的查询很平凡且性能好——只用其中一条。
③ schema 演进复杂不同表的不同列语义完全相同。重命名或修改超类属性类型 → 要改多张表的多个列。IDE 的很多标准重构操作需要手工调整，因为自动流程通常不考虑 @AttributeOverride。
④ 完整性约束难做要实现适用于所有子类的数据库完整性约束困难得多。
推荐用法

只推荐用于类层次的顶层——那里通常不需要多态，而且未来不太可能修改超类。对某些真实领域模型可行，但不适合 CaveatEmptor（查询和其他实体都要引用 BillingDetails）。

7.2每具体类一张表 + UNION

源码目录 mapping-inheritance-tableperclass

注意

JPA 标准规定 TABLE_PER_CLASS 是可选的，所以并非所有 JPA 实现都支持。

@Entity                                                    ← 不再是 @MappedSuperclass
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class BillingDetails {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;                // 现在必须在超类，供所有子类和它们的表共享
    @NotNull
    private String owner;
}

// 子类只需 @Entity，所有具体类映射都从超类继承持久化属性
@Entity @AttributeOverride(name="owner", column=@Column(name="CC_OWNER", nullable=false))
public class CreditCard extends BillingDetails { … }

@Entity
public class BankAccount extends BillingDetails { … }
repository 侧的变化

去掉 @NoRepositoryBean。这个改动加上 BillingDetails 现在标了 @Entity，就让 BillingDetailsRepository 能真正与数据库交互了。

最重要的收益

能处理多态关联。比如 User → BillingDetails 的关联映射现在成为可能 —— Hibernate 可以用 UNION 查询模拟出一张单表作为关联映射的目标。

但要记住：SQL schema 仍然对继承一无所知，表结构和图 7.1 完全一样，表之间没有任何关系，只是碰巧有（很多）相似的列。如果 BillingDetails 是具体类，还需要额外一张表来放它的实例。

7.3每个类层次一张表

源码目录 mapping-inheritance-singletable

把整个类层次映射到一张表，这张表包含层次中所有类的所有属性的列。额外的类型判别列（或判别公式）的值标明某一行代表的是哪个具体子类。

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "BD_TYPE")          // 不写则默认列名 DTYPE，值为字符串
public abstract class BillingDetails {
    @Id @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;

    @NotNull
    @Column(nullable = false)                     // 超类的共享属性可以是 NOT NULL
    private String owner;
}

@Entity
@DiscriminatorValue("CC")                         // 每个具体类都该显式给判别值
public class CreditCard extends BillingDetails {
    @NotNull private String cardNumber;      // schema 里不能有 NOT NULL 约束！
    @NotNull private String expMonth;
    @NotNull private String expYear;
}
优点：性能与简洁的赢家
  • 表示多态性能最好 —— 多态查询和非多态查询都很快
  • 甚至可以手写查询；临时报表不需要复杂的 join 或 union
  • schema 演进直截了当
两个严重问题

① 数据完整性：子类声明的属性对应的列必须可空。如果各子类都定义了若干非空属性，丢失 NOT NULL 约束从数据正确性角度可能很严重 —— 信用卡的到期日是必填的，但 schema 无法强制这条规则，一个简单的编程错误就能写进无效数据。

② 规范化：在非键列之间制造了函数依赖，违反第三范式。为性能而反规范化往往具有误导性 —— 它牺牲了长期的稳定性、可维护性和数据完整性，去换取那些本来也可以靠优化 SQL 执行计划得到的即时收益（换句话说：去问 DBA）。

Hibernate 的两个实现怪癖

① 生成数据库 schema 时 Hibernate 忽略 Bean Validation 的 @NotNull，所以超类共享属性要用 @Column(nullable = false) 来声明非空。

② 子类属性的 @NotNull 在 DDL 生成时被忽略，但运行期插入行之前仍会被遵守。这能帮你避免编程错误（不会不小心存下没有到期日的信用卡数据）。当然，别的行为不那么规矩的应用仍然可以往这个库里写错误数据。

③ 不显式指定判别值时：用 Hibernate XML 文件默认取全限定类名；用注解或 JPA XML 默认取简单实体名。JPA 没有为非字符串判别类型规定默认值，各提供者可能不同 —— 所以总是显式给具体类指定判别值。

多态查询：一条简单 SELECT
select ID, OWNER, EXPMONTH, EXPYEAR, CARDNUMBER,
       ACCOUNT, BANKNAME, SWIFT, BD_TYPE
from BILLINGDETAILS
子类查询：加一个判别列限制
select ID, OWNER, EXPMONTH, EXPYEAR, CARDNUMBER
from BILLINGDETAILS
where BD_TYPE='CC'

没有判别列怎么办：@DiscriminatorFormula

源码目录 mapping-inheritance-singletableformula　遗留 schema 里往往没有自由加一列。此时可以用表达式为每行算出一个判别值（判别公式不是 JPA 规范的一部分，是 Hibernate 扩展）：

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@org.hibernate.annotations.DiscriminatorFormula(
        "case when CARDNUMBER is not null then 'CC' else 'BA' end"
)
public abstract class BillingDetails { … }

依靠 SQL 的 CASE/WHEN 表达式判断某一行代表信用卡还是银行账户；结果是字面量 CC 或 BA，与子类映射上声明的判别值对应。

7.4每子类一张表 + JOIN

源码目录 mapping-inheritance-joined

把继承关系表示成 SQL 外键关联：每个声明了持久化属性的类或子类（包括抽象类甚至接口）都有自己的表。与第一种策略不同，这里具体 @Entity 的表只含子类自己声明的非继承属性的列，外加一个既是主键又是超类表外键的列。

@Entity
@Inheritance(strategy = InheritanceType.JOINED)      // 不需要判别列
public abstract class BillingDetails {
    @Id @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;
    @NotNull private String owner;
}

@Entity
public class BankAccount extends BillingDetails {     // 无标识符属性：自动继承 ID 属性和列
    @NotNull private String account;
    @NotNull private String bankname;
    @NotNull private String swift;
}

@Entity
@PrimaryKeyJoinColumn(name = "CREDITCARD_ID")          // 想显式指定连接列名就写它
public class CreditCard extends BillingDetails { … }

子类表的主键列若与超类主键列同名（或应当同名），就不必指定连接列。BANKACCOUNT 与 CREDITCARD 的主键列同时也带有指向 BILLINGDETAILS 主键的外键约束。

多态查询 → 外连接 + CASE…WHEN
select
    BD.ID, BD.OWNER,
    CC.EXPMONTH, CC.EXPYEAR, CC.CARDNUMBER,
    BA.ACCOUNT, BA.BANKNAME, BA.SWIFT,
    case
        when CC.CREDITCARD_ID is not null then 1
        when BA.ID is not null then 2
        when BD.ID is not null then 0
    end
from BILLINGDETAILS BD
    left outer join CREDITCARD  CC on BD.ID=CC.CREDITCARD_ID
    left outer join BANKACCOUNT BA on BD.ID=BA.ID

CASE…WHEN 检测子类表中行的存在与否，据此判断 BILLINGDETAILS 某一行的具体子类。

窄子类查询 → 内连接
select CREDITCARD_ID, OWNER,
       EXPMONTH, EXPYEAR, CARDNUMBER
from CREDITCARD
    inner join BILLINGDETAILS on CREDITCARD_ID=ID
优点

规范化了 SQL schema。schema 演进和完整性约束定义都很直接。指向某个子类表的外键可以表示到该具体子类的多态关联。

缺点

手写实现更难，连临时报表都更复杂——如果你打算把 Spring Data JPA/Hibernate 代码与手写 SQL 混用，这是个重要考量（常见且可移植的做法是用 JPQL 并给方法加 JPQL 查询注解）。而且看似简单，作者的经验是复杂类层次下性能可能无法接受：查询总是需要跨多表的 join 或多次顺序读取。

JOINED 需要判别列吗？

Hibernate 不需要特殊的判别列来实现 JOINED，JPA 规范也没有这个要求 —— CASE…WHEN 是区分每行实体类型的聪明办法。但你可能看到别处的 JPA 示例同时用 JOINED 和 @DiscriminatorColumn：显然有些 JPA 提供者不用 CASE…WHEN，即使 JOINED 也只靠判别值。Hibernate 不需要判别列，但如果你声明了 @DiscriminatorColumn，它就会用（老版本 Hibernate 会忽略）。想忽略它，开启配置项 hibernate.discriminator.ignore_explicit_for_joined。

7.5混合继承策略

源码目录 mapping-inheritance-mixed

整个层次只能用 TABLE_PER_CLASS、SINGLE_TABLE 或 JOINED 之一，不能混用……除非用点技巧：可以为某个特定子类切换映射策略。

…/ch07/model/CreditCard.java
@Entity
@DiscriminatorValue("CC")
@SecondaryTable(
        name = "CREDITCARD",
        pkJoinColumns = @PrimaryKeyJoinColumn(name = "CREDITCARD_ID")
)
public class CreditCard extends BillingDetails {
    @NotNull
    @Column(table = "CREDITCARD", nullable = false)   // @Column 的 table 参数：指明来自哪张次表
    private String cardNumber;

    @Column(table = "CREDITCARD", nullable = false)
    private String expMonth;

    @Column(table = "CREDITCARD", nullable = false)
    private String expYear;
}
这个映射的价值SINGLE_TABLE 强制子类的所有列可空；拆出去之后就能把 CREDITCARD 表的列声明为 NOT NULL，保证数据完整性。不指定次表的主键连接列时，会用单表继承表的主键名（这里是 ID）。
适用场景如果你想再加一个继承 BillingDetails 的新类（比如 Paypal），这就是可行方案。
注意上限对特别宽的类层次，这个外连接会成为问题 —— 某些数据库（如 Oracle）限制外连接中的表数量。宽层次下，可考虑换成执行「立即第二次 SELECT」的抓取策略而非外连接。

7.6可嵌入类的继承

源码目录 mapping-inheritance-embeddable

可嵌入类是其拥有者实体的组件，因此本章讲的实体继承规则不适用。作为 Hibernate 扩展，可嵌入类可以从超类（或接口）继承一些持久化属性。

@MappedSuperclass
public abstract class Measurement {
    @NotNull private String name;
    @NotNull private String symbol;
}

@Embeddable
@AttributeOverride(name = "name",
        column = @Column(name = "DIMENSIONS_NAME"))
@AttributeOverride(name = "symbol",
        column = @Column(name = "DIMENSIONS_SYMBOL"))
public class Dimensions extends Measurement {
    @NotNull private BigDecimal depth, height, width;
}
@Embeddable
@AttributeOverride(name = "name",
        column = @Column(name = "WEIGHT_NAME"))
@AttributeOverride(name = "symbol",
        column = @Column(name = "WEIGHT_SYMBOL"))
public class Weight extends Measurement {
    @NotNull @Column(name = "WEIGHT")
    private BigDecimal value;
}

@Entity
public class Item {
    private Dimensions dimensions;   // 普通的嵌入属性
    private Weight weight;
}
另一条支持多态的路

对照 §6.3.2「转换组件的属性」那一节的可嵌入类继承方案（Zipcode / GermanZipcode / SwissZipcode）：它支持多态，但需要你自己写类型判别代码。

7.7如何选择策略

两个额外事实

① 不能把继承注解放在接口上——JPA 没有标准化这一点。但 Hibernate 的隐式多态足够聪明能处理这类特例：假设加一个业务接口 ElectronicPaymentOption（没有持久化意涵，但 CreditCard 之类的持久化类会实现它），无论 BillingDetails 层次怎么映射，Hibernate 都能正确回答 select o from ElectronicPaymentOption o。即使有不属于该层次的其他持久化类也实现了这个接口，Hibernate 依然知道该查哪些表、构造哪些实例、如何返回多态结果。

② 所有映射策略都能用于抽象类。即便你查询或加载抽象类，Hibernate 也不会试图去实例化它。

7.8多态关联

7.8.1　多态多对一关联

源码目录 mapping-inheritance-manytoone

…/ch07/model/User.java
@Entity
@Table(name = "USERS")
public class User {
    @ManyToOne
    private BillingDetails defaultBilling;   // 目标是抽象类
}

USERS 表多出连接/外键列 DEFAULTBILLING_ID，可空（用户可能没设默认支付方式）。因为 BillingDetails 是抽象的，运行期这个关联必然指向某个子类实例。

启用多态关联不需要做任何特别的事

只要关联的目标类用 @Entity + @Inheritance 映射，这个关联天然就是多态的。

// 建立到 CreditCard 子类实例的关联
CreditCard creditCard = new CreditCard(
    "John Smith", "123456789", "10", "2030");
User john = new User("John Smith");
john.setDefaultBilling(creditCard);
creditCardRepository.save(creditCard);
userRepository.save(john);

// 第二个工作单元里导航该关联，Hibernate 自动取回 CreditCard 实例
List<User> users = userRepository.findAll();
users.get(0).getDefaultBilling().pay(123);   // ← 调用的是具体子类的 pay()

一对一关联的处理方式完全相同。

7.8.2　多态集合

源码目录 mapping-inheritance-onetomany

…/ch07/model/User.java（反向端）
@Entity
@Table(name = "USERS")
public class User {
    @OneToMany(mappedBy = "user")
    private Set<BillingDetails> billingDetails
            = new HashSet<>();
}
…/ch07/model/BillingDetails.java（拥有端 = 持有外键的一侧）
@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class BillingDetails {
    @ManyToOne
    private User user;
}
唯一的限制

这个关联映射本身毫无特别之处，BillingDetails 层次用 TABLE_PER_CLASS、SINGLE_TABLE 或 JOINED 都行 —— Hibernate 足够聪明，加载集合元素时会用带 JOIN 或 UNION 的正确 SQL。但 BillingDetails 不能是 @MappedSuperclass（§7.1 解释过原因），它必须用 @Entity + @Inheritance 映射。

本章小结

  • 每具体类一表 + 隐式多态（@MappedSuperclass）是映射实体继承层次最简单的策略，但对多态关联支持不佳；不同表的不同列语义完全相同，使 schema 演进更复杂。只推荐用于类层次顶层，那里通常不需要多态且超类未来不太会改。
  • 每具体类一表 + UNION（TABLE_PER_CLASS）是可选特性，JPA 实现未必支持，但它能处理多态关联。
  • 每类层次一表（SINGLE_TABLE）在性能与简洁性上都是赢家：无需复杂 join 或 union 就能做临时报表，schema 演进直接。
  • 单表策略的一大问题是数据完整性（必须把一些列声明为可空）；另一个顾虑是规范化——它在非键列之间制造函数依赖，违反第三范式。
  • 每子类一表 + JOIN（JOINED）的首要优势是规范化 SQL schema，schema 演进与完整性约束定义都很直接；缺点是手写更难，且复杂类层次下性能可能不可接受。
  • 可用 @SecondaryTable 把某个子类拆出单表策略，换回 NOT NULL 约束；@MappedSuperclass 也可用于可嵌入类的继承，但那样的引用不是多态的。
