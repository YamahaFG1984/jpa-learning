Part 1 · 入门 ORM

第 1 章　理解对象/关系持久化

这一章不写一行框架代码，但它是全书的地基：它回答“为什么我们需要 ORM”。如果你能把这 5 个失配问题讲清楚，后面 19 章的所有设计取舍你都能自己推导出来。

§章前导读：一张图看懂本章

Java 是面向对象的：类、继承、多态、引用、集合。关系数据库是基于关系代数的：表、行、列、外键、连接。这两套模型各自都很优秀，但把它们缝在一起时会出现结构性的裂缝——这就是对象/关系范式失配（object/relational paradigm mismatch）。

本章要点

ORM 不是“帮你隐藏 SQL 的魔法”，而是把这 5 类失配以可配置的方式系统性解决掉的中间层。你依然必须懂 SQL —— 事实上，ORM 是“已经用硬办法做过一遍的人”才该用的高级技术。

1.1什么是持久化

对象持久化（object persistence）的定义很朴素：让单个对象的寿命超过创建它的应用进程 —— 能存进数据存储，之后再被重建出来。在 Java 语境里，这几乎总是指“用 SQL 把对象实例映射并存进数据库”。

1.1.1　关系数据库：数据比应用活得久

选择关系型数据库最重要的理由之一叫数据独立性（data independence）：

核心原则

数据通常比应用活得更久。同一份数据可能同时被录入系统、报表系统、对账系统读写；关系模型是这些异构系统之间的最大公约数，因此它常常是企业级业务实体的权威表示。

1.1.2　理解 SQL 的四张面孔

SQL 这门语言在书中被拆成四个用途，后面章节会反复用到这些术语：

缩写全称做什么典型语句
DDLData Definition Language定义/修改/删除表、约束等 schema 构件；schema 演进也靠它CREATE TABLE ALTER DROP
DMLData Manipulation Language对数据做增删改INSERT UPDATE DELETE
DQLData Query Language限制、投影、笛卡儿积；连接、聚合、分组、子查询SELECT … JOIN … GROUP BY
DCLData Control Language授权与回收访问权限GRANT REVOKE

1.1.3　在 Java 里使用 SQL：JDBC 的层次太低

不用 ORM 时，你通过 JDBC 亲手做这些事：绑定查询参数 → 执行查询 → 滚动结果集 → 从 ResultSet 一列列取值 → 塞进对象。这些都是低层数据访问，而我们真正关心的是业务问题。

不要教条

本书并不主张“任何场景都上 ORM”。简单应用没有领域模型反而更好：直接用 ResultSet、调存储过程、写报表 SQL 直出页面，都是完全正当的做法。ORM 的价值出现在业务逻辑不平凡、需要复用和长期维护领域模型的系统里。实践中两种策略往往并存。

CAP 与互联网规模

书中特意提醒：分布式系统无法同时满足一致性（C）、可用性（A）、分区容错（P）。搜索引擎、CDN、IM 这类超大规模系统常常接受弱一致性，此时 ACID 事务型 SQL 数据库、JDBC、Hibernate 只扮演次要角色。关系技术不是万能药，而是唯一被充分验证的通用数据管理技术。

1.2.1　① 粒度问题（granularity）

把 address 从一个 String 拆成独立的 Address 类（街道/城市/邮编…），因为别的类也要复用地址。理想做法是在数据库里也建一个 ADDRESS 自定义类型（UDT）：

为什么不用 UDT？因为 UDT 支持是各家 DBMS 的冷门特性、互不兼容、SQL 标准对它的定义也很弱；而且即便支持，你仍要把类型定义写两遍（Java 一遍、SQL 一遍）。

ORM 的答案 → 第 5.1.1 节 / 第 6 章

Hibernate 用 @Embeddable（可嵌入组件）解决粒度问题：Java 侧保留 Address 类，数据库侧自动摊成多列。这是最容易解决的一类失配。

1.2.2　② 继承问题（inheritance）

现在支持信用卡付款，自然的建模是让 BillingDetails 成为超类，CreditCard 和 BankAccount 是子类。

1.2.3　③ 标识问题（identity）

“两个东西是不是同一个”在两个世界里有三套不同答案：

顺带暴露另一个坑：初版把 USERNAME 当主键，结果用户改名就得同时改 USERS 的行和 BILLINGDETAILS 中所有外键值。所以书里的建议是：

代理键（surrogate key）

找不到好的自然键时，用一个对业务用户毫无意义、也永不展示给用户的主键列（如自增 ID BIGINT），它唯一的职责就是在应用内部标识数据。

Ch01/Ch01.sql　—— 改用代理键之后
CREATE TABLE USERS (
    ID BIGINT NOT NULL PRIMARY KEY,          -- ← 代理键，系统生成
    USERNAME VARCHAR(15) NOT NULL UNIQUE,   -- 自然键降级为唯一约束
    ADDRESS_STREET  VARCHAR(255) NOT NULL,
    ADDRESS_ZIPCODE VARCHAR(5) NOT NULL,
    ADDRESS_CITY    VARCHAR(255) NOT NULL
);
CREATE TABLE BILLINGDETAILS (
    ID BIGINT NOT NULL PRIMARY KEY,
    ACCOUNT  VARCHAR(15) NOT NULL,
    BANKNAME VARCHAR(255) NOT NULL,
    USER_ID  BIGINT NOT NULL,                 -- ← 引用代理键，改名不影响它
    FOREIGN KEY (USER_ID) REFERENCES USERS(ID)
);

新问题随之而来：这个纯为数据模型而生的 ID 列，在 Java 领域模型里该不该出现、怎么出现？答案在 §5.2。

1.2.4　④ 关联问题（associations）

对象引用天生有方向——它就是指针。要双向可导航，你必须在两个类里各定义一次。而外键是键值的副本，方向对关系模型毫无意义（用 JOIN 和投影可以任意组合）。

真正的难点

挑战在于：把一个完全开放、与应用无关的数据模型，映射到一个受限于本应用需要的导航式对象模型上。第 8、9 章会把所有关联映射形态讲透。

1.2.5　⑤ 数据导航问题（data navigation）—— 最难的一个

前四个问题都是结构性的，静态看模型就能发现。第五个是动态的：运行时数据怎么被访问。

记住这条铁律

提升数据访问性能，最重要的一件事是减少对数据库的请求次数，最直接的手段就是减少 SQL 查询数。缓存等手段是第二步。

1.3ORM、JPA、Hibernate 与 Spring Data

把四个名词的关系一次讲清 —— 这是最容易混淆的地方：

名词它是什么一句话记住
ORM一种技术/思想用元数据描述类与表的映射，自动、透明、可逆地在两种表示之间转换数据
JPA规范（接口）规定做什么：怎么写映射元数据、EntityManager 提供哪些 CRUD、查询语言是 JPQL
HibernateJPA 的实现规定怎么做：最流行的持久化提供者，另有丰富的原生扩展
Spring DataSpring 系的伞形项目再往上加一层：连 DAO 实现都不用写，接口声明完就有实现

JPA 规范定义了什么

  • 映射元数据机制——持久化类及其属性如何对应到数据库 schema。JPA 重度依赖领域类上的注解，也支持 XML 文件（第 3 章）。
  • 基本 CRUD 的 API——最核心的是 EntityManager（第 10 章）。
  • 查询语言与 API——JPQL（长得像 SQL，但引用的是类和属性而非表和列），以及可程序化构造、无需拼字符串的 Criteria API。
  • 持久化引擎的行为——如何对事务中的实例做脏检查、关联抓取及其他优化，还有基本缓存策略。

Hibernate 带来的四个收益

Productivity 生产力消除大量重复劳动；无论自顶向下（从领域模型出发）还是自底向上（从既有 schema 出发）都能显著缩短开发时间。
Maintainability 可维护性代码行数变少 ⇒ 更易理解、更易重构；并在领域模型和 SQL schema 之间形成缓冲层，一侧的小改动不会立刻冲击另一侧。
Performance 性能手写持久化理论上可以更快（就像汇编快过 Java），但自动化方案能始终启用大量优化（如应用层可调缓存），让你把精力集中在真正剩下的瓶颈上，而不是过早优化一切。
Vendor independence 厂商无关缓解厂商锁定风险；即便你永不换 DBMS，本地用轻量库开发、测试与生产用另一套系统的场景也很常见。

Spring Data 再叠加的五个收益

共享基础设施Spring Data Commons 提供元数据模型和技术中立的 Repository 接口，供家族内所有项目复用。
干掉 DAO 实现JPA 方案通常用 DAO 模式；Spring Data JPA 让你完全不写 DAO 实现类。
自动生成实现类DAO 接口只要继承 JpaRepository，Spring Data 会以代理类的形式自动生成实现。
默认方法实现基础 CRUD 不用再写 —— 少了样板代码，也就少了引入 bug 的机会。
按方法名生成查询按命名模式声明方法，Spring Data 解析方法名并替你造出查询（第 4 章重点）。
需要时贴近数据库Spring Data JDBC 绕开 JPA 的“魔法”直连数据库，但仍用 Spring 设施消除样板代码（第 15 章）。
本书的立场，请务必记牢

“ORM 让开发者不必接触讨厌的 SQL”——这个观点是错的。恰恰相反：要用好 Hibernate 和 Spring Data，你必须能看懂并解读它发出的 SQL、判断其性能影响；要用好 Spring Data，你必须能预判它生成了什么样板代码和查询。ORM 是给已经用硬办法做过一遍的人准备的高级技术。

本章小结

  • 对象持久化让对象活得比进程久；当存储是 SQL 数据库时，就出现对象/关系失配——对象网无法整体存入一张表，必须拆解成可移植 SQL 类型的列。
  • 五道裂缝：粒度（Java 无限细分 vs SQL 只有两级）、继承（无表继承、外键无法多态）、标识（== / equals() / 主键三套语义）、关联（引用有向、M:N 需链接表）、导航（走对象网 vs 一次 JOIN）。
  • ORM 不是银弹：它的职责是替开发者消化掉约 95% 的对象持久化工作——写复杂多表 JOIN、把 JDBC 结果集的值搬进对象网。
  • 成熟的 ORM 中间件还提供数据库可移植性、缓存等优化，这些用有限时间靠 SQL + JDBC 手写很难做好。在 Java 世界，这意味着 JPA 规范 + 一个实现（当下最流行的是 Hibernate）。
  • Spring Data 叠在 JPA 实现之上，遵循 Spring 框架理念，进一步简化：去掉 DAO 模式、自动生成代码、自动生成查询。
