Part 3 · 事务性数据处理

第 11 章　事务与并发

工作单元是操作的原子分组，事务让我们设定工作单元的边界并把一个工作单元与另一个隔离开。本章从最低层（数据库与系统事务）讲起，一路到 Spring 的声明式事务。

JPA 2 的重要新特性

① 新增悲观锁的锁模式与异常：可以在 Query 上设置乐观/悲观锁模式；可在 find()、refresh()、lock() 时设置锁模式；悲观锁模式的锁超时提示也被标准化。
② 抛出新的 QueryTimeoutException 或 LockTimeoutException 时，事务不必回滚。
③ 持久化上下文现在可以处于非同步（unsynchronized）模式，禁用自动刷新 —— 这允许我们把修改排队直到加入事务，从而把 EntityManager 的使用与事务解耦。

本章所有示例都能在任何 Java SE 环境下运行，不需要特殊运行时容器。运行前先执行 Ch11/Ch11.sql。

11.1事务要义

拍卖结束时 CaveatEmptor 必须做三件事：① 找出该商品的最高出价；② 向卖家收取拍卖费用；③ 通知卖家与中标者。如果外部信用卡系统故障导致无法计费怎么办？业务需求可能规定：要么全部成功，要么全部不成功。这时这些步骤合起来就是一个事务或工作单元——只要有一步失败，整个工作单元就必须失败。

还有第五个：正确性（correctness）

业务规则规定「应用只向卖家收费一次，而不是两次」。这是合理的假设，但我们可能无法用数据库约束表达它。因此：事务的「正确性」是应用的责任，而「一致性」是数据库的责任。

数据库事务必须短开着的事务消耗数据库资源，还可能因数据上的排他锁而阻止并发访问。单个数据库事务通常只包含一批数据库操作。
事务划界（demarcation）必须开启事务、在某个点提交更改；出错（执行操作时或提交时）则回滚以让数据保持一致状态。边界可以程序化设定，也可以声明式设定（Spring 部分主要用声明式）。

11.2控制并发访问

数据库传统上用加锁实现隔离：事务可以对某个数据项加锁，暂时阻止其他事务读/写它。一些现代数据库引擎用多版本并发控制（MVCC）实现隔离，厂商普遍认为它更可扩展。本章按加锁模型分析，但大多数结论对 MVCC 也适用。

11.2.1　理解数据库级并发

怎么选隔离级别

①　几乎所有场景都要排除 READ_UNCOMMITTED

让一个事务的未提交更改被另一个事务使用极其危险：一个事务的回滚或失败会影响其他并发事务 —— 可能把其他事务一起拖垮，甚至让数据库进入不正确的状态（拍卖商品的卖家可能被收费两次 —— 符合数据库完整性规则，但不正确）。最糟的是：某个最终被回滚的事务所做的更改，可能因为被另一个成功事务读取并传播而被「提交」进去！

它可以用于调试：跟踪长插入查询的执行、对聚合函数（SUM(*)、COUNT(*)）做粗略估算。

②　多数应用不需要 SERIALIZABLE

幻读通常不成问题，而这个级别扩展性很差。生产环境中很少有应用使用它，人们转而在特定场景下有选择地施加悲观锁，从而有效地强制某些操作串行执行。

③　本书的建议：READ_COMMITTED + 实体版本控制

持久化上下文缓存（强制存在）与版本控制的组合，已经给了我们「可重复读」的大部分好处：上下文缓存确保某事务加载的实体实例状态与其他事务的修改隔离；同一工作单元里第二次查同一实体会在上下文缓存中解析、不打库 —— 因此读是可重复的，看不到冲突的已提交数据（仍可能出现幻读，但那通常好处理得多）。此外，版本控制把语义切换成「首次提交者获胜（first commit wins）」。

因此，对几乎所有多用户 JPA 应用，在开启实体版本控制的前提下，所有数据库事务用 READ_COMMITTED 都是可接受的。

怎么改隔离级别

Hibernate 保留数据库连接的隔离级别，不去改它。多数产品默认 read committed，但 MySQL 默认 repeatable read。修改途径：① DBMS 私有配置里的全局设置；② 标准 SQL 的 SET SESSION CHARACTERISTICS（设置该数据库会话中开启的所有事务）；③ SET TRANSACTION（设置当前事务）；④ JDBC 的 Connection.setTransactionIsolation()（文档措辞是「尝试改变」）—— 在 Hibernate/JPA 应用中可从原生 Session API 拿到 JDBC Connection。

但更好的做法：与其改整个事务的隔离级别，不如用 JPA API 对相关数据获取额外的锁。这种细粒度加锁在高并发应用中更可扩展。

11.2.2　乐观并发控制

适用场景：并发修改很少发生，且在工作单元的较晚阶段检测冲突是可行的。JPA 提供自动版本检查作为乐观冲突检测手段。

什么改动会让版本递增只要实体变脏就递增：包括实体的所有变脏的值类型属性，无论是单值（String、int）、嵌入的（Address）还是集合。例外是用 mappedBy 变成只读的 @OneToMany / @ManyToMany 关联集合 —— 在这些集合里增删元素不会递增拥有者实体的版本号。
重要警告这些规则在 JPA 里都没有标准化 —— 访问同一个共享数据库时，不要指望两个 JPA 提供者实现相同的规则。
排除某个属性不想让某属性的变化触发版本递增：@org.hibernate.annotations.OptimisticLock(excluded = true)。

OptimisticLockType.DIRTY：看似更宽松，实则危险

它只把被修改的属性放进限制条件（上例会缩减为 where ID = 123 and NAME = 'Old Name'）。这意味着两个工作单元可以并发修改同一个 Item，只有当它们修改同一个值类型属性（或外键值）时才检测到冲突。

与共享数据库的版本控制

如果多个应用访问同一数据库、而不是全都使用 Hibernate 的版本控制算法，就会出并发问题。一个简单方案是数据库级触发器 + 存储过程：用 INSTEAD OF 触发器在任何 UPDATE 时执行一个存储过程替代该更新。在过程里检查应用是否递增了该行版本；如果版本没更新、或更新语句里根本没包含版本列，就说明这条语句不是 Hibernate 应用发出的 —— 那就在过程里先递增版本再应用 UPDATE。

手工版本检查：让「读」可重复

问题场景

拍卖系统里每个 Item 属于一个 Category（常规 @ManyToOne）。现在要汇总若干类别下所有商品的价格总和：需要对每个类别查询其全部 item 再累加。问题是：如果在你查询并遍历所有类别与商品的过程中，有人把某个 Item 从一个 Category 移到了另一个 Category 呢？在 read-committed 隔离下，同一个 Item 可能出现两次！

BigDecimal totalPrice = BigDecimal.ZERO;
for (Long categoryId : CATEGORIES) {
    List<Item> items = em
        .createQuery("select i from Item i where i.category.id = :catId", Item.class)
        .setLockMode(LockModeType.OPTIMISTIC)          // 告诉 Hibernate 刷新时要检查每个 Item
        .setParameter("catId", categoryId)
        .getResultList();
    for (Item item : items)
        totalPrice = totalPrice.add(item.getBuyNowPrice());
}
em.getTransaction().commit();   // 刷新时对每个 Item 执行一条 SELECT 检查版本；不一致就抛 OptimisticLockException
为什么持久化上下文缓存救不了这个场景？

「查某类别下所有 item」的查询返回一个 ResultSet。Hibernate 看主键值，先尝试在持久化上下文缓存里解析每个 Item 的其余细节。

但这个缓存在这里帮不上忙：如果并发事务把某个 item 移到了另一个类别，那个 item 可能在不同的 ResultSet 里被返回多次。Hibernate 做上下文查找后会说：「哦，这个 Item 实例我已经加载过了，用内存里现成的吧。」—— 它根本不知道该 item 的类别变了，也不知道它在另一个结果里又出现了一次。

因此这正是持久化上下文的「可重复读」特性隐藏了并发提交数据的情形。我们必须手工检查版本，才能发现「我们以为不会变的数据」其实变了。

要点
别被术语迷惑JPA 规范没有规定每个 LockModeType 具体怎么实现。对 OPTIMISTIC，Hibernate 执行的是版本检查，根本不涉及真正的锁
前提必须先在 Item 上启用版本控制，否则无法在 Hibernate 中使用乐观锁模式
性能代价Hibernate 不会批量或以其他方式优化手工版本检查的 SELECT —— 汇总 100 个 item 就会在刷新时多出 100 条查询。这种情况下悲观方案可能更好
适用接口Query、TypedQuery、NamedQuery 都支持 setLockMode()

强制版本递增：OPTIMISTIC_FORCE_INCREMENT

问题场景：两个用户同时给同一商品出价

下新出价时应用要做两件事：① 从数据库取该 Item 当前最高的 Bid；② 比较新 Bid 与最高 Bid，更高则存库。这两步之间存在竞态条件：如果在读到最高出价和放入新出价之间，另一条出价进来了，你根本看不到它。

这个冲突是「不可见的」，即使给 Item 启用版本控制也无济于事 —— 因为整个过程中 Item 从未被修改。

Item item = em.find(Item.class, ITEM_ID,
        LockModeType.OPTIMISTIC_FORCE_INCREMENT);   // 加载后即便从未修改也递增其版本
Bid highestBid = queryHighestBid(em, item);
// …另一个事务改动了记录…
Bid newBid = new Bid(new BigDecimal("45.45"), item, highestBid);
em.persist(newBid);          // 只往 BID 表插入新行，不影响 Item 的任何值

assertThrows(RollbackException.class, () -> em.getTransaction().commit());
// 刷新时：为新 Bid 执行 INSERT，并强制对 Item 做一次带版本检查的 UPDATE
// → 若期间有人并发修改了 Item 或并发下了出价，就抛异常
一个重要的替代方案

如果不用 Bid#item 的 @ManyToOne 实体关联，而是用 Item#bids 的 @ElementCollection，那么往集合里加一个 Bid 就会递增 Item 的版本，不需要强制递增。（可回顾 §8.3 关于父/子歧义以及聚合与组合在 ORM 中如何工作的讨论。）手工递增版本在「插入或修改数据、并希望某个聚合根实例的版本被递增」的许多场景中都有用。

11.2.3　显式悲观锁

for (Long categoryId : CATEGORIES) {
    List<Item> items = em
        .createQuery("select i from Item i where i.category.id = :catId", Item.class)
        .setLockMode(LockModeType.PESSIMISTIC_READ)
        .setHint("javax.persistence.lock.timeout", 5000)   // 拿不到锁就等 5 秒，仍拿不到则抛异常
        .setParameter("catId", categoryId)
        .getResultList();
    // 查询成功返回 = 我们已持有排他锁，本事务提交前其他事务无法排他访问或修改这些数据
    …
}
em.getTransaction().commit();     // 事务完成、提交后锁被释放
LockModeType语义与 Hibernate 的实现
OPTIMISTIC
（JPA 1.0 的 READ 等价，已不建议用）		刷新时做版本检查，无真实锁
OPTIMISTIC_FORCE_INCREMENT
（JPA 1.0 的 WRITE 等价）		加载后强制递增版本，即便从未修改
PESSIMISTIC_READ规范定义它保证可重复读。Hibernate 在加载数据的 SQL 后追加 FOR UPDATE 子句，在数据库层对行加锁。
H2：SELECT … FOR UPDATE（H2 只支持一种排他锁，所有悲观模式生成相同 SQL）
PostgreSQL：支持共享读锁，追加 FOR SHARE
MySQL：翻译成 LOCK IN SHARE MODE
PESSIMISTIC_WRITE在可重复读之上，还要求 JPA 提供者串行化数据访问，且不能出现幻读。
PostgreSQL/MySQL：FOR UPDATE 排他写锁
PESSIMISTIC_FORCE_INCREMENT要求实体已启用版本控制。Hibernate 执行 FOR UPDATE NOWAIT（或方言支持的等价物），查询一返回立即递增版本并对每个返回的实体实例做 UPDATE —— 向任何并发事务表明「我们更新过这些行」，即便我们至今未修改任何数据。除了聚合加锁外很少用到
悲观 vs 乐观：失败时机的根本差别

悲观：只要加锁查询成功，就知道可以安全地读写数据。

乐观：我们抱最好的希望，可能到提交时才被打个措手不及。

JPA 中悲观锁的持续时间是单个数据库事务 —— 无法用排他锁把并发访问阻塞得比一个数据库事务更久。

// 也可以给 find() 设超时提示
Map<String,Object> hints = new HashMap<>();
hints.put("javax.persistence.lock.timeout", 5000);
Category category = em.find(Category.class, CATEGORY_ID,
        LockModeType.PESSIMISTIC_WRITE, hints);
// 方言支持时执行 SELECT … FOR UPDATE WAIT 5000
两类异常的差别

拿不到锁时 Hibernate 抛 LockTimeoutException 或 PessimisticLockException：

• 抛 PessimisticLockException → 事务必须回滚，工作单元结束
• 抛超时异常 → 对事务不是致命的

抛哪个取决于 SQL 方言。例如 H2 不支持逐语句的锁超时，所以总是得到 PessimisticLockException。

锁超时提示的可移植性

和其他提示一样，Hibernate 可能忽略它，取决于数据库产品。H2 只支持连接级的全局锁超时（默认 1 秒）；PostgreSQL、Oracle 等方言下超时设为 0 会给 SQL 追加 NOWAIT。

悲观锁到底锁住了什么？—— 容易误判的边界

Hibernate 只锁定对应实体实例状态的那些行。锁一个 Item 实例 → 锁 ITEM 表里它那行；joined 继承策略下会锁父表和子表中相应的行；实体的次表映射同理。

因为锁的是整行，所以外键在该行中的任何关系也实际上被锁住了：若 SELLER_ID 外键列在 ITEM 表中，Item#seller 关联被锁住 —— 但真正的 Seller 实例并没有被锁！外键在其他表中的集合或其他关联也都没被锁。

扩展锁作用域：JPA 2.0 定义了 PessimisticLockScope.EXTENDED，可用查询提示 javax.persistence.lock.scope 设置。启用后，持久化引擎会把加锁数据的范围扩展到被锁实体的集合与关联连接表中的数据。

离线锁（offline locks）

悲观数据库锁只持有一个事务。其他实现也是可能的：内存中的锁、数据库里的所谓「锁表」等，统称离线锁。

悲观地锁定超过一个数据库事务，通常是性能瓶颈：每次数据访问都要额外向一个全局同步的锁管理器做锁检查。而乐观锁则是长时间会话（conversation）的完美并发控制策略，性能也好。取决于冲突解决策略（检测到冲突后做什么），应用的用户对乐观锁的满意度可能与阻塞式并发访问一样高 —— 他们大概还会庆幸应用没有因为别人正在看同一份数据而把自己锁在某些界面之外。

11.2.4　避免死锁

hibernate.order_updates 的效果

无论应用以什么顺序加载和修改数据，Hibernate 总是先更新主键为 1 的行，再更新第 2 行。刷新时检测到的被修改实体实例与集合元素，其 UPDATE 都按主键值升序排列。这能显著降低死锁概率。（再次提醒：务必彻底理解你的 DBMS 产品的事务与加锁行为。Hibernate 的大部分事务保证继承自 DBMS；你的 MVCC 数据库产品可能避免了读锁，但写者隔离多半仍依赖排他锁，因此仍可能出现死锁。）

EntityManager#lock()

它接受一个已加载的持久实体实例和一个锁模式，执行与 find()/Query 相同的加锁，但不加载实例。此外，对已启用版本的实体做悲观加锁时，lock() 会立即在数据库上做一次版本检查，可能抛 OptimisticLockException；若数据库表示已不存在，抛 EntityNotFoundException。EntityManager#refresh() 也接受锁模式，语义相同。

11.3非事务数据访问

JDBC Connection 默认处于自动提交（auto-commit）模式。想象你用 SQL 控制台连上数据库随手跑几个查询、甚至更新删除 —— 这种交互式访问是临时的，多数时候你并没有一个「构成工作单元」的语句序列计划。自动提交模式非常适合这种数据访问（你总不想为每条 SQL 都敲 begin transaction / end transaction）。

许多开发者出于错误的理由依赖自动提交
  • 不会提升性能：许多小的、每语句一个的数据库事务（这正是自动提交的含义）并不会让应用更快。
  • 不会提升可扩展性：你可能以为长事务比每条 SQL 一个小事务持有数据库锁的时间更久，但这是次要顾虑 —— 因为 Hibernate 在事务内尽可能晚地写库（提交时刷新），数据库本来就只短暂持有写锁。
  • 并发修改时隔离保证更弱：自动提交模式下基于读锁的可重复读是不可能的（当然，持久化上下文缓存在这里有帮助）。
  • 与 MVCC 冲突：如果 DBMS 有 MVCC（Oracle、PostgreSQL），你多半想用它的快照隔离来避免不可重复读和幻读 —— 每个事务拿到自己的数据快照。自动提交模式下快照隔离毫无意义，因为根本没有事务作用域。
  • 代码更难理解：任何读你代码的人都要特别留意持久化上下文是否加入了事务、是否处于非同步模式。如果你总是把操作组织在系统事务里（哪怕只是读数据），所有人都能遵循这条简单规则，难以定位的并发问题也会更少。

那非同步上下文的真正好处是什么？—— 把修改排队

// ① 排队 INSERT
EntityManager em = emf.createEntityManager();       // 无事务
Item newItem = new Item("New Item");
em.persist(newItem);            // Hibernate 只取一个新标识符值（通常调数据库序列）并赋给实例
assertNotNull(newItem.getId()); // 实例在上下文中已是持久态，但 SQL INSERT 还没发生
                                //（这只有用「预插入」标识符生成器才可能，见 §5.2.5）
em.getTransaction().begin();
if (!em.isJoinedToTransaction()) em.joinTransaction();   // 准备好保存时，把上下文加入事务
em.getTransaction().commit();   // 同步与刷新照常发生，Hibernate 写出所有排队的操作

// ② 排队 UPDATE（游离实例的 merge）
detachedItem.setName("New Name");
Item mergedItem = em.merge(detachedItem);   // merge 时以自动提交模式执行一条 SELECT
em.getTransaction().begin();  em.joinTransaction();  em.getTransaction().commit();  // UPDATE 被推迟到这里

// ③ 排队 DELETE
Item item = em.find(Item.class, ITEM_ID);
em.remove(item);
em.getTransaction().begin();  em.joinTransaction();  em.getTransaction().commit();
这项能力的意义

非同步持久化上下文让你把持久化操作与事务解耦。能够独立于事务（以及客户端/服务器请求）把数据修改排队，是持久化上下文的一项重要特性。

Hibernate 的 MANUAL 刷新模式 —— 更方便的替代品

Session#setFlushMode() 支持额外的 FlushMode.MANUAL：它禁用持久化上下文的一切自动刷新，即便加入的事务提交时也不刷新；必须显式调 flush() 才同步数据库。

JPA 的设计思路是「事务提交应当总是写出所有未决更改」，因此用非同步模式把读与写分开。如果你不认同这一点、或不想要自动提交的语句，就用 Session API 启用手工刷新 —— 这样你可以为所有工作单元保留常规的事务边界，享有可重复读甚至 MVCC 数据库的快照隔离，同时仍在持久化上下文里排队更改，并在事务提交前手工 flush()。

11.4用 Spring 与 Spring Data 管理事务

Spring 的事务模型适用于不同 API（Hibernate、JPA、Spring Data JPA）。管理方式可以是程序化的，也可以是声明式的（注解，本节主要用这种）。核心抽象是 org.springframework.transaction.PlatformTransactionManager：

public interface PlatformTransactionManager extends TransactionManager {
    TransactionStatus getTransaction(@Nullable TransactionDefinition definition)
                                     throws TransactionException;
    void commit(TransactionStatus status) throws TransactionException;
    void rollback(TransactionStatus status) throws TransactionException;
}
// 通常不直接使用这个接口：要么用注解声明式标注事务，要么用 TransactionTemplate 做程序化定义

Spring 使用的隔离级别与前面讨论的 ANSI 隔离级别完全相同。

11.4.1　事务传播（transaction propagation）

传播行为调用方有事务 T1 时调用方无事务时
REQUIRED
默认		在 T1 中继续执行创建新事务
SUPPORTS在 T1 中继续执行不创建事务，直接执行
MANDATORY在 T1 中继续执行抛 TransactionRequiredException
REQUIRES_NEW挂起 T1，开启新事务 T2照样创建新事务
NOT_SUPPORTED挂起 T1，以非事务方式继续直接继续执行
NEVER抛 IllegalTransactionStateException直接继续执行
NESTED创建 T1 的子事务 T2 并建立一个保存点；子事务失败则回滚到该保存点创建新事务

11.4.2　事务回滚

Spring 的默认回滚规则：遇到 RuntimeException 就回滚事务。可以用 @Transactional 的四个属性覆盖：

属性类型行为
rollbackFor继承 Throwable 的 Class 数组定义必须导致回滚的异常类
rollbackForClassName继承 Throwable 的类名数组定义必须导致回滚的异常类名
noRollbackFor继承 Throwable 的 Class 数组定义不得导致回滚的异常类
noRollbackForClassName继承 Throwable 的类名数组定义不得导致回滚的异常类名

11.4.3　@Transactional 的属性与作用位置

属性类型行为
isolationIsolation 枚举按 ANSI 标准声明隔离级别
propagationPropagation 枚举上表的传播设置
timeoutint（秒）超时后事务自动回滚
readOnlyboolean声明只读还是读写。只读事务允许一些优化，可以更快
作用位置与继承规则

@Transactional 可用于接口、接口方法、类、类方法。

加在接口或类上 → 该类/接口的所有方法都继承它；可以对特定方法单独注解来改变行为。加在接口或接口方法上 → 实现该接口的类（或对应方法）也继承它，同样可被覆盖。

因此：要获得细粒度的行为，建议把 @Transactional 加在类的方法上。

11.4.4　程序化事务定义（TransactionTemplate）

transactionTemplate.setIsolationLevel(TransactionDefinition.ISOLATION_REPEATABLE_READ);
transactionTemplate.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
transactionTemplate.setTimeout(5);
transactionTemplate.setReadOnly(false);

// TransactionCallback 是函数式接口（带 @FunctionalInterface），可用 lambda
transactionTemplate.execute(status -> {
    // 要在事务中执行的操作
});

在 Spring 应用中，声明式事务管理通常是首选：代码更少，行为由注解提供的元信息决定。

11.4.5　完整示例：用传播行为实现「无论成败都记日志」

源码目录 transactions5-springdata

Spring Data 的「片段接口（fragment interface）」机制

先声明 ItemRepositoryCustom / LogRepositoryCustom 这类片段接口，用途是给 repository 扩展自定义功能；再让 ItemRepository 同时继承 JpaRepository 和这个片段接口。

类名以 Impl 结尾是关键约定（它本身与 Spring Data 无关，只实现片段接口）。注入 ItemRepository bean 时，Spring Data 要创建代理类，会发现它实现了 ItemRepositoryCustom，于是去查找名为 ItemRepositoryImpl 的类作为自定义实现 —— 结果就是注入的 bean 的这些方法拥有 ItemRepositoryImpl 中的行为。

ItemRepositoryImpl.java（节选）
@Transactional(propagation = Propagation.MANDATORY)
public void checkNameDuplicate(String name) {
    if (…已存在同名 item…)
        throw new DuplicateItemNameException(
            "Item with name " + name + " already exists");
}

@Transactional                       // 默认 REQUIRED
public void addItem(String name, LocalDate creationDate) {
    logRepository.log("adding item with name " + name);
    checkNameDuplicate(name);
    itemRepository.save(new Item(name, creationDate));
}

@Transactional(noRollbackFor = DuplicateItemNameException.class)
public void addItemNoRollback(String name, LocalDate d) { … }

@Transactional
public void addLogs()  { logRepository.addSeparateLogsNotSupported(); }
@Transactional
public void showLogs() { logRepository.showLogs(); }
LogRepositoryImpl.java（节选）
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void log(String message) {     // ← 日志在独立事务中执行
    logRepository.save(new Log(message));
}

@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void addSeparateLogsNotSupported() {
    logRepository.save(new Log("check from not supported 1"));
    if (true) throw new RuntimeException();
    logRepository.save(new Log("check from not supported 2"));
}

@Transactional(propagation = Propagation.SUPPORTS)
public void addSeparateLogsSupports() { … 同上结构 … }

@Transactional(propagation = Propagation.NEVER)
public void showLogs() {
    logRepository.findAll().forEach(System.out::println);
}
测试验证的行为
notSupported()addLogs() 开启了事务，但它调用的 addSeparateLogsNotSupported() 会挂起该事务，然后显式抛异常。抛异常之前 logRepository 已成功保存了一条消息 → 断言仓库里有 1 条且内容是 "check from not supported 1"
supports()直接调 addSeparateLogsSupports()（无事务），显式抛异常前也成功保存了 1 条消息
mandatory()无事务时调 checkNameDuplicate() → 抛 IllegalTransactionStateException，消息为 "No existing transaction found for transaction marked with propagation 'mandatory'"
never()加完 Item 后直接调 logRepository.showLogs() 是安全的（无事务）；但通过事务性的 itemRepository.showLogs() 去调它就会抛 IllegalTransactionStateException："Existing transaction found for transaction marked with propagation 'never'"
requiresNew()
重点		加了 3 个 Item 后再加一个重名的 → 抛 DuplicateItemNameException，外层事务回滚。但那条日志消息仍然被持久化了，因为它是在独立事务中添加的。结果：4 条 Log（每次插入尝试一条，无论成败），但只有 3 个 Item
noRollback()用 addItemNoRollback()（noRollbackFor = DuplicateItemNameException.class）时，因为事务没有回滚，异常之后日志消息同样被保留。结果同样是 4 条 Log、3 个 Item

本章小结

  • Hibernate 依赖数据库的并发控制机制，但借助自动版本控制与持久化上下文缓存，在事务中提供了更好的隔离保证。
  • ACID：一致性是数据库的职责，正确性是应用的职责。四类隔离问题：丢失更新、脏读、不可重复读、幻读。本书建议：READ_COMMITTED + 实体版本控制。
  • 乐观并发控制（@Version）把「最后提交者获胜」变成「首次提交者获胜」；OPTIMISTIC 做手工版本检查、OPTIMISTIC_FORCE_INCREMENT 强制递增以检测「不可见的冲突」。
  • 显式悲观锁（PESSIMISTIC_READ/WRITE）在数据库层加锁，只持有一个数据库事务；只锁实体自身的行，关联实体并未被锁。注意 LockTimeoutException 与 PessimisticLockException 的致命性差异。
  • 死锁可用 serializable 模式、提前取排他锁，或务实的 hibernate.order_updates=true 缓解。
  • 可以在事务之外用自动提交模式与非同步持久化上下文工作 —— 它的真正价值是把修改排队、与事务解耦；Hibernate 的 FlushMode.MANUAL 是更方便的替代品。
  • 用 Spring 与 Spring Data 管理事务：7 种传播行为、回滚规则、@Transactional 的四个属性，以及 TransactionTemplate 的程序化方式。REQUIRES_NEW 的经典用途就是「无论主事务成败都要留下日志」。
