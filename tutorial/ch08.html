第 8 章　映射集合与实体关联

很多人用 Hibernate 做的第一件事就是映射父/子关系 —— 这通常也是他们第一次遇到集合、第一次不得不思考实体与值类型的区别，或者第一次迷失在 ORM 的复杂度里。管理类之间的关联与表之间的关系正是 ORM 的核心，实现 ORM 方案的大多数难题都与集合和实体关联管理有关。

JPA 2 的重要新特性

① 新增对基本类型和可嵌入类型的集合与 Map 的支持。
② 新增对持久化 List 的支持 —— 每个元素的索引存在一个额外的数据库列里。
③ 一对多关联新增了 orphan removal（孤儿移除）选项。

8.1.1　数据库 schema：先看表，再看类

给拍卖商品挂图片。假设图片文件存在文件系统上，数据库里只存文件名；从数据库删除图片时，另有一个独立进程负责删磁盘上的文件。

8.1.2　该不该映射集合属性？先算清收益与代价

请牢记：持久化集合永远是可选的

就算不映射任何集合，也能把 IMAGE 表当作一个 @Entity 类映射（用 @ManyToOne 映射外键列 + 复合主键映射），需要某个商品的图片时写查询即可：select img from Image img where img.item = :itemParameter。

映射 Item#images 能得到什么

按需加载调 someItem.getImages() 时自动执行 SELECT * from IMAGE where ITEM_ID = ?。只要领域模型实例处于受管状态，就能边导航边按需读库，不用手写查询。
级联持久化不必对每个 Image 调 persist() / save() —— 往集合里 add()，保存 Item 时它就自动持久化了。
依赖生命周期Item 被删时，Hibernate 用额外的 SQL DELETE 删掉所有附属 Image，你不用操心孤儿清理（假设外键没有 ON DELETE CASCADE）。

代价与边界

代价是额外的映射复杂度。很多 JPA 新手在集合映射上挣扎，而「你为什么要这么做？」的答案常常是——「我以为这个集合是必须的。」

局限：一旦开始遍历集合，这个集合查询永远是「该 item 的全部图片」，绝不会是「只要满足条件 XYZ 的图片」。

本例为什么值得映射：图片生命周期依赖 item；显示 item 时通常也要显示全部图片，someItem.getImages() 在 UI 代码里很方便 —— 这更像是信息的急加载，不用再调持久化服务，图片就在那儿。

8.1.3　选择集合接口

// Java 领域模型里集合属性的惯用写法
<<Interface>> images = new <<Implementation>>();   // 用接口声明类型，挑一个匹配的实现，立刻初始化
// 不推荐在构造器或 setter 里「延迟」初始化集合

Set<Image> images = new HashSet<Image>();
属性接口 / 实现语义支持度
Set / HashSet不保序、不允许重复所有 JPA 提供者
SortedSet / TreeSet稳定的元素顺序：加载后在内存中排序Hibernate 扩展 其他提供者可能忽略 sorted
List / ArrayList用额外的索引列在数据库里保存每个元素的位置所有 JPA 提供者
Collection / ArrayListbag 语义：允许重复，但不保序所有 JPA 提供者
Map / HashMap键值对都能存进数据库所有 JPA 提供者
SortedMap / TreeMap稳定顺序：加载后在内存中排序Hibernate 扩展
数组Hibernate 支持持久化数组，但 JPA 不支持很少用 Hibernate 无法包装数组属性，按需懒加载等集合红利都没有
Hibernate 为什么要「包装」你的集合

它会包装你在字段声明处已经初始化的集合，有时甚至替换掉它（如果类型不对）。这样做是为了实现集合元素的懒加载和脏检查等能力。想映射 Hibernate 不直接支持的集合？扩展点是 org.hibernate.collection.spi.PersistentCollection，通常继承已有的 PersistentSet/PersistentBag/PersistentList。自定义持久化集合不好写，不是老手不建议做。

不带泛型的原始集合

如果不用泛型指定元素类型（或 Map 的键/值类型），必须告诉 Hibernate：@ElementCollection(targetClass = String.class)，Map 的键类型用 @MapKeyClass。本书所有例子都用泛型集合，你也应该这样。

题外话：文件系统不是事务性的

如果只在 SQL 库里存文件名，二进制数据得放别处。存数据库 BLOB 列是一种选择；若决定存成普通文件，要意识到 java.io.File 和 java.nio.file.Files 不是事务性的 —— 文件系统操作不会加入 JTA 系统事务：可能事务成功提交、Hibernate 把文件名写进了库，而文件的存储或删除却失败了。你无法把这些操作作为一个原子单元回滚，也得不到正确的隔离性。可以用 Bitronix 这类独立事务管理器把文件操作也纳入同一个事务。

§8.1.4–8.1.7　四种映射的主键差异（本节的核心）

映射 List 之前请三思

第一反应总是想按用户录入顺序保存，因为之后往往也要按同样顺序展示。但如果有别的排序依据（比如录入时间戳），应该在查询时排序，而不是把展示顺序存下来。如果需要的展示顺序变了怎么办？数据的展示顺序通常不是数据不可分割的一部分，而是一个正交的关注点。

Map 的键类型

例子用 String 作键，但 Hibernate 支持任意基本类型（BigDecimal、Integer 等）。键是 Java 枚举时用 @MapKeyEnumerated；键是时间类型（如 java.util.Date）时用 @MapKeyTemporal。

一个值得思考的问题

只看 bag 那张 schema，你能说出 Java 侧是怎么映射的吗？ITEM 和 IMAGE 表长得一模一样：各有一个代理主键列和若干规范化的列，每张表都可以映射成 @Entity 类。但我们也可以选择用 JPA 的集合特性把 IMAGE 映射成集合，甚至带上组合生命周期。这实际上是一个设计决定：对这张表来说，一些预定义的查询与操作规则就够了，不需要更通用的 @Entity 映射。做这个决定时，务必清楚理由和后果。

8.1.8　排序（sorted）与有序（ordered）集合

有序集合的可靠性问题

有序集合的元素只在刚加载时处于期望的顺序。一旦添加或删除元素，迭代顺序就可能不再是「按文件名」了 —— 它们的行为和普通的 linked set/map/list 一样。作者的结论：这个技术方案有其缺陷，算不上可靠的解决办法。另外，bag 无法排序（没有 TreeBag），list 元素的索引已经预定义了它们的顺序。

8.2组件（可嵌入类）的集合

真实系统里往往不止存图片名和文件名，还要 title、width、height。这正是组件集合的完美用例。

8.2.1　组件实例的相等性：一个必须理解的连锁反应

someItem.addImage(new Image("background.jpg", 640, 480));
someItem.addImage(new Image("foreground.jpg", 800, 600));
someItem.addImage(new Image("landscape.jpg", 1024, 768));
someItem.addImage(new Image("landscape.jpg", 1024, 768));   ← 完全一样的值

assertEquals(3, someItem.getImages().size());   // 你期望是 4 吗？

如果不重写，Java 的常规相等性检查依赖标识（Object#equals() 用 a==b），集合里会有四个 Image。对这个用例来说，三才是「正确」答案。

为什么第 6 章映射 Address 时没重写相等性？

说实话我们本该重写。唯一的借口是：除非把可嵌入组件放进 Set、或者用作依赖 equals()/hashCode() 的 Map 的键（即不是 TreeMap，后者靠比较来排序定位），否则常规的标识相等性不会出问题。最好在每个 @Embeddable 类上都重写这两个方法 —— 所有值类型都该「按值」比较。

Hibernate schema 生成器的一个小问题

如果给可嵌入类的属性标 @NotNull 而不是 @Column(nullable=false)，Hibernate 不会为集合表的那一列生成 NOT NULL 约束 —— Bean Validation 校验正常，但数据库 schema 缺了这条完整性规则。当可嵌入类被映射在集合里、且该属性应当是主键的一部分时，请用 @Column(nullable=false)。

@Entity
public class Item {
    @ElementCollection              // 泛型声明已告知目标是 @Embeddable
    @CollectionTable(name = "IMAGE") // 否则默认 ITEM_IMAGES
    @AttributeOverride(
            name = "filename",
            column = @Column(name = "FNAME", nullable = false))
    private Set<Image> images = new HashSet<>();
}
setofembeddablesorderby/Item.java —— JPA 的 @OrderBy
@ElementCollection
@CollectionTable(name = "IMAGE")
@OrderBy("filename DESC, width DESC")   // ← 参数是属性名
private Set<Image> images = new LinkedHashSet<>();

参数是 Image 类的属性加 ASC/DESC（默认升序）。这与接受纯 SQL 的 Hibernate 私有 @OrderBy 不同。

用 Filename 作 Map 键时的限制

不能使用 @MapKeyColumn 和 @AttributeOverrides —— 当 map 的键是 @Embeddable 类时它们不起作用。另外，因为 map 的键构成一个集合，每个 Filename 在给定键集合内必须唯一，所以必须重写 equals()/hashCode()。

8.3映射实体关联

先厘清「父/子」这个词

我们其实已经映射过父/子关系了：父是实体 Item，多个子是值类型（Image 集合）。删除 Item 时它的 Image 集合也随之删除 —— 子完全依赖父，永远和父一起保存、更新、删除，绝不单独存在。

现在要映射的是另一种关系：两个实体类之间的关联。它们的实例没有依赖的生命周期，一个可以独立于另一个被保存、更新、删除。当然实体之间有时也存在依赖，但我们需要比完全依赖的嵌入类型更细粒度的控制。

「父/子」这个术语很含混，人人有自己的定义，从现在起我们不再用它，改用更精确、至少是定义明确的词汇。

8.3.1　最简单的关联：单向多对一

源码目录 mapping-associations

…/ch08/onetomany/bidirectional/Bid.java
@Entity
public class Bid {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "ITEM_ID", nullable = false)
    private Item item;
}
@ManyToOne必需，标记属性是实体关联。fetch 默认 EAGER（加载 Bid 时连带加载 Item）；作者更倾向把懒加载作为默认策略（§12.1.1）。
连接列（join column）多对一关联天然映射到外键列。默认名就是 ITEM_ID：目标实体名 + 下划线 + 其标识符属性名。
这里为何还写 @JoinColumn不是为了改名，而是为了让生成的 SQL schema 里这个外键列是 NOT NULL —— 出价必须指向某个商品，不能独立存在（这已经暗示了某种生命周期依赖）。等价写法：@ManyToOne(optional = false) 或 Bean Validation 的 @NotNull。
这条建议非常重要

这就完了。而且必须意识到：不用其他任何东西，你也能写出一个完整而复杂的应用。

不需要映射这个关系的另一端，可以忽略 Item → Bid 的一对多关联。数据库 schema 里只有一个外键列，我们已经映射过它了。

我们是认真的：当你看到一个外键列和两个实体类时，多半应该只用 @ManyToOne 映射它，别的什么都不要。

调 someBid.getItem() 就能拿到出价对应的商品，JPA 提供者会解引用外键并加载 Item，也会管理外键值。

那怎么拿到某个 item 的全部出价？写查询即可：

// JPQL
select b from Bid b where b.item = :itemParameter

当然，我们之所以用 Hibernate / Spring Data JPA，正是因为大多数情况下不想自己写和执行这条查询。

8.3.2　把它变成双向

映射 Item#bids 的收益

① 调 someItem.getBids() 并开始遍历时，自动执行 SELECT * from BID where ITEM_ID = ?。

② 可以把状态变更从 Item 级联到集合中被引用的所有 Bid，并选择哪些生命周期事件是传递性的。

这个清单不算长。一对多映射的主要好处是导航式数据访问 —— 这是 ORM 的核心承诺之一：只调用自己 Java 领域模型的方法就能访问数据，ORM 引擎负责聪明地加载所需数据。

但请先做三个自问

① 数据库里会有任何表带 BID_ID 外键列吗？如果没有，就把 Bid 映射成 @Embeddable 而非 @Entity —— 用同样的表，但换一种映射、带上固定的传递性状态变更规则。如果有别的表引用某个 BID 行，那就需要一个共享的 Bid 实体，它不能被嵌入到 Item 里。

② 应用里会多频繁地调 someItem.getBids() 并按预定义顺序访问/展示全部出价？如果只想展示子集、或每次需要不同顺序，反正都得手写查询 —— 那么这个一对多映射及其集合就只是维护包袱。

③ 代价是额外的 Java 代码和显著更高的复杂度，作者的经验是：这是问题和 bug 的常见来源，尤其对 ORM 新手。选择映射集合这件事，应该慎之又慎。

CaveatEmptor 的答案是「是」—— 我们会频繁调 getBids() 展示给想参与拍卖的用户。

…/ch08/onetomany/bidirectional/Item.java
@Entity
public class Item {
    @OneToMany(mappedBy = "item", fetch = FetchType.LAZY)
    private Set<Bid> bids = new HashSet<>();
}
mappedBy 的含义参数是「另一侧」属性的名字。Bid 侧负责外键列 ITEM_ID（用 @ManyToOne 映射）；mappedBy 告诉 Hibernate：「用那个属性已经映射好的外键列来加载这个集合」。当一对多是双向的、且你已经映射了外键列时，mappedBy 总是必需的。
fetch 默认值集合映射的 fetch 默认永远是 LAZY，所以以后不用写这个选项。这是个好默认值；反过来的 EAGER 很少需要 —— 我们不希望每次加载 Item 都急切地把所有出价拉出来，它们应该在被访问时按需加载。

8.3.3　级联状态：四个台阶

@ManyToOne 也有 cascade，但很少用

你没法真的说「保存 bid 时也保存 item」—— item 必须事先存在，否则这个 bid 在数据库里就是无效的。想想另一个可能的 @ManyToOne：Item#seller —— User 必须先存在，才能卖东西。

孤儿移除的经典陷阱：共享引用

什么时候可以放心开启孤儿移除

当数据库里没有别的表对 BID 有外键引用、删除 BID 行没有任何后果、且内存中对 bid 的唯一引用就在 Item#bids 里时。这时它是个很方便的选项：展现层从集合里移除一个元素就能删除数据，只需操作领域模型实例，不用调服务。

数据库级 ON DELETE CASCADE 的代价
  • 该选项不影响 Hibernate 的运行期行为，仍会遇到上面那个内存不一致问题。内存中的数据可能不再准确反映数据库状态；如果不小心，甚至可能保存一个自己或别人先前已删除的东西。
  • Bid 实例不走常规生命周期，@PreRemove 之类的回调不会生效。
  • Hibernate 不会自动清理可选的二级全局缓存，其中可能残留陈旧数据。
  • 本质上，这类问题与「另一个应用也在访问同一个数据库」或「有数据库触发器在改数据」是同一类问题。

Hibernate 的一个怪癖：@OnDelete 只影响 Hibernate 的 schema 生成。影响 schema 生成的设置通常放在「另一侧」（映射了外键/连接列的那侧），也就是 Bid 的 @ManyToOne 旁边；但当关联是双向映射时，Hibernate 只在 @OneToMany 一侧识别它。另外这在 MySQL 上不工作，所以书里这个例子改用 H2 演示。

新 schema 的最省心做法

不启用数据库级级联，而是把领域模型里的组合关系映射成 embedded/embeddable，而不是实体关联 —— 这样框架就能执行高效的 SQL DELETE 一次性删掉整个组合。也就是：如果能避免共享引用，就把 Bid 作为 Item 里的 @ElementCollection 映射，而不是带 @ManyToOne/@OneToMany 的独立实体。或者，干脆一个集合都不映射，只用最简单的映射：@Entity 类之间单向的、带 @ManyToOne 的外键列。

本章小结

  • 用简单的集合映射（如 Set<String>）就能用上一整套丰富的接口与实现；集合表的主键构成随集合类型而变：Set = FK+值列，bag = 代理键，List = FK+索引列，Map = FK+键列。
  • 可以用排序集合（内存中用 Comparator），也可以用 Hibernate 的选项让数据库按期望顺序返回元素（@OrderBy）—— 但要清楚有序集合只在刚加载时有序。
  • 可以使用用户自定义可嵌入类型的复杂集合：组件的 set、bag 和 map；组件既能作 Map 的值，也能作 Map 的键。
  • 可嵌入组件自己也能拥有集合。
  • 值类型集合必须重写 equals()/hashCode()「按值」比较，它与集合表的复合主键互相呼应；必要时用 @org.hibernate.annotations.Parent 拿到反向指针来保持对称。
  • 把第一个外键列映射成实体多对一关联（@ManyToOne）是最简单也最重要的一步 —— 只用它就能写出完整的应用；一对多集合是可选的，主要价值是导航式访问与级联，代价是复杂度。
  • 级联有四个台阶：手工 → CascadeType.PERSIST → CascadeType.REMOVE → orphanRemoval → 数据库 ON DELETE CASCADE；越往后越高效，也越容易与共享引用冲突、造成内存与数据库状态不一致。
