第 20 章　测试 Java 持久化应用

所有代码都需要测试。开发时我们写代码、编译、运行；运行时有时会测一下代码工作得如何。但测试持久化应用不止于此——我们的代码要和外部数据库交互，程序的行为可能依赖于它。本章的核心问题只有一个：怎样让每次测试跑完之后，数据库的内容和跑之前一模一样。

本章的三个源码工程

Ch20/1 spring testing（TestContext 框架、@DirtiesContext、@Transactional）、Ch20/2 spring profiles（配置文件切换）、Ch20/3 spring listeners（测试执行监听器）。运行前先执行 Ch20/Ch20.sql。

20.1 测试金字塔

前面的章节我们专注于编写与数据库交互的代码。现在需要确保程序是安全的、没有 bug 的：能引入改动而不制造 bug，能添加新特性而不影响旧特性，能重构代码而不破坏既有功能。

为什么持久化测试属于集成层

因为我们把自己的代码与数据库交互组合在了一起，并且依赖于数据库如何工作。由此产生本章要解决的两个目标：

  • 让测试的行为在重复执行之间保持一致
  • 让数据库的内容在跑测试前后保持相同

20.3 使用 Spring TestContext 框架

Spring TestContext 框架专为提供集成测试支持而设计，因此非常适合测试持久化层。它与你使用的测试框架无关（我们用 JUnit 5）。它的核心类和注解属于 org.springframework.test.context 包。

框架的入口点是 TestContextManager 类，其目标是管理单个 TestContext 并向注册的监听器发送事件。

脏数据库问题：一个会「第二次才失败」的测试

Ch20/1 spring testing/src/test/.../SaveRetrieveUserTest.java
@SpringBootTest
class SaveRetrieveUserTest {

    @Autowired
    private UserRepository userRepository;

    @RepeatedTest(2)                       // 在一次类执行中跑两遍
    void saveRetrieve() {
        userRepository.save(new User("User1"));
        List<User> users = userRepository.findAll();

        assertAll(
            () -> assertEquals(1, users.size()),
            () -> assertEquals("User1", users.get(0).getName()));
    }
}
结果：第一次成功，第二次失败

从数据库拿到了两个 User 而不是一个。因为第一次测试插入的那一行没有被删掉，第二次测试在表里发现了它，又加了一行。

20.4 方案一：@DirtiesContext 注解

@DirtiesContext 的意思是「承认这个测试方法或测试类改动了 Spring 上下文」，于是 Spring TestContext 框架会从头重建上下文并提供给下一个测试。这个注解可以加在方法或类上，其效果可以作用于每个测试方法执行的前/后，或整个测试类执行的前/后。

Ch20/1 spring testing/src/test/.../SaveRetrieveUserTest.java
@SpringBootTest
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
class SaveRetrieveUserTest {

    @Autowired
    private UserRepository userRepository;

    @RepeatedTest(2)
    void saveRetrieve() { /* . . . 同上 */ }
}

现在两次都通过了。因为每个测试之前都会执行「建表 + 插入」全套 SQL——连 Spring Boot 的横幅都会打印两次，因为应用被启动了两次。

20.5 方案二：@Transactional 执行

第 11 章详细讲过事务：事务控制要么全部成功、要么全部失败的原子操作组。现在要应用的思路是：让每个测试在事务中运行，并在执行结束时回滚事务。

默认就会回滚

执行测试时，由于 TransactionalTestExecutionListener 的存在，事务会自动回滚（20.8 节详谈监听器）。这个默认行为可以用 @Commit 和 @Rollback 注解修改：想让测试在执行结束时提交，就标注 @Commit 或 @Rollback(false)。

为了跟踪测试执行期间事务何时活跃，我们用 TransactionSynchronizationManager 类——它为一个线程管理资源和事务同步，其 isActualTransactionActive() 方法检查当前是否有 Transaction 对象处于活跃状态。

Ch20/1 spring testing/src/test/.../TransactionalTest.java
@SpringBootTest
@Transactional
class TransactionalTest {

    @BeforeAll
    static void beforeAll() {
        System.out.println("beforeAll, transaction active = " +
               TransactionSynchronizationManager.isActualTransactionActive());
    }

    @BeforeEach  void beforeEach() { /* 同样打印 */ }

    @RepeatedTest(2)
    void storeRetrieve() { /* . . . 打印 end of method */ }

    @AfterEach   void afterEach() { /* 同样打印 */ }

    @AfterAll
    static void afterAll() { /* 同样打印 */ }
}

执行日志

beforeAll,      transaction active = false
beforeEach,     transaction active = true
end of method,  transaction active = true
afterEach,      transaction active = true
beforeEach,     transaction active = true
end of method,  transaction active = true
afterEach,      transaction active = true
afterAll,       transaction active = false

怎么读这份日志

事务在 @BeforeAll 和 @AfterAll 里不活跃，但在 @BeforeEach、@AfterEach 以及测试方法内部是活跃的。

也就是说：事务的边界正好包住「@BeforeEach → 测试方法 → @AfterEach」这一整段。测试结束时事务被回滚，所以 @RepeatedTest 每一次都通过。

陷阱：在独立事务中启动的方法

引入一个带事务方法的 UserService 类：

Ch20/1 spring testing/src/main/.../service/UserService.java
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    @Transactional                       // 默认传播行为是 REQUIRED
    public void saveTransactionally(User user) {
        userRepository.save(user);
    }
}
@RepeatedTest(2)
void storeRetrieve() {
    List<User> users = buildUsersList();
    userRepository.saveAll(users);
    assertEquals(getIterations(), userRepository.findAll().size());

    userService.saveTransactionally(users.get(0));

    System.out.println("end of method, transaction active = " +
           TransactionSynchronizationManager.isActualTransactionActive());
}

性能对比：两种方案该怎么选

为了对比 @DirtiesContext 和 @Transactional 的性能，书中执行了一系列 10 个测试，把记录数从 100 逐步增加到 2000，分别在 MySQL 和 H2（内存数据库）上测量。

结论（对两种数据库都成立）

用 @DirtiesContext 与用 @Transactional 的执行时间差近似恒定。这个差值不取决于记录数，而取决于上下文被重新初始化的次数。

所以：要节制地使用 @DirtiesContext。把带这个注解的测试推到 CI/CD（持续集成/持续交付）环境会严重增加它们的执行时间。

默认用 @Transactional，只在测试确实修改了 Spring 上下文本身时才用 @DirtiesContext。

20.6 @BeforeTransaction 与 @AfterTransaction

顾名思义，这两个注解指明要在事务执行前后运行的方法。我们来验证：这样的方法内部确实没有活跃事务。

assumeFalse 与 assertFalse 的区别

用 JUnit 5 的 Assumptions.assumeFalse 表示「跑这些测试的前提条件是此刻没有活跃事务，否则测试就不跑」。

  • 假设（assumption）不成立 → 测试被中止（aborted）
  • 断言（assertion）不成立 → 测试失败（failed）
Ch20/1 spring testing/src/test/.../TransactionsManagementTest.java
@SpringBootTest
@Transactional
class TransactionsManagementTest {

    @Autowired private UserRepository userRepository;
    @Autowired private LogRepository  logRepository;

    @BeforeTransaction
    void beforeTransaction() {
        Assumptions.assumeFalse(
             TransactionSynchronizationManager.isActualTransactionActive());
    }

    // . . .

    @AfterTransaction
    void afterTransaction() {
        Assumptions.assumeFalse(
             TransactionSynchronizationManager.isActualTransactionActive());
    }
}
这里还有一个必须避开的陷阱

在 @BeforeTransaction 或 @AfterTransaction 方法里持久化数据。因为它们在事务之外执行，数据不会被回滚，会影响数据库的内容。

更糟的是：如果我们持久化的是测试中不检查的数据（比如测试验证的是 User 实体，而我们存的是 Log 实体），那么测试永远都会正确执行，却在身后留下已提交的数据——这是一种沉默的污染，比直接失败更难发现。

@BeforeTransaction
void beforeTransaction() {
    Assumptions.assumeFalse(
         TransactionSynchronizationManager.isActualTransactionActive());
    logRepository.save(new Log("@BeforeTransaction"));   // ← 这行数据永远留下
}

20.7 使用 Spring profiles

Spring Boot 默认创建 main/resources/application.properties 保存应用配置。但经常需要根据用户的 profile 区分不同的属性。Spring Boot 允许把属性分离到默认命名为 main/resources/application-profilename.properties 的文件里，并在 profile 之间切换。

一个真实场景：开发人员有一个 profile，开发期间使用内嵌数据库；生产有另一个 profile，使用真实数据库。程序员希望能快速执行他们的测试，而在生产环境测试会跑在真实环境里。

Ch20/2 spring profiles/src/test/.../SpringProfilesTest.java
@SpringBootTest
@Transactional
@ActiveProfiles("prod")          // 覆盖 application.properties 里设置的 profile
class SpringProfilesTest {

    @Autowired
    private UserRepository userRepository;

    @Test
    void storeUpdateRetrieve() {
        List<User> users = buildUsersList();
        userRepository.saveAll(users);
        assertEquals(getIterations(), userRepository.findAll().size());
    }
}
别忘了驱动依赖

跑 dev 需要 com.h2database:h2（runtime），跑 prod 需要 mysql:mysql-connector-java（runtime）。两个都要放在 pom.xml 里，否则切过去就报找不到驱动。

20.8 使用测试执行监听器

控制测试执行生命周期的一种方式是用 JUnit 5 的注解：@BeforeAll、@AfterAll、@BeforeEach、@AfterEach。但某些情况下这不方便：如果多个测试需要相同的 @BeforeEach 和 @AfterEach 行为，我们就得创建一个包含这些方法的基类，再创建多个子类去继承——这样就把测试挂进了一个类层次结构里（又是熟悉的「继承位被占用」问题，参见 16.5 节的处理器 vs 监听器之争）。

替代方案：使用测试执行监听器，即 TestExecutionListener 接口和 @TestExecutionListeners 注解，把控制测试生命周期的行为分离出来。

Spring 默认提供的两个关键监听器

  • DependencyInjectionTestExecutionListener——为测试实例提供依赖注入
  • TransactionalTestExecutionListener——支持测试的事务化执行与回滚

20.5 节说的「事务默认会自动回滚」，正是第二个监听器的功劳。这对于测试持久化、力求跑完后留下干净数据库来说是至关重要的。

表 20.1　接口的默认方法与执行顺序

beforeTestClass在 JUnit 5 的 @BeforeAll 方法之前执行
prepareTestInstance准备所提供测试上下文的测试实例
beforeTestMethod在 @BeforeEach 方法之前执行
beforeTestExecution在测试方法之前执行
afterTestExecution在测试方法之后执行
afterTestMethod在 @AfterEach 方法之后执行
afterTestClass在 @AfterAll 方法之后执行

它们比 JUnit 5 的生命周期方法粒度更细。

Ch20/3 spring listeners/src/test/.../listeners/DatabaseOperationsListener.java
public class DatabaseOperationsListener implements TestExecutionListener {

    @Override
    public void beforeTestClass(TestContext testContext) {
        System.out.println("beforeTestClass, transaction active = " +
            TransactionSynchronizationManager.isActualTransactionActive());
    }

    @Override
    public void prepareTestInstance(TestContext testContext) { /* 同样打印 */ }

    @Override
    public void beforeTestMethod(TestContext testContext)    { /* 同样打印 */ }

    @Override
    public void beforeTestExecution(TestContext testContext) { /* 同样打印 */ }

    @Override
    public void afterTestExecution(TestContext testContext)  { /* 同样打印 */ }

    @Override
    public void afterTestMethod(TestContext testContext)     { /* 同样打印 */ }

    @Override
    public void afterTestClass(TestContext testContext)      { /* 同样打印 */ }
}
第一次尝试会以 NullPointerException 失败

如果这样写测试：

@SpringBootTest
@Transactional
@TestExecutionListeners(value = {DatabaseOperationsListener.class})
class ListenersTest { /* . . . */ }

会发现 userRepository 引用是 null。控制台显示 TestContextManager 里只注册了一个监听器——我们自己的 DatabaseOperationsListener。之前所需的、为测试实例（以及 userRepository）提供依赖注入的 DependencyInjectionTestExecutionListener 不再被注册了。

原因：一旦引入我们自己的监听器，默认监听器就不再被自动注册。

修复方法是用 MERGE_WITH_DEFAULTS 作为合并模式：

Ch20/3 spring listeners/src/test/.../ListenersTest.java
@SpringBootTest
@Transactional
@TestExecutionListeners(value = {DatabaseOperationsListener.class},
        mergeMode = TestExecutionListeners.MergeMode.MERGE_WITH_DEFAULTS)
class ListenersTest {

    @Autowired
    private UserRepository userRepository;

    @BeforeAll  static void beforeAll()  { System.out.println("@BeforeAll"); }
    @BeforeEach void beforeEach()        { System.out.println("@BeforeEach"); }

    @Test
    void storeUpdateRetrieve() {
        TestContextManager testContextManager = new TestContextManager(getClass());
        System.out.println("testContextManager.getTestExecutionListeners().size() = "
              + testContextManager.getTestExecutionListeners().size());
        List<User> users = buildUsersList();
        userRepository.saveAll(users);
        assertEquals(getIterations(), userRepository.findAll().size());
    }

    @AfterEach  void afterEach()        { System.out.println("@AfterEach"); }
    @AfterAll   static void afterAll() { System.out.println("@AfterAll"); }
}
// 实际控制台输出
beforeTestClass, transaction active = false
@BeforeAll
prepareTestInstance, transaction active = false
beforeTestMethod, transaction active = true
@BeforeEach
beforeTestExecution, transaction active = true
testContextManager.getTestExecutionListeners().size() = 15
afterTestExecution, transaction active = true
@AfterEach
afterTestMethod, transaction active = true
@AfterAll
afterTestClass, transaction active = false

20.9 注解速查表

表 20.2　测试持久化应用最重要的 Spring TestContext 框架注解
注解说明
@DirtiesContext底层 Spring 上下文在测试执行期间被改动了，应该重新初始化。
@BeforeTransaction该 void 方法应在任何带 Spring @Transactional 注解的方法之前执行。
@AfterTransaction该 void 方法应在任何带 Spring @Transactional 注解的方法之后执行。
@Rollback事务型测试的事务在测试完成后回滚。这是默认行为，可以用 @Rollback(false) 或 @Commit 改变。
@Commit事务型测试的事务在测试完成后提交。
@ActiveProfiles指定 Spring 上下文中哪些配置 profile 处于激活状态。
@TestExecutionListeners配置要注册到 TestContextManager 的测试执行监听器。记得配 MERGE_WITH_DEFAULTS。
本书作者的收尾寄语

「Spring TestContext 框架为集成测试提供了强有力的支持，而持久化应用测试正属于集成测试。在这个基础上，你可以继续构建系统测试和验收测试，就像本章开头介绍测试金字塔时展示的那样。」

「有了可预测的、安全的测试——只在你的代码有问题时才失败，而不是因为外部因素（比如脏数据库里不合适的内容）——你作为程序员的生活会好过得多！」

本章小结

  • 测试金字塔由单元、集成、系统和验收四个层次组成。持久化测试归类于集成层——因为它把我们的代码和数据库交互组合在了一起。
  • 可以用 Spring Boot 创建并配置一个持久化应用，并在其中管理实体和仓库。
  • 可以用 Spring TestContext 框架创建持久化测试，并用 @DirtiesContext 或 @Transactional 管理它们。
    关键判断：@Transactional 是默认选择（每个测试跑在事务里、结束时自动回滚）；@DirtiesContext 要节制使用，它的开销取决于上下文被重新初始化的次数，会严重拖慢 CI/CD。
  • 两个必须记住的陷阱：① 用 REQUIRES_NEW 传播行为启动的方法会独立提交，绕过测试的回滚；② 在 @BeforeTransaction / @AfterTransaction 里持久化数据不会被回滚，可能留下沉默的污染。
  • 可以用 Spring profiles 测试访问不同数据库、拥有不同配置的 Java 持久化应用：application-dev.properties（内存 H2、显示 SQL）与 application-prod.properties（真实 MySQL、不显示 SQL），通过 spring.profiles.active 或 @ActiveProfiles 切换。
  • 可以创建自定义测试执行监听器来跟踪测试的生命周期，并与默认监听器配合工作。它把生命周期行为从类继承中解放出来，但一旦自定义就必须加 MERGE_WITH_DEFAULTS，否则依赖注入和事务回滚都会失效。
