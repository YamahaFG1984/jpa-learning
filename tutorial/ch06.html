第 6 章　映射值类型

上一章讲实体，这一章讲值类型——分两类：JDK 自带的基本值类型（String、Date、基本类型及其包装类），和你自己定义的值类型类（CaveatEmptor 里的 Address、MonetaryAmount）。最后深入到类型转换器这个 ORM 最灵活的扩展点。

JPA 2 的重要新特性

JPA 2.2 支持 Java 8 的 Date and Time API。不再需要 @Temporal 这类以前用来注解 java.util.Date 字段的额外映射注解。

6.1映射基本属性

映射持久化类（无论是实体还是可嵌入类型）时，它的所有属性默认都是持久化的。JPA 按下面这套规则决定怎么处理每个属性：

为什么不该依赖序列化存储

数据比应用活得久。当这个应用几年后消失，维护数据库里那些二进制信息的人会发现：序列化版本所映射的那些类已经不存在了。

6.1.1　覆盖基本属性的默认行为

排除属性：@Transient vs transient

Item#initialPrice 该持久化，但Item#totalPriceIncludingTax（只在运行时算出来用一下）不该。

写法效果
Java 关键字 transient同时把字段从 Java 序列化和持久化中排除（JPA 提供者也认它）
@javax.persistence.Transient只把字段从持久化中排除
怎么判断一个属性该不该持久化？问自己五个问题
  1. 这是塑造实例形态的基本属性吗？
  2. 从一开始就需要它，还是能由别的属性算出来？
  3. 过一段时间后重建这个信息还有意义吗，还是那时它已不再重要？
  4. 是敏感信息吗（比如明文密码），是否宁可不持久化以免日后泄露？
  5. 是换个环境就没意义的信息吗（比如在另一个网络里毫无意义的本地 IP）？

三种声明「必填」的方式

// ① @Basic —— 只有 optional 和 fetch 两个参数
@Basic(optional = false)
BigDecimal initialPrice;

// ② @Column
@Column(nullable = false)
BigDecimal initialPrice;

// ③ Bean Validation（§3.3.2）—— 推荐
@NotNull
BigDecimal initialPrice;

三者对 JPA 提供者的效果相同

保存时做 null 检查 + schema 里生成 NOT NULL 约束。

作者推荐 @NotNull：这样你可以手工校验 Item 实例，展现层的 UI 代码也能自动执行校验。最终结果差别不大，但「不拿一条注定失败的语句去打数据库」更干净。

@Column 还能改列名
@Column(name = "START_PRICE", nullable = false)
BigDecimal initialPrice;
默认全都是可空的

默认情况下所有持久化属性都可为 null、可选，也就是说一个 Item 可以有未知的 initialPrice。若不标为非可选而试图存 null，数据库会拒绝该 SQL 语句，抛出约束违反异常。

6.1.2　定制属性访问

Ch06/mapping-value-types/src/main/java/…/ch06/model/Item.java
@Entity
public class Item {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    private Long id;                                    ❶ @Id 在字段 → 实体默认字段访问

    @Access(AccessType.PROPERTY)                        ❷ 唯独 name 切换成访问器访问
    @Column(name = "ITEM_NAME")
    private String name;

    public String getName() { return name; }
    public void setName(String name) {                   ❸ 加载和存储 item 时会调用它们
        this.name = !name.startsWith("AUCTION: ") ? "AUCTION: " + name : name;
    }
}
字段访问 vs 属性访问，怎么选

字段访问：可以省掉那些不该暴露的字段的 getter；而且字段声明只占一行，访问器要铺开好几行 —— 代码更易读。

属性访问：访问器方法可以执行额外逻辑。如果你希望持久化对象时发生这些逻辑，就用属性访问；如果希望持久化时避开这些额外动作，就用字段访问。

6.1.3　派生属性：值来自 SQL 表达式

Ch06/mapping-value-types/…/ch06/model/Item.java
@Formula("CONCAT(SUBSTR(DESCRIPTION, 1, 12), '...')")
private String shortDescription;

@Formula("(SELECT AVG(B.AMOUNT) FROM BID B WHERE B.ITEM_ID = ID)")   // 甚至可以是子查询
private BigDecimal averageBidAmount;
特性说明
何时求值每次从数据库取回 Item 时求值，其他时候都不。因此若别的属性被改了，结果可能过时
出现在哪些 SQL 里只在 SELECT 中，永远不出现在 INSERT / UPDATE 里。加载实例时公式被嵌进 SELECT 子句
在哪里计算在数据库里计算
能写什么可引用表的列、调用特定数据库的 SQL 函数、甚至包含子查询
列名解析未限定的列名指的是该派生属性所属类的那张表的列
可移植性代价

SQL 表达式原样传给底层数据库。依赖厂商特有的运算符或关键字会把映射元数据绑死在某个数据库产品上 —— 上例中的 CONCAT() 就是 MySQL 特有的。

6.1.4　转换列值：@ColumnTransformer

数据库列 IMPERIALWEIGHT 存磅，应用属性 Item#metricWeight 用千克。

6.1.5　数据库生成的值与默认值

创建时间戳、商品默认价格、每次修改都跑的触发器 —— 这些值由数据库生成。把属性标为「生成的」，就把「插入/更新后再回查一次」的责任交给了框架：一旦对声明了生成属性的实体发出 INSERT 或 UPDATE，SQL 会紧接着做一次 SELECT 取回生成的值。

Ch06/mapping-value-types/…/ch06/model/Item.java
@CreationTimestamp                      // 实例插入数据库前，自动设为当前日期
private LocalDate createdOn;

@UpdateTimestamp                        // 实例被更新时自动生成
private LocalDateTime lastModified;

@Column(insertable = false)             // 该属性不参与 INSERT
@ColumnDefault("1.00")                   // 导出/生成 DDL 时设置列的默认值
@Generated(org.hibernate.annotations.GenerationTime.INSERT)
private BigDecimal initialPrice;
GenerationTime行为
ALWAYS每次 SQL UPDATE 或 INSERT 之后都刷新实体实例
INSERT只在 SQL INSERT 之后刷新，用来取回数据库提供的默认值

6.1.6　@Temporal 注解（Java 8 之前的遗留写法）

@CreationTimestamp
@Temporal(TemporalType.DATE)
private Date createdOn;

@UpdateTimestamp
@Temporal(TemporalType.TIMESTAMP)
private Date lastModified;

TemporalType 可选 DATE、TIME、TIMESTAMP，决定把时间值的哪一部分存进数据库；没有 @Temporal 时默认是 TIMESTAMP。

用 Java 8 就不需要它

java.time 包里的 LocalDate、LocalDateTime、LocalTime 自身就带着时间精度（日期 / 日期+时间 / 仅时间），所以 JPA 2.2 起不再需要 @Temporal。

6.1.7　映射枚举

…/ch06/model/AuctionType.java
public enum AuctionType {
    HIGHEST_BID,
    LOWEST_BID,
    FIXED_PRICE
}
…/ch06/model/Item.java
@NotNull
@Enumerated(EnumType.STRING)
private AuctionType auctionType =
        AuctionType.HIGHEST_BID;
默认（ORDINAL）是个脆弱的选择

不加 @Enumerated，框架会存序数位置：HIGHEST_BID→1、LOWEST_BID→2、FIXED_PRICE→3。一旦你改动枚举、插入一个新常量，已存在的值就不再对应同一个位置，应用就坏了。因此 EnumType.STRING 是更好的选择 —— 直接存枚举值的标签。

6.2映射可嵌入组件

User 与 Address 之间是聚合（part-of 关系）的一种更强形式：组合（composition） —— 部分的生命周期完全依赖整体。Address 不能脱离 User 存在，所以 UML 里被组合的类通常就是 ORM 的值类型候选。

6.2.1　目标数据库 schema

如果别的实体也引用 Address

比如 Shipment#deliveryAddress，那么 SHIPMENT 表也会带上存放一个 Address 所需的全部列。「类比表多」正是支撑细粒度领域模型的方式。

6.2.2　让类可嵌入

组件与实体的唯一区别就是数据库标识符

Java 里没有「组合」这个概念，类或属性没法被标记为组件。组件类没有个体标识，因此不需要标识符属性或标识符映射。它就是一个普通 POJO。

Ch06/mapping-value-types/…/ch06/model/Address.java
@Embeddable                                ❶ 不是 @Entity；没有标识符属性
public class Address {

    @NotNull                               ❷ DDL 生成时会被忽略！见下方警告
    @Column(nullable = false)               ❸ 靠它来生成 DDL 约束
    private String street;

    @NotNull
    @Column(nullable = false, length = 5)    ❹ length 覆盖默认的 VARCHAR(255)
    private String zipcode;

    @NotNull
    @Column(nullable = false)
    private String city;                     ❺ 默认 VARCHAR(255)

    public Address() { }                     ❻ 框架调它建实例，再直接填字段

    public Address(String street, String zipcode, String city) {   ❼ 便利构造器
        this.street = street; this.zipcode = zipcode; this.city = city;
    }
}
已知缺陷：Hibernate Validator 不为组件属性生成 NOT NULL

写作时这个缺陷仍未修复：生成数据库 schema 时，Hibernate 不会把可嵌入组件属性上的 @NotNull 映射为 NOT NULL 约束，只在运行期用它做 Bean Validation。因此必须额外写 @Column(nullable = false) 才能在 schema 里生成约束。Hibernate 缺陷库编号 HVAL-3。

…/ch06/model/User.java　—— 拥有者实体侧毫无特别之处
@Entity
@Table(name = "USERS")
public class User {
    @Id
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    private Long id;

    private Address homeAddress;   // Address 已是 @Embeddable，这里无需任何注解
}

注解该放在组件类的哪里？五条规则

条件注解位置 / 运行期访问方式
拥有者 @Entity 是字段访问
（隐式：@Id 在字段；显式：类上 @Access(FIELD)）		组件类的映射注解应在字段上，运行期直接读写字段。Address 上的 getter/setter 可选
拥有者 @Entity 是属性访问组件类的映射注解应在 getter 上，运行期调 getter/setter
拥有者的嵌入属性标了 @Access(FIELD)
（如 User#homeAddress）		注解在 Address 的字段上，运行期访问字段
拥有者的嵌入属性标了 @Access(PROPERTY)注解在 Address 的 getter 上，运行期用 getter/setter
@Access 标在可嵌入类自身用所选策略来读取该类上的映射注解并做运行期访问
null 引用的尴尬：没有优雅的表示方式

设想 STREET、ZIPCODE、CITY 都可空。加载一个没有地址信息的 User 时，someUser.getHomeAddress() 该返回什么？返回 null。反过来，框架把 null 的嵌入属性存成所有组件列都是 NULL。

后果：如果你存了一个「空的」Address（实例存在但所有属性都是 null），再加载这个 User 时会拿不到任何 Address 实例。这很反直觉 —— 你本来就不该让这些列可空，也应避免三值逻辑，因为你多半希望用户有一个真实地址。

equals() / hashCode()

应该重写 Address 的 equals() 和 hashCode() 以按值比较实例。不过只要你不需要比较实例（比如把它们放进 HashSet），这就不是关键问题。§8.2.1 会在集合语境下讨论它。

6.2.3　覆盖嵌入属性

要在同一张 USERS 表里存第二个 Address（billingAddress），会和已有的 STREET/ZIPCODE/CITY 三列冲突 —— 用 @AttributeOverride 改列名：

Ch06/mapping-value-types/…/ch06/model/User.java
@Entity
@Table(name = "USERS")
public class User {

    @Embedded                                         ❶ 其实不是必需的，见下
    @AttributeOverride(name = "street",
        column = @Column(name = "BILLING_STREET"))
    @AttributeOverride(name = "zipcode",               ❷ 可重复注解，逐个覆盖属性映射
        column = @Column(name = "BILLING_ZIPCODE", length = 5))
    @AttributeOverride(name = "city",
        column = @Column(name = "BILLING_CITY"))
    private Address billingAddress;
}
❶ @Embedded 何时有用标组件类或标拥有者里的属性二选一即可（都标也无害，但没好处）。@Embedded 在这种情况下有用：你要映射一个第三方组件类，没有源码、没有注解，但有正确的 getter/setter（像普通 JavaBean）。
@AttributeOverride 是「完全」覆盖

被覆盖属性上任何 JPA 或 Hibernate 注解都被忽略。也就是说 Address 类上的 @Column 全部失效 —— 所有 BILLING_* 列都变成可空的！（不过 Bean Validation 仍然认组件属性上的 @NotNull；被覆盖的只是持久化注解。）

ANSI 标准类型 → 厂商类型：方言负责翻译

表里写的是 ANSI 标准类型名，多数 DBMS 厂商忽略 SQL 标准的这一部分（通常因为它们的遗留类型系统早于标准）。JDBC 提供了对厂商类型的部分抽象，让 Hibernate 执行 INSERT/UPDATE 时能用 ANSI 标准类型；生成 schema 时，Hibernate 用配置的 SQL 方言把 ANSI 类型翻译成合适的厂商类型。

想知道具体映射？看方言源码。例如 H2Dialect 里就有：registerColumnType(Types.NUMERIC, "decimal($p,$s)")。BigDecimal 属性的默认精度与标度是 NUMERIC(19, 2)，用 @Column 的 precision / scale 参数可覆盖。

String 的长度决定 SQL 类型属性标了 @Column(length = …) 或 Bean Validation 的 @Length 时，Hibernate 按大小挑类型，且取决于方言。以 MySQL 为例：≤65,535 → VARCHAR(length)；≤16,777,215 → MEDIUMTEXT；更大 → LONGTEXT。Hibernate 对所有 String 属性的默认长度是 255，所以不做任何映射时 String → VARCHAR(255)。
国际化字符类型数据库通常整库或整表设一个合理的（UTF-8）字符集。需要更细控制、想切到国家化变体（NVARCHAR、NCHAR、NCLOB）时，用 @org.hibernate.annotations.Nationalized。
遗留库 / 类型系统受限的 DBMSOracle 连真值类型都没有（而这是关系模型唯一要求的类型）。许多既有 Oracle schema 用 Y/N 或 T/F 字符表示布尔值；Hibernate 的 Oracle 方言默认期待并生成 NUMBER(1,0) 列。

java.util.Date 的经典大坑

存进去的是 java.util.Date，加载回来的不是。Hibernate 会按映射的 TemporalType 返回 java.sql.Date、java.sql.Time 或 java.sql.Timestamp。

为什么：数据库类型精度更高。java.util.Date 是毫秒精度，而 java.sql.Timestamp 包含数据库里可能存在的纳秒信息。Hibernate 不会为了塞进 java.util.Date 而截掉这部分信息 —— 于是用 equals() 比较 java.util.Date 时会出问题：它与 java.sql.Timestamp 子类的 equals() 不对称。

解法（与 Hibernate 无关的通用建议）：不要调 aDate.equals(bDate)。用 Unix 毫秒比较，例如 aDate.getTime() > bDate.getTime()。但要小心：HashSet 这类集合内部也会调 equals() —— 千万别在同一个集合里混放 java.util.Date 与 java.sql.Date|Time|Timestamp。

Calendar 属性没有这个问题（存 Calendar 就返回 Calendar，由 Calendar.getInstance() 创建，实际类型取决于 locale 和时区）。而只要你改用 Java 8 的 LocalDate/LocalTime/LocalDateTime，这些烦恼全部消失。

// 都委托给这个自定义实现

6.3.2　创建自定义 JPA 转换器

业务背景（一个贯穿三节的演进故事）

在线拍卖系统要支持多币种。这类改动很复杂：要改 schema、可能要迁移数据、还要更新所有访问该库的应用。本节展示 JPA 转换器与 Hibernate 可扩展类型系统如何在这个过程中充当缓冲。

Ch06/mapping-value-types2/…/ch06/model/MonetaryAmount.java
public class MonetaryAmount implements Serializable {   ❶ 见下方说明
    private final BigDecimal value;
    private final Currency currency;

    public MonetaryAmount(BigDecimal value, Currency currency) { … }
    public BigDecimal getValue()   { return value; }
    public Currency   getCurrency(){ return currency; }

    @Override public boolean equals(Object o) { … }   ❷ 「按值」比较金额
    @Override public int hashCode() { return Objects.hash(value, currency); }

    public String toString() { return value + " " + currency; }        ❸

    public static MonetaryAmount fromString(String s) {              ❹ 静态工厂
        String[] split = s.split(" ");
        return new MonetaryAmount(new BigDecimal(split[0]),
                                  Currency.getInstance(split[1]));
    }
}
❶ 为什么值类型类应实现 Serializable

Hibernate 把实体实例数据存入共享二级缓存时会拆解（disassemble）实体状态。若实体有 MonetaryAmount 属性，缓存区里存的是该属性值的序列化表示；从缓存区取回实体数据时再反序列化并重新组装。

第一步：DBA 只能改列类型 → 用 AttributeConverter

把 BUYNOWPRICE 存进 ITEM 表的一个 VARCHAR 列，把币种代码拼在金额字符串后面，例如 11.23 USD 或 99 EUR。

…/ch06/model/Item.java
@NotNull
@Convert(converter = MonetaryAmountConverter.class)
@Column(name = "PRICE", length = 63)
private MonetaryAmount buyNowPrice;
…/ch06/converter/MonetaryAmountConverter.java
@Converter
public class MonetaryAmountConverter
  implements AttributeConverter<MonetaryAmount, String> {

    @Override
    public String convertToDatabaseColumn(MonetaryAmount m) {
        return m.toString();
    }
    @Override
    public MonetaryAmount convertToEntityAttribute(String s) {
        return MonetaryAmount.fromString(s);
    }
}

AttributeConverter 的两个泛型参数分别是 Java 属性类型和 schema 中的类型；类必须标 @Converter。

缓冲的价值体现在这里

日后 DBA 升级 schema、为金额和币种提供独立的列时，只需改几处：把 MonetaryAmountConverter 从项目里去掉，把 MonetaryAmount 变成 @Embeddable，它就自动映射到两列。而且选择性地启停转换器也很容易 —— 万一 schema 里有些表还没升级。

把转换器用在组件的属性上

继续细粒度化：给 Zipcode 引入继承（德国邮编 5 位，瑞士 4 位）。

…/ch06/converter/ZipcodeConverter.java
@Converter
public class ZipcodeConverter
    implements AttributeConverter<Zipcode, String> {

    @Override
    public String convertToDatabaseColumn(Zipcode a) {
        return a.getValue();
    }

    @Override
    public Zipcode convertToEntityAttribute(String s) {
        if (s.length() == 5) return new GermanZipcode(s);
        else if (s.length() == 4) return new SwissZipcode(s);
        throw new IllegalArgumentException(
            "Unsupported zipcode in database: " + s);
    }
}
…/ch06/model/User.java　—— 用 attributeName 指路
@Entity
@Table(name = "USERS")
public class User {
    @Convert(
        converter = ZipcodeConverter.class,
        attributeName = "city.zipcode"   // 点号路径
    )
    private Address homeAddress;
}

zipcode 不是 Address 的属性、而是嵌套的 City 的属性，所以写成嵌套路径 city.zipcode。JPA 2.2 起可以在同一个嵌入属性上叠加多个 @Convert；JPA 2.1 及以前必须用一个 @Converts 包起来。

用在集合与 Map 上的 attributeName 语法

持久化属性要转换的目标attributeName
Map<Address, String>每个 map 键的 zipcode 属性key.zipcode
Map<String, Address>每个 map 值的 zipcode 属性value.zipcode
Map<Zipcode, String>每个条目的键本身key
Map<String, Zipcode>每个条目的值本身不设 attributeName

嵌套时同样可写点号路径，如 key.city.zipcode。转换器也能用在集合的值上（如持久化的 Set<Zipcode>，配合 @ElementCollection，见第 8 章）。

JPA 转换器的限制
  • 不能用在实体的标识符或版本属性上。
  • 不该用在标了 @Enumerated 或 @Temporal 的属性上 —— 这些注解已经声明了该做何种转换。想为枚举或日期时间属性写自定义转换器，就不要再标这两个注解。
  • 不支持多列转换。
  • 不与查询引擎集成：写不出 select i from Item i where i.buyNowPrice.amount > 100 —— Hibernate 知道怎么把 MonetaryAmount 与字符串互转，却不知道它有个 amount 属性，因此无法解析这种查询。

6.3.3　用 Hibernate UserType 扩展

业务背景第三幕

DBA 终于加了列：ITEM 表现在有 BUYNOWPRICE_AMOUNT / BUYNOWPRICE_CURRENCY，以及 INITIALPRICE_AMOUNT / INITIALPRICE_CURRENCY。但还有一个附加要求：因为还有别的老应用访问这个库，存库前必须把每个金额换算成目标币种 —— buyNowPrice 存美元，initialPrice 存欧元。

「如果这个例子看着牵强，我们向你保证：真实世界里更糟的都有。共享数据库 schema 的演进代价高昂但必然，因为数据总比应用活得久。」

org.hibernate.usertype 包里的扩展接口

接口能力
UserType直接与 JDBC 交互来转换值：存数据用 PreparedStatement，读数据用 ResultSet。还能控制 Hibernate 如何缓存与脏检查这些值
CompositeUserType告诉 Hibernate MonetaryAmount 有 amount 和 currency 两个属性，于是查询里能用点号引用：select avg(i.buyNowPrice.amount) from Item i
ParameterizedType在映射中给适配器传设置。只写一个适配器，在映射属性时定制其行为（有的映射转美元、有的转欧元）
DynamicParameterizedType更强的设置 API，能拿到动态信息（如映射的列名和表名）。没有额外成本或复杂度，不妨直接用它代替 ParameterizedType
EnhancedUserType可选接口，用于标识符属性和判别列的适配器。与 JPA 转换器不同，Hibernate 的 UserType 可以适配任何实体属性
UserVersionType可选接口，用于版本属性的适配器
UserCollectionType很少用。实现自定义集合时需要 —— 比如持久化非 JDK 集合（Guava 的 Multiset、Multimap、BiMap、Table 等）并保留其额外语义
Ch06/mapping-value-types4/…/ch06/converter/MonetaryAmountUserType.java（结构与要点）
public class MonetaryAmountUserType
        implements CompositeUserType, DynamicParameterizedType {

    private Currency convertTo;                                   // 目标币种

    public void setParameterValues(Properties parameters) {       // 来自 DynamicParameterizedType
        String p = parameters.getProperty("convertTo");
        this.convertTo = Currency.getInstance(p != null ? p : "USD");  // 未设置则默认美元
    }

    public Class returnedClass() { return MonetaryAmount.class; }   // 适配的类
    public boolean isMutable() { return false; }                   // 知道它不可变 → Hibernate 可优化
    public Object deepCopy(Object value) { return value; }        // 不可变类直接返回原实例

    public Serializable disassemble(Object v, …) { return v.toString(); }  // 存入二级缓存时
    public Object assemble(Serializable cached, …) {                        // 从二级缓存读回时
        return MonetaryAmount.fromString((String) cached); }
    public Object replace(Object original, …) { return original; }        // merge() 期间调用

    public boolean equals(Object x, Object y) { … }   // 用值相等判断是否变脏、要不要 UPDATE
    public int hashCode(Object x) { return x.hashCode(); }

    public Object nullSafeGet(ResultSet rs, String[] names, …) throws SQLException {
        BigDecimal amount = rs.getBigDecimal(names[0]);
        if (rs.wasNull()) return null;
        Currency currency = Currency.getInstance(rs.getString(names[1]));
        return new MonetaryAmount(amount, currency);
    }

    public void nullSafeSet(PreparedStatement st, Object value, int index, …) throws SQLException {
        if (value == null) {
            st.setNull(index,     StandardBasicTypes.BIG_DECIMAL.sqlType());
            st.setNull(index + 1, StandardBasicTypes.CURRENCY.sqlType());
        } else {
            MonetaryAmount dbAmount = convert((MonetaryAmount) value, convertTo);  // 换算到目标币种
            st.setBigDecimal(index,     dbAmount.getValue());
            st.setString(index + 1, convertTo.getCurrencyCode());
        }
    }

    public MonetaryAmount convert(MonetaryAmount a, Currency to) {   // 不是 UserType API 的方法
        return new MonetaryAmount(a.getValue().multiply(new BigDecimal(2)), to);
        // ↑ 例子里简单地翻倍，方便验证转换是否生效；真实应用要换成真正的汇率换算
    }

    // 下面这几个来自 CompositeUserType —— 正是它们让查询引擎认识 MonetaryAmount 的内部属性
    public String[] getPropertyNames() { return new String[]{"value", "currency"}; }
    public Type[] getPropertyTypes()  { return new Type[]{
            StandardBasicTypes.BIG_DECIMAL, StandardBasicTypes.CURRENCY}; }
    public Object getPropertyValue(Object c, int property) { … }
    public void setPropertyValue(Object c, int p, Object v) {
        throw new UnsupportedOperationException("MonetaryAmount is immutable");
    }
}

    @org.hibernate.annotations.Type(type = "monetary_amount_usd")
    @org.hibernate.annotations.Columns(columns = {          ← 注意注解顺序很重要！
        @Column(name = "BUYNOWPRICE_AMOUNT"),
        @Column(name = "BUYNOWPRICE_CURRENCY", length = 3)
    })
    private MonetaryAmount buyNowPrice;

    @NotNull
    @org.hibernate.annotations.Type(type = "monetary_amount_eur")
    @org.hibernate.annotations.Columns(columns = {
        @Column(name = "INITIALPRICE_AMOUNT"),
        @Column(name = "INITIALPRICE_CURRENCY", length = 3)
    })
    private MonetaryAmount initialPrice;
}
三点必须注意
  1. UserType 若只转换单列，不需要 @Column。MonetaryAmountUserType 访问两列，所以必须显式声明两列。
  2. JPA 不支持在单个属性上写多个 @Column，所以要用私有的 @org.hibernate.annotations.Columns 分组。
  3. 注解的顺序现在很重要！回看 MonetaryAmountUserType：很多操作依赖数组的下标访问。访问 PreparedStatement / ResultSet 的顺序，就是映射中声明列的顺序。

另外：选 UserType 还是 CompositeUserType，与列数无关 —— 只取决于你是否想把值类型的属性暴露给查询。

本章小结

  • 可以映射实体类的基本属性与嵌入属性。
  • 可以覆盖基本映射、改列名，使用派生属性（@Formula）、默认值（@ColumnDefault+@Generated）、时间属性与枚举属性，并为之编写测试。
  • 可以实现可嵌入组件类，构建细粒度领域模型；用 @AttributeOverride 在同一张表里放多份组件。
  • 组合中多个 Java 类（如 Address 和 City）的属性可以全部映射到一张实体表，无论嵌套多深。
  • 任何 JPA 提供者都支持一组最小的 Java↔SQL 类型转换，Hibernate 还提供额外适配器；用 @org.hibernate.annotations.Type 显式选择，或在引导配置里全局覆盖。
  • 可以用标准 JPA 扩展接口写自定义类型转换器（AttributeConverter，如 MonetaryAmount），也可以用原生的 Hibernate UserType API 写低层适配器 —— 后者支持多列并能集成查询引擎。
