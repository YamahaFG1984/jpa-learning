第 12 章　抓取计划、策略与剖面

本章解决第 1 章提出的 ORM 根本难题之一：导航（§1.2.5） —— Java 代码访问数据的方式与关系数据库访问数据的方式之间的差异。这是全书性能优化的核心章节。

Hibernate 把数据从数据库放进内存的五种方式
  1. 按标识符取回实体实例 —— 已知唯一标识符时最方便，如 entityManager.find(Item.class, 123)
  2. 导航实体图 —— 从一个已加载实例出发，通过属性访问器访问关联实例，如 someItem.getSeller().getAddress().getCity()；开始遍历映射集合时元素也会按需加载。只要持久化上下文还开着，Hibernate 就会自动加载图中的节点。本章的焦点就是：调访问器和遍历集合时加载了什么、怎么加载的。
  3. JPQL —— 基于字符串的完整面向对象查询语言
  4. CriteriaQuery 接口 —— 类型安全、面向对象、无需字符串拼接
  5. 原生 SQL 查询 / 存储过程 —— 让 Hibernate 负责把 JDBC 结果集映射成领域模型实例

JPA 2 新特性：用新的 PersistenceUtil 静态帮助类手工检查实体或属性的初始化状态；用新的 EntityGraph API 创建标准化的声明式抓取计划。运行示例前先执行 Ch12/Ch12.sql。

§三个核心概念，一次分清

12.1懒加载与急加载

为实现懒加载，Hibernate 依赖运行期生成的实体占位符（代理 proxy）和智能的集合包装器（collection wrapper）。

12.1.1　理解实体代理

@ManyToOne 的 JPA 默认值是 EAGER！ 
@Entity
public class Item {
    @ManyToOne(fetch = FetchType.LAZY)     // ← 必须显式覆盖，否则加载 Item 就连带加载 seller
    public User getSeller() { return seller; }
}

集合（@ElementCollection、@OneToMany、@ManyToMany）默认就是 LAZY，不必写。

懒抓取计划下的 LazyInitializationException 
Item item = em.find(Item.class, ITEM_ID);   // seller 是未初始化的 User 代理
em.detach(item);
em.detach(item.getSeller());                // 或直接 em.close() 游离一切

assertTrue(pu.isLoaded(item));              // PersistenceUtil 没有上下文也能工作
assertFalse(pu.isLoaded(item, "seller"));
assertEquals(USER_ID, item.getSeller().getId());   // 游离态下调「标识符 getter」可以
// item.getSeller().getUsername();          ← 抛 LazyInitializationException

数据只能在持久化上下文管理该代理期间按需加载，游离态下不行。

一对一关联的懒加载为什么令人困惑？

考虑基于共享主键的一对一（§9.1.1）：只有 optional=false 时该关联才能被代理化。例如 Address 总是引用一个 User。如果这个关联可空、可选，Hibernate 必须先打库才能知道该放代理还是放 null —— 而懒加载的目的恰恰是「根本不打库」。

代理的妙用：不加载任何数据就能存新 Bid 
Item item = em.getReference(Item.class, ITEM_ID);   // 产生 Item 代理
User user = em.getReference(User.class, USER_ID);   // 产生 User 代理
Bid newBid = new Bid(new BigDecimal("99.00"));
newBid.setItem(item);  newBid.setBidder(user);
em.persist(newBid);
// 整个过程没有一条 SELECT，只有一条 INSERT ——
// 所有外键值都可以从 Item 与 User 代理的标识符值拿到
运行期代理的三点局限
  1. 有些代理不完全透明：例如用 instanceof 测试的多态关联（§7.8.1 演示过）。
  2. 写自定义 equals()/hashCode() 时不能直接访问字段（§10.3.2）。
  3. 代理只能懒加载实体关联，不能懒加载单个基本属性或嵌入组件（如 Item#description、User#homeAddress）。给这类属性加 @Basic(fetch = FetchType.LAZY) 会被 Hibernate 忽略，值在拥有者实体加载时就急切加载了。除非你有大量可选/可空列、或有因物理限制必须按需取的大值列，否则在「SQL 选取的单个列」这个层面优化是不必要的；大值最好用 LOB 表示 —— 它们按定义就提供懒加载（§6.3.1）。

12.1.2　懒加载的持久集合

特殊优化：LazyCollectionOption.EXTRA 
@OneToMany(mappedBy = "item")
@org.hibernate.annotations.LazyCollection(
    org.hibernate.annotations.LazyCollectionOption.EXTRA)
public Set<Bid> getBids() { return bids; }

// 用法
Item item = em.find(Item.class, ITEM_ID);      // select * from ITEM where ID = ?
assertEquals(3, item.getBids().size());       // select count(b) from BID b where b.ITEM_ID = ?
                                               // ← 不把 bids 加载进内存！

extra-lazy 集合支持的免初始化操作：size()、isEmpty()、contains()；Set 的 add() 用一条简单查询检查重复；List 的 get(index) 只加载一个元素；Map 支持 containsKey()/containsValue()。

另外：Hibernate.initialize(bids) 会把集合完全加载 —— 没法说「只加载前两条出价」，那得写查询。

12.1.3　关联与集合的急加载

@Entity
public class Item {
    @ManyToOne(fetch = FetchType.EAGER)                          // 实体的默认值本来就是 EAGER
    private User seller;
    @OneToMany(mappedBy = "item", fetch = FetchType.EAGER)      // ← 一般不推荐
    private Set<Bid> bids = new HashSet<>();
}
LAZY 是提示，EAGER 是硬性要求

FetchType.LAZY 是一个 JPA 提供者可以忽略的提示；而 FetchType.EAGER 是硬性要求 —— 提供者必须保证数据被加载、在游离态可用，不能忽略这个设置。

集合上写 EAGER 真的是好主意吗？「只要 item 被加载进内存，就立刻把它的出价也加载进来」—— 即便你只想显示商品名或看拍卖何时结束，所有出价都会被载入内存。把 FetchType.EAGER 作为映射中的默认抓取计划通常不是好策略（下一节的笛卡儿积问题会说明原因）。集合最好保持默认的 FetchType.LAZY。

Item item = em.find(Item.class, ITEM_ID);
// select i.*, u.*, b.*
// from ITEM i
//   left outer join USERS u on u.ID = i.SELLER_ID
//   left outer join BID   b on b.ITEM_ID = i.ID
// where i.ID = ?                        ← 一条 SQL，JOIN 三张表
em.detach(item);                          // 抓取结束，不再有懒加载
assertEquals(3, item.getBids().size());              // ✓ 游离态可用
assertEquals("johndoe", item.getSeller().getUsername()); // ✓ 游离态可用
// 但每个 Bid 仍持有一个未初始化的 bidder 代理 —— 访问它就抛异常

12.2选择抓取策略：在两个极端之间找中点

hibernate.max_fetch_depth

Hibernate 必须在某处停止跟随 EAGER 计划。JOIN 的表数由这个全局配置属性决定，默认无限制。合理值很小，通常 1 到 5；设为 0 可以禁用 @ManyToOne/@OneToOne 的 JOIN 抓取。达到上限后 Hibernate 仍会按计划急加载数据，但改用额外的 SELECT 语句。（注意有些数据库方言会预设它，例如 MySQLDialect 设为 2。）

四种优化手段横向对比

手段配置生成的 SQL取舍
批量预抓取
§12.2.3		@org.hibernate.annotations.BatchSize(size = 10)（放在实体类上，或集合属性上）select * from USERS where ID in (?,?,?,?,?,?,?,?,?,?)「盲猜式优化」：我们不知道某个上下文里有多少未初始化代理，10 只是猜。把 n+1 条查询降到 ⌈n/10⌉+1 条，显著减少。合理值通常较小 —— 也不想载入太多不确定要用的数据
子查询预抓取
§12.2.4		@org.hibernate.annotations.Fetch(FetchMode.SUBSELECT)（只用于集合）select * from BID where ITEM_ID in (select ID from ITEM)不是盲猜：Hibernate 记住加载 items 的原始查询，把它（略作修改）嵌进子查询。但这个「记忆」只在某个持久化上下文内有效 —— 若把 Item 游离后再 merge 进新上下文再遍历集合，不会发生预抓取
多 SELECT 急抓取
§12.2.5		@Fetch(FetchMode.SELECT) + FetchType.EAGER三条独立 SELECT：ITEM、USERS、BID用来避开笛卡儿积。FetchMode 默认是 JOIN。注意：这些额外 SELECT 不是懒执行的 —— 一次 find() 就产生多条 SQL
动态急抓取
§12.2.6
推荐		查询里写 join fetch，或 Criteria 的 root.fetch("seller")inner join USERS u on u.ID = i.SELLER_ID只对特定过程生效，不是全局设置。上面三种都是全局的、永远激活的 —— 为解决某一处问题而调的设置，可能对别处产生负面副作用，这种平衡很难维持
§12.2.3 批量预抓取
@Entity @Table(name = "USERS")
@org.hibernate.annotations.BatchSize(size = 10)
public class User { … }

@Entity public class Item {
    @OneToMany(mappedBy = "item")
    @org.hibernate.annotations.BatchSize(size = 5)
    private Set<Bid> bids = new HashSet<>();
}
真实的批量抓取算法（比上面复杂）

假设批大小 32。启动时 Hibernate 在内部创建若干批加载器，每个知道自己能初始化多少个代理。目标是最小化创建加载器的内存消耗、创建足够多的加载器覆盖每种可能的批次、以及最小化 SQL 查询数。

要初始化 31 个代理，Hibernate 执行 3 批（你大概以为是 1，因为 32>31），自动选中的加载器是 16、10、5。

可用 hibernate.batch_fetch_style 定制：默认 LEGACY（启动时构建并挑选多个批加载器）；PADDED（启动时只建一条带 32 个 IN 占位符的 SQL，不足 32 个时重复绑定标识符）；DYNAMIC（运行时知道要初始化多少个代理后动态构建批 SQL）。

§12.2.6 动态急抓取 —— JPQL 与 Criteria 两种写法
// ① 关联：join fetch（生成 INNER JOIN）
List<Item> items = em.createQuery(
    "select i from Item i join fetch i.seller", Item.class)
    .getResultList();
em.close();                       // 全部游离
for (Item item : items)
    assertNotNull(item.getSeller().getUsername());  // ✓ 数据都在

// 等价的 Criteria 写法
CriteriaQuery<Item> criteria = cb.createQuery(Item.class);
Root<Item> i = criteria.from(Item.class);
i.fetch("seller");
criteria.select(i);

// ② 集合：必须用 LEFT OUTER JOIN
//    —— 因为没有出价的 ITEM 行我们也要
em.createQuery(
    "select i from Item i left join fetch i.bids", Item.class);

i.fetch("bids", JoinType.LEFT);   // Criteria 版
批量预抓取的价值判断

「虽然我们可能预抓了用不上的数据、多占了内存，但减少的数据库往返可以带来巨大差别。内存很便宜，扩展数据库服务器却不便宜。」

12.3使用抓取剖面

Hibernate 抓取剖面JPA 实体图（Entity graphs）
标准性私有 APIJPA 2.1 规范
声明@org.hibernate.annotations.FetchProfile@NamedEntityGraph（注解或 XML），或 EntityGraph API
启用Session#enableFetchProfile()（需要 Hibernate API），启用后对该工作单元中的任何操作都激活作为 hint 加在 find() 或查询（JPQL/Criteria）上
能改什么选择性地覆盖懒映射的实体关联与集合，为某个工作单元启用 JOIN 急抓取策略只控制「应加载什么」，遗憾的是不控制怎么加载
局限功能较简单，适合较小或较简单的应用① 只能改抓取计划，改不了 Hibernate 的抓取策略（batch/subselect/join/select）；② 注解或 XML 中声明不是完全类型安全的（属性名是字符串）—— 但 EntityGraph API 是类型安全的

作者评价：「公平地说，这里还有改进空间，我们期待未来版本的 Hibernate 与 JPA 提供一个统一且更强大的 API。」JPQL 查询本身就是一种声明式（具名）抓取剖面，我们缺的是在同一个基础查询上轻松叠加不同计划的能力（见过一些用字符串拼接的「创意方案」，最好避免）。Criteria 查询则已有完整的 Java 能力来组织构建代码。实体图的价值在于：抓取计划可以跨任意类型的查询复用。

12.3.1　声明 Hibernate 抓取剖面

Ch12/profile/src/main/java/…/ch12/profile/package-info.java　—— 全局元数据，作者偏好放包级
@org.hibernate.annotations.FetchProfiles({
    @FetchProfile(name = Item.PROFILE_JOIN_SELLER,      // ❶ 每个剖面有名字，抽成常量
        fetchOverrides = @FetchProfile.FetchOverride(
            entity = Item.class,
            association = "seller",                     // ❷ 每条覆盖指名一个关联或集合
            mode = FetchMode.JOIN                        // ❸ 用 JOIN 急抓取
        )),
    @FetchProfile(name = Item.PROFILE_JOIN_BIDS,
        fetchOverrides = @FetchProfile.FetchOverride(
            entity = Item.class, association = "bids", mode = FetchMode.JOIN))
})
Item item = em.find(Item.class, ITEM_ID);                // 默认懒计划：只取 Item

em.clear();
em.unwrap(Session.class).enableFetchProfile(Item.PROFILE_JOIN_SELLER);
item = em.find(Item.class, ITEM_ID);                     // 现在同一条 SQL 里 join 取 seller

em.clear();
em.unwrap(Session.class).enableFetchProfile(Item.PROFILE_JOIN_BIDS);
item = em.find(Item.class, ITEM_ID);                     // 剖面可以叠加：seller 和 bids 都 join 取

12.3.2　使用实体图（Entity graphs）

① 注解式声明
@NamedEntityGraphs({
    @NamedEntityGraph(
        name = "ItemSeller",
        attributeNodes = { @NamedAttributeNode("seller") })
})
@Entity
public class Item {
    @NotNull @ManyToOne(fetch = FetchType.LAZY) private User seller;
    @OneToMany(mappedBy = "item") private Set<Bid> bids = new HashSet<>();
    @ElementCollection private Set<String> images = new HashSet<>();
}

// 使用
Map<String,Object> properties = new HashMap<>();
properties.put("javax.persistence.loadgraph",
               em.getEntityGraph("ItemSeller"));
Item item = em.find(Item.class, ITEM_ID, properties);
// select i.*, u.* from ITEM i inner join USERS u on u.ID = i.SELLER_ID where i.ID = ?
② API 式构建（类型安全）
EntityGraph<Item> itemGraph = em.createEntityGraph(Item.class);
itemGraph.addAttributeNodes(Item_.seller);   // ← 静态元模型（§3.3.4）
properties.put("javax.persistence.loadgraph", itemGraph);
Item item = em.find(Item.class, ITEM_ID, properties);

// 也可以作为查询提示
List<Item> items = em.createQuery("select i from Item i", Item.class)
    .setHint("javax.persistence.loadgraph", itemGraph)
    .getResultList();
// select i.*, u.* from ITEM i left outer join USERS u on u.ID = i.SELLER_ID

空的实体图（不指定任何 attributeNode）会沿用实体类的默认值 —— 因此对全懒的 Item 来说，加不加这个 hint 结果一样。

③ 复杂实体图：可复用的子图（subgraph）
@NamedEntityGraphs({
    @NamedEntityGraph(
        name = "BidBidderItemSellerBids",
        attributeNodes = {
            @NamedAttributeNode(value = "bidder"),
            @NamedAttributeNode(value = "item", subgraph = "ItemSellerBids")
        },
        subgraphs = {
            @NamedSubgraph(name = "ItemSellerBids",
                attributeNodes = { @NamedAttributeNode("seller"),
                                   @NamedAttributeNode("bids") })
        })
})
@Entity
public class Bid { … }
// 作为 load graph 取 Bid 时，会连带急抓取 Bid#bidder、Bid#item，
// 以及更深层的 Item#seller 和全部 Item#bids

// 等价的 API 写法
EntityGraph<Bid> bidGraph = em.createEntityGraph(Bid.class);
bidGraph.addAttributeNodes(Bid_.bidder, Bid_.item);
Subgraph<Item> itemGraph = bidGraph.addSubgraph(Bid_.item);
itemGraph.addAttributeNodes(Item_.seller, Item_.bids);
命名约定

「虽然你可以随意命名实体图，我们建议制定一套团队所有人都能遵循的约定，并把这些字符串移到共享常量里。」

本章小结

  • 抓取剖面把抓取计划（加载什么）与抓取策略（怎么加载）结合起来，封装成可复用的元数据或代码。
  • 可以创建全局抓取计划，定义哪些关联和集合应当始终被加载进内存。本书推荐：全部 FetchType.LAZY，再逐案覆盖。
  • 制定抓取计划的依据是用例：应用如何访问关联实体、如何遍历集合，以及哪些数据必须在游离态可用。
  • 为抓取计划选择正确的抓取策略，目标是最小化必须执行的 SQL 语句数量以及每条 SQL 的复杂度。
  • 抓取策略尤其用于避免 n+1 selects 问题与笛卡儿积问题：批量预抓取（@BatchSize，盲猜式）、子查询预抓取（FetchMode.SUBSELECT）、多 SELECT 急抓取（FetchMode.SELECT）、以及最推荐的动态 join fetch。
  • 代理与集合包装器是懒加载的实现基础，也是「已加载图」的边界；游离态访问未初始化代理会抛 LazyInitializationException。
