第 15 章　使用 Spring Data JDBC

Spring Data JDBC 的目标是高效地处理基于 JDBC 的仓库。它是 Spring Data 家族里更年轻的成员，不提供缓存、不提供延迟加载，因而是一个更简单、也更受限的 ORM。本章从零搭一个 Spring Boot + Spring Data JDBC 项目，走一遍查询、分页、流式、修改型查询，最后把一对一 / 嵌入 / 一对多 / 多对多四种关系都建一遍模。

本章的六个源码工程

同一个 CaveatEmptor 用户模块会逐步演进六次：Ch15/spring-data-jdbc（骨架）→ spring-data-jdbc2（查询方法）→ spring-data-jdbc3（一对一）→ spring-data-jdbc4（嵌入）→ spring-data-jdbc5（一对多）→ spring-data-jdbc6（多对多）。运行前先执行 Ch15/Ch15.sql。

15.0 已经有 JPA 了，为什么还要 Spring Data JDBC？

前面 14 章你已经充分体会到：对象/关系映射（ORM）会给项目带来复杂度。持久化上下文、脏检查、一级缓存、代理、延迟加载、LazyInitializationException、n+1 查询⋯⋯这些机制在解决问题的同时也带来了心智负担。有时候我们只想去掉这层复杂度，但又不想放弃 Spring 带来的好处。

那么退回到「老式 JDBC」呢？也不行——你得自己开关连接、自己处理异常，写一大堆样板服务代码。

Spring Data JDBC 给你什么

  • 沿用你已经熟悉的概念：实体、仓库、@Query
  • 自带一个（很轻的）ORM：对象 ↔ 表的映射仍然自动完成
  • Spring Boot 自动配置、依赖注入、声明式事务照旧
  • 2.0 起提供查询构建器机制（按方法名派生查询）

Spring Data JDBC 不给你什么

  • 不用 JPQL，只写原生 SQL → 没有可移植性，换数据库要重写
  • 实体加载要么全加载、要么不加载（没有延迟加载）
  • 没有缓存
  • 没有 Session、没有脏检查——必须显式 save()
  • 不支持 schema 自动生成——DDL 得你自己写自己跑

schema.sql 与实体类

启动时 Spring Boot 会执行 classpath 上的 schema.sql 和 data.sql。因为 Spring Data JDBC 不生成 DDL，这个文件就是你的 schema 唯一来源。

实体类用的注解全部来自 org.springframework.data 包，不是 javax.persistence：

Spring Data JDBC对应的 JPA 注解说明
org.springframework.data.relational.core.mapping.Tablejavax.persistence.Table指定对应的表名
org.springframework.data.annotation.Idjavax.persistence.Id标识符字段。没有 @GeneratedValue——由数据库的 AUTO_INCREMENT 负责
org.springframework.data.relational.core.mapping.Columnjavax.persistence.Column指定列名；默认把驼峰转成蛇形（registrationDate → REGISTRATION_DATE）
Ch15/spring-data-jdbc/src/main/java/com/manning/javapersistence/ch15/model/User.java
@Table("USERS")                          // A
public class User {

    @Id                                    // B
    @Column("ID")                          // C：这就是默认值，写不写都一样
    private Long id;

    @Column("USERNAME")                    // D
    private String username;

    @Column("REGISTRATION_DATE")           // E
    private LocalDate registrationDate;

    // 构造器、getter、setter
}
驼峰转蛇形是自动的

上面三个 @Column 写的都是默认值，可以全部删掉。Spring Data JDBC 会把类字段的驼峰命名转成表列的蛇形命名。只有当列名不符合这条规则时，才必须显式写 @Column。

15.2.2 限制结果、排序与分页

和 Spring Data JPA 一样，first 与 top 关键字（两者等价）用来限制结果条数，后面可跟一个可选数字；不写数字则默认为 1。分页信息用 Pageable 接口表达，实践中用它的实现类 PageRequest，可以指定页号、页大小和排序条件。

Ch15/spring-data-jdbc2/.../repositories/UserRepository.java
Optional<User> findFirstByOrderByUsernameAsc();
Optional<User> findTopByOrderByRegistrationDateDesc();
Page<User>     findAll(Pageable pageable);
List<User>     findFirst2ByLevel(int level, Sort sort);
List<User>     findByLevel(int level, Sort sort);
List<User>     findByActive(boolean active, Pageable pageable);
Ch15/spring-data-jdbc2/src/test/.../FindUsersSortingAndPagingTest.java
public class FindUsersSortingAndPagingTest extends SpringDataJdbcApplicationTests {

    @Test
    void testOrder() {
        User user1 = userRepository.findFirstByOrderByUsernameAsc().get();          // A
        User user2 = userRepository.findTopByOrderByRegistrationDateDesc().get();
        Page<User> userPage = userRepository.findAll(PageRequest.of(1, 3));         // B
        List<User> users = userRepository.findFirst2ByLevel(2,                       // C
                                          Sort.by("registrationDate"));
        assertAll(
            () -> assertEquals("beth",   user1.getUsername()),
            () -> assertEquals("julius", user2.getUsername()),
            () -> assertEquals(2, users.size()),
            () -> assertEquals(3, userPage.getSize()),
            () -> assertEquals("beth",   users.get(0).getUsername()),
            () -> assertEquals("marion", users.get(1).getUsername()));
    }

    @Test
    void testFindByLevel() {
        Sort.TypedSort<User> user = Sort.sort(User.class);                          // D
        List<User> users = userRepository.findByLevel(3,
                   user.by(User::getRegistrationDate).descending());              // E
        assertAll(
            () -> assertEquals(2, users.size()),
            () -> assertEquals("james", users.get(0).getUsername()));
    }

    @Test
    void testFindByActive() {
        List<User> users = userRepository.findByActive(true,                        // F
                   PageRequest.of(1, 4, Sort.by("registrationDate")));
        assertAll(
            () -> assertEquals(4, users.size()),
            () -> assertEquals("burk", users.get(0).getUsername()));
    }
}
A 按用户名升序取第一个用户；按注册日期降序取第一个用户。
B 取全部用户并切页，返回页号 1、每页 3 条（页号从 0 开始）。
C 取 level 为 2 的前两个用户，按注册日期排序。
D Sort.TypedSort 继承 Sort，可以用方法引用指定排序属性——不再用容易写错的字符串。
E 取 level 为 3 的用户，按注册日期降序。
F 取活跃用户，按注册日期排序，切页后返回页号 1、每页 4 条。
Sort.by("registrationDate") vs Sort.sort(User.class).by(User::getRegistrationDate)

前者是字符串——重构改字段名时不会跟着变，编译器也拦不住你。后者是类型安全的：TypedSort 用方法句柄（method handle）来指定属性，写错就编译不过。能用后者就用后者。这和第 19 章的 Querydsl 是同一种精神。

15.2.3 流式结果

返回多条结果的查询方法可以用标准 Java 接口（Iterable、List、Set）。和 Spring Data JPA 一样，Spring Data JDBC 也支持 Streamable——它可以替代 Iterable 或任何集合类型，并且允许你拼接多个 Streamable、直接对元素做 filter / map。

使用场景：不等整个集合（或整页）加载完，就开始处理最先流进来的结果。与集合不同，流只能消费一次且不可变。

Ch15/spring-data-jdbc2/.../repositories/UserRepository.java
Streamable<User> findByEmailContaining(String text);
Streamable<User> findByLevel(int level);
Ch15/spring-data-jdbc2/src/test/.../QueryResultsTest.java
@Test
void testStreamable() {
    try (Stream<User> result =
             userRepository.findByEmailContaining("someother")      // A
                 .and(userRepository.findByLevel(2))                 // B
                 .stream().distinct()) {                              // C
        assertEquals(6, result.count());                            // D
    }
}
必须关闭流

注意流是放在 try-with-resources 里的，所以会自动关闭。另一种做法是显式调用 close()。否则这个流会一直占着底层的数据库连接不放。

15.2.4 @Query 与 15.2.5 修改型查询

用 @Query 注解可以给方法指定自定义查询，此时方法名不必遵循任何命名约定。但和 Spring Data JPA 相比有两处关键差异：

差异 1：只能用具名参数

参数只能按名字识别，必须用 @Param 注解绑定到查询里的 :NAME 占位符。没有 ?1 这种位置参数的写法。

差异 2：SQL，不是 JPQL

写的是原生 SQL，因此没有可移植性——换数据库厂商就得重写所有查询。

Ch15/spring-data-jdbc2/.../repositories/UserRepository.java
@Query("SELECT COUNT(*) FROM USERS WHERE ACTIVE = :ACTIVE")                    // A
int findNumberOfUsersByActivity(@Param("ACTIVE") boolean active);

@Query("SELECT * FROM USERS WHERE LEVEL = :LEVEL AND ACTIVE = :ACTIVE")      // B
List<User> findByLevelAndActive(@Param("LEVEL") int level,
                                @Param("ACTIVE") boolean active);

// —— 修改型查询：必须再加 @Modifying ——
@Modifying
@Query("UPDATE USERS SET LEVEL = :NEW_LEVEL WHERE LEVEL = :OLD_LEVEL")       // C
int updateLevel(@Param("OLD_LEVEL") int oldLevel,
                @Param("NEW_LEVEL") int newLevel);

@Modifying
@Query("DELETE FROM USERS WHERE LEVEL = :LEVEL")                            // D
int deleteByLevel(@Param("LEVEL") int level);
A 返回活跃用户的数量。
B @Param 把查询里的 :LEVEL 与方法参数 level、:ACTIVE 与 active 对应起来。
C 把 level 为 oldLevel 的用户改成 newLevel。INSERT / UPDATE / DELETE 及 DDL 语句都要加 @Modifying。
D 删除指定 level 的全部用户，返回受影响行数。
删除方法没有查询派生

写作本书时，Spring Data JDBC 不支持 delete 方法的查询派生（Spring Data JPA 支持）。也就是说你不能只写一个 deleteByLevel(int level) 方法名就完事——必须配上 @Modifying + @Query 明确写出 SQL。

15.3 用 Spring Data JDBC 建模关系

类之间的关联、表之间的关系，是 ORM 问题的核心。第 8 章我们看了 JPA / Spring Data JPA 的解法，现在看 Spring Data JDBC 的。

核心机制：@MappedCollection

JPA 用 @OneToOne / @OneToMany / @ManyToMany 三个注解表达三种基数。Spring Data JDBC 只有一个 @MappedCollection（1.1 引入），基数由「你在类里声明的是单个引用还是集合」决定：

  • 字段是 private Address address; → 一对一
  • 字段是 private Set<Address> addresses; → 一对多
  • 多对多？没有——你得手写中间类，把它降级成一对多

换句话说：关系建模的责任更多落在程序员的类设计上，而不是注解上。

15.3.1 一对一

每个 User 只有一个 Address，每个 Address 属于一个 User。

Ch15/spring-data-jdbc3/src/main/resources/schema.sql
DROP TABLE IF EXISTS ADDRESSES;
DROP TABLE IF EXISTS USERS;

CREATE TABLE USERS (
   ID INTEGER AUTO_INCREMENT PRIMARY KEY,
   ACTIVE BOOLEAN, USERNAME VARCHAR(30), EMAIL VARCHAR(30),
   LEVEL INTEGER, REGISTRATION_DATE DATE
);

CREATE TABLE ADDRESSES (
   USER_ID INTEGER AUTO_INCREMENT PRIMARY KEY,   -- 主键同时充当外键
   STREET VARCHAR(30) NOT NULL,
   CITY VARCHAR(20) NOT NULL
);
Ch15/spring-data-jdbc3/.../model/User.java
@Table("USERS")
public class User {
    @Id private Long id;
    // . . .
    @MappedCollection(idColumn = "USER_ID")
    private Address address;          // 单值引用 ⇒ 一对一
}

Address 因为对应数据库里另一张表，所以要加 @Table("ADDRESSES")。仓库照旧，两个都是空接口：

15.3.2 嵌入式实体

把 Address 的内容直接嵌进 USERS 表——只有一张表。这对应第 6 章 JPA 的 @Embeddable / @Embedded。

User 里的字段

@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL)
private Address address;

USE_NULL：如果嵌入的 STREET 和 CITY 两列都为空，那么 address 字段就是 null（而不是一个所有属性都为 null 的 Address 对象）。

Address 类

// 注意：没有 @Table 注解！
public class Address {
    private String street;
    private String city;
}

它不再对应数据库里的独立表，全部信息都嵌在 USERS 里，所以不能加 @Table。

怎么判断该用嵌入还是一对一？

回到第 5 章的老问题：这个东西有没有自己的独立身份？地址如果只是「某个用户的地址」，离开用户就没有意义 → 嵌入。如果地址需要被独立查询、独立引用、独立共享 → 独立表。

15.3.3 一对多

一个用户可以有多个地址。类设计上只改一个字（Address → Set<Address>），但表结构变了：ADDRESSES 现在有自己的 ID 主键，外加一个 USER_ID 外键。

Ch15/spring-data-jdbc5/src/main/resources/schema.sql
CREATE TABLE ADDRESSES (
  ID INTEGER AUTO_INCREMENT PRIMARY KEY,
  USER_ID INTEGER,
  STREET VARCHAR(30) NOT NULL,
  CITY VARCHAR(20) NOT NULL,
  FOREIGN KEY (USER_ID) REFERENCES USERS(ID) ON DELETE CASCADE
);
Ch15/spring-data-jdbc5/.../model/User.java
@MappedCollection(idColumn = "USER_ID")
private Set<Address> addresses = new HashSet<>();   // 集合 ⇒ 一对多
Ch15/spring-data-jdbc5/.../repositories/AddressOneToManyRepository.java
public interface AddressOneToManyRepository extends CrudRepository<Address, Long> {

    @Query("SELECT COUNT(*) FROM ADDRESSES WHERE USER_ID = :USER_ID")
    int countByUserId(@Param("USER_ID") Long userId);
}
为什么 countByUserId 明明符合命名规范，却还要写 @Query？

因为查询派生看的是 Java 类上的属性，而 Address 类里根本没有 userId 这个字段——外键只存在于表里，不在对象里。这正是 Spring Data JDBC 与 JPA 的一个根本差异：关联是单向的、从「聚合根」向下的，子对象不持有回指父对象的引用。所以只能手写 SQL。

@Test
void oneToManyTest() {
    assertAll(
        () -> assertEquals(10, userOneToManyRepository.count()),
        () -> assertEquals(20, addressOneToManyRepository.count()),
        () -> assertEquals(2,
              addressOneToManyRepository.countByUserId(users.get(0).getId())));
}

15.3.4 多对多

每个 User 可以有多个 Address，每个 Address 也可以属于多个 User。Spring Data JDBC 没有 @ManyToMany，我们必须手动引入一个对应 USERS_ADDRESSES 中间表的类。

Ch15/spring-data-jdbc6/src/main/resources/schema.sql
DROP TABLE IF EXISTS USERS_ADDRESSES;
DROP TABLE IF EXISTS USERS;
DROP TABLE IF EXISTS ADDRESSES;

CREATE TABLE USERS ( ID INTEGER AUTO_INCREMENT PRIMARY KEY, ACTIVE BOOLEAN,
   USERNAME VARCHAR(30), EMAIL VARCHAR(30), LEVEL INTEGER, REGISTRATION_DATE DATE );

CREATE TABLE ADDRESSES ( ID INTEGER AUTO_INCREMENT PRIMARY KEY,
   STREET VARCHAR(30) NOT NULL, CITY VARCHAR(20) NOT NULL );

CREATE TABLE USERS_ADDRESSES (
  USER_ID INTEGER,
  ADDRESS_ID INTEGER,
  FOREIGN KEY (USER_ID)    REFERENCES USERS(ID)     ON DELETE CASCADE,
  FOREIGN KEY (ADDRESS_ID) REFERENCES ADDRESSES(ID) ON DELETE CASCADE
);
Ch15/spring-data-jdbc6/.../model/User.java 与 UserAddress.java
@Table("USERS")
public class User {
    @Id private Long id;
    // . . .
    @MappedCollection(idColumn = "USER_ID")
    private Set<UserAddress> addresses = new HashSet<>();   // 指向中间类，不是 Address
}

@Table("USERS_ADDRESSES")
public class UserAddress {
    private Long addressId;      // 只存 Address 的 ID

    public UserAddress(Long addressId) { this.addressId = addressId; }
    public Long getAddressId() { return addressId; }
}
为什么 UserAddress 里没有 userId 字段？

因为 USER_ID 列由 User 那边的 @MappedCollection(idColumn = "USER_ID") 负责写入。Spring Data JDBC 把 User 当作聚合根：保存 User 时，它会连带把这个用户的 UserAddress 集合写进 USERS_ADDRESSES，并自动填上 USER_ID。子对象自己不需要（也不应该）持有父 ID。

同理，UserAddressManyToManyRepository.countByUserId 也必须用 @Query 手写 SQL：

public interface UserAddressManyToManyRepository
        extends CrudRepository<UserAddress, Long> {

    @Query("SELECT COUNT(*) FROM USERS_ADDRESSES WHERE USER_ID = :USER_ID")
    int countByUserId(@Param("USER_ID") Long userId);
}

读懂这些断言

10 个用户、3 个地址、20 条关联 —— 每个用户关联 2 个地址（10 × 2 = 20），而 3 个地址被反复共享。这正是多对多的意义：地址实体只存 3 份，却被 10 个用户共同引用。如果用一对多（15.3.3），同样的场景会产生 20 行 ADDRESSES 记录。

时效提醒

Spring Data JDBC 是一个年轻且处于快速发展中的项目，预计近期会加入不少新特性。上表反映的是本书写作时（Spring Data JDBC 2.x 时代）的状态。

什么时候选 Spring Data JDBC

  • 数据模型简单，基本是「表 ↔ 类」一一对应
  • 已经确定了数据库厂商，短期不会换
  • 团队想要可预测的 SQL：每次操作发了哪些语句一眼可见
  • 不想被 LazyInitializationException、n+1、脏检查时机这些问题困扰

什么时候还是选 Spring Data JPA

  • 需要数据库可移植性
  • 领域模型有丰富的双向关联、继承层次
  • 需要二级缓存、延迟加载来撑性能
  • 希望 schema 由实体驱动生成（开发期尤其省事）

本章小结

  • 可以用 Spring Boot 创建并配置一个 Spring Data JDBC 项目，逐步添加查询数据库的方法，并建模不同类型的关系。注意 MySQL 这类非内嵌数据库必须设 spring.sql.init.mode=always，schema.sql 才会执行。
  • 可以按照 Spring Data JDBC 的查询构建器机制（2.0 版本引入）定义并使用一系列查询方法来访问仓库。注意它派生的是原生 SQL，且不支持连接。
  • Spring Data JDBC 的能力包括限制查询结果、排序、分页、流式结果和 @Query 注解。Sort.TypedSort 提供类型安全的排序；流必须关闭；@Query 只支持 @Param 具名参数。
  • 可以创建并使用修改型查询（@Modifying + @Query）来更新和删除实体。delete 方法没有查询派生。
  • 可以用 Spring Data JDBC 建模一对一、一对多、多对多关系以及嵌入式实体：@MappedCollection 的基数由字段是单值还是集合决定；嵌入用 @Embedded(onEmpty = USE_NULL)；多对多必须手写中间类。
  • 子实体不持有回指父实体的外键字段，因此凡是要按外键查询的方法（如 countByUserId）都必须用 @Query 手写 SQL。
