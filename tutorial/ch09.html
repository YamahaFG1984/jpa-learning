第 9 章　高级实体关联映射

本章之所以单独成章，是因为其中不少映射相当罕见、至少是可选的。作者的原话：只用组件映射和多对一（偶尔一对一）关联，你完全可以写出一个精巧的应用而从不映射任何集合。上一章讲的「什么时候才该映射集合」的规则，同样适用于本章的每一个例子。

JPA 2 的重要新特性

① 多对一和一对一关联现在也可以用中间连接/链接表来映射。
② 可嵌入组件类可以拥有指向实体的单向关联，甚至是带集合的多值关联。

运行示例前先执行 Ch09/Ch09.sql。

9.1一对一关联

第 6 章我们说过：User 与 Address 的关系最好用 @Embeddable 组件映射 —— 因为这种情况下生命周期通常是依赖的（UML 里的聚合或组合）。那什么时候需要真正的一对一实体关联？当需要共享引用时：另一个实体类（比如 Shipment）也要引用某个特定的 Address 实例。这时 Address 必须支持共享引用，因而需要自己的标识。

9.1.1　共享主键

源码目录 onetoone-sharedprimarykey

…/onetoone/sharedprimarykey/Address.java
@Entity
public class Address {
    @Id
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    private Long id;
    @NotNull private String street;
    @NotNull private String zipcode;
    @NotNull private String city;
}
…/onetoone/sharedprimarykey/User.java
@Entity @Table(name = "USERS")
public class User {
    @Id
    private Long id;              ❶ 没有标识符生成器 —— 罕见的「应用赋值标识符」场景

    @OneToOne(
        fetch = FetchType.LAZY,   ❷ 覆盖默认的 EAGER
        optional = false,        ❸ User 必须有 shippingAddress
        cascade = CascadeType.ALL ❹ 变更强制级联到 Address
    )
    @PrimaryKeyJoinColumn          ❺ 选定「共享主键」策略
    private Address shippingAddress;

    public User(Long id, String username) { … }  ❻ 公有 API 要求提供 id
}
JPA 规范没有标准化共享主键的生成方式 —— 只能手工做 
Address address = new Address("Flowers Street", "01246", "Boston");
addressRepository.save(address);                       ❶ 先存 Address
User john = new User(address.getId(), "John Smith");   ❷ 取它生成的 id 设给 User
john.setShippingAddress(address);
userRepository.save(john);                             ❸ 再存 User

这个方案有三个问题：

  1. 必须记得先存 Address 再取 id。而这只有在 Address 的标识符生成器能在 INSERT 之前产生值时才可行（§5.2.5）；否则 getId() 返回 null，你无法手工给 User 设标识符。这正是应当优先选择「预插入」生成器的原因之一。
  2. 代理懒加载只在关联「非可选」时才有效——这常让 JPA 新手意外。@OneToOne 默认 EAGER：加载 User 时立刻加载 shippingAddress。概念上，只有当 Hibernate 知道确实存在一个关联的 shippingAddress 时，代理懒加载才有意义；若属性可空，Hibernate 就得去查 ADDRESS 表看值是不是 NULL —— 既然都要查库了，不如直接加载，用代理没有任何好处。（FetchType.LAZY 对提供者只是提示而非要求；可用字节码增强实现可空 @OneToOne 的懒加载，见 §12.1.3。）
  3. 这个一对一关联是单向的，有时需要双向导航。
本章测试代码的结构变化

本章有些例子需要事务性执行，配置类要多加几个注解：

9.1.2　foreign 主键生成器（把双向和自动赋值一起解决）

源码目录 onetoone-foreigngenerator

User.java —— 选它作 mappedBy 的一侧
@Entity @Table(name = "USERS")
public class User {
    @Id @GeneratedValue(generator = Constants.ID_GENERATOR)
    private Long id;

    @OneToOne(
        mappedBy = "user",             // 底层细节由「另一侧」映射
        cascade = CascadeType.PERSIST  // 传递性持久化，方便按正确顺序保存
    )
    private Address shippingAddress;
}

双向映射总是需要一个 mappedBy 侧；选哪边是品味问题，也可能取决于次要需求。持久化 User 时，Hibernate 会顺带持久化 shippingAddress 并自动生成主键。

Address.java —— 特殊的 foreign 生成器
@Entity
public class Address {
    @Id
    @GeneratedValue(generator = "addressKeyGenerator")
    @org.hibernate.annotations.GenericGenerator(
        name = "addressKeyGenerator",
        strategy = "foreign",          // Hibernate 私有
        parameters = @Parameter(name = "property", value = "user"))
    private Long id;

    @OneToOne(optional = false)     // Address 必须引用一个 User
    @PrimaryKeyJoinColumn
    private User user;

    public Address(User user, String street, String zipcode, String city) { … }
}
foreign 生成器做了什么

持久化 Address 实例时，这个特殊生成器会抓取 user 属性的值，取被引用实体实例（User）的标识符值作为自己的主键。§5.2.5 的生成器总览里没提它，因为「共享主键一对一关联」是它唯一的用例。

// 现在存数据简单多了 —— 不再需要调 address.getId() 或 user.getId()
User john = new User("John Smith");
Address address = new Address(john, "Flowers Street", "01246", "Boston");
john.setShippingAddress(address);   // 双向关联必须两侧都链上
userRepository.save(john);          // 传递性持久化 shippingAddress

9.1.3　使用外键连接列

源码目录 onetoone-foreignkey

@Entity @Table(name = "USERS")
public class User {
    @Id @GeneratedValue(generator = Constants.ID_GENERATOR)
    private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false, cascade = CascadeType.PERSIST)
    @JoinColumn(unique = true)          // 默认列名 SHIPPINGADDRESS_ID
    private Address shippingAddress;
}

// 创建、链接、存储都很直接
User john = new User("John Smith");
Address address = new Address("Flowers Street", "01246", "Boston");
john.setShippingAddress(address);
userRepository.save(john);      // 传递性保存 address
为什么 optional=false它不影响加载行为，而是 unique=true 的逻辑后果：如果 SHIPPINGADDRESS_ID 的值对所有用户都必须唯一，那么只能有一个用户「没有收货地址」。因此可空的唯一列通常没有意义。
自引用这个外键约束的源和目标甚至可以是同一张表 —— 称为自引用关系（self-referencing relationship）。

9.1.4　使用连接表（可选一对一）

源码目录 onetoone-jointable

业务场景：托管服务（escrow）

拍卖结束后买卖双方线下约定收货与付款方式，本可不在系统内。但 CaveatEmptor 想提供托管服务：卖家在拍卖结束后创建可追踪的 shipment，买家把钱付给受托方（我们），我们通知卖家钱已到位；货到且买家接受后，我们把钱转给卖家。更进一步：我们还允许用户为任何在拍卖之外、甚至 CaveatEmptor 之外达成的交易创建可追踪的托管 shipment。这就要求 Shipment 与 Item 之间是一个「可选的」一对一关联。

作者的坦白：「我们一度考虑在这一节放弃 CaveatEmptor 例子，因为找不到一个自然的、需要可选一对一关联的场景。如果这个托管例子显得牵强，可以考虑等价的问题：给员工分配工位 —— 那也是一个可选的一对一关系。」

…/onetoone/jointable/Shipment.java
@Entity
public class Shipment {
    @OneToOne(fetch = FetchType.LAZY)          ❶ 懒加载可用，但有个转折，见下
    @JoinTable(                                ❷ 必须指定中间表名
        name = "ITEM_SHIPMENT",
        joinColumns = @JoinColumn(name = "SHIPMENT_ID"),          ❸ 默认 ID
        inverseJoinColumns = @JoinColumn(name = "ITEM_ID",          ❹ 默认 AUCTION_ID
                    nullable = false, unique = true)                ❺ 生成 UNIQUE 约束
    )
    private Item auction;
}
❶ 懒加载的转折加载 Shipment 时，Hibernate 同时查询 SHIPMENT 表和 ITEM_SHIPMENT 连接表 —— 它必须先知道到 Item 的链接是否存在，才能决定用不用代理。这是在一条外连接 SQL 查询里完成的，你不会看到额外的 SQL 语句。如果 ITEM_SHIPMENT 里有对应行，Hibernate 就放一个 Item 占位符。
@JoinTable 隐藏了连接表没有对应的 Java 类，这个注解定义了 ITEM_SHIPMENT 表的列名。Hibernate 还会为连接表的列生成恰当的外键约束。
一对一映射的选择总结

① 如果两个实体中总有一个先被存储、可以充当主键来源 → 用共享主键关联。
② 其他所有情况 → 用外键关联。
③ 当一对一关联是可选的 → 用隐藏的中间连接表。

9.2一对多关联

先记住这条总纲

一对多关联是涉及集合的实体关联中最重要的一种。作者甚至说：当一个简单的双向多对一/一对多就能解决问题时，我们不鼓励使用更复杂的关联样式。而且别忘了：你完全可以不映射任何实体集合 —— 总是可以写显式查询来代替通过迭代的直接访问。

9.2.1　考虑一对多 bag

源码目录 onetomany-bag

@Entity
public class Item {
    @OneToMany(mappedBy = "item")
    private Collection<Bid> bids = new ArrayList<>();
}
// Bid 侧的 @ManyToOne 与表结构都和 §8.3.1 完全一样
// 内存里允许「重复」…
item.addBid(someBid);  item.addBid(someBid);
assertEquals(2, someItem.getBids().size());

// …但重新加载后没有重复
Item item2 = itemRepository.findItemWithBids(item.getId());
assertEquals(1, item2.getBids().size());

// 关键优势：加新元素不必初始化集合
Bid bid = new Bid(new BigDecimal("456.00"), item);
item.addBid(bid);
bidRepository.save(bid);
// 只要不迭代 Collection，就不需要更多查询，
// 新 Bid 的 INSERT 会在不加载全部 bids 的情况下完成。
// 若集合是 Set 或 List，加一个元素就会加载全部元素。

9.2.2　单向与双向 List 映射

源码目录 onetomany-list

Item.java —— 单向 List
@Entity
public class Item {
    @OneToMany                                // 单向：没有 mappedBy 侧
    @JoinColumn(name = "ITEM_ID", nullable = false)
    @OrderColumn(name = "BID_POSITION",       // 默认 BIDS_ORDER
                  nullable = false)
    private List<Bid> bids = new ArrayList<>();
}

BID 表里同时有连接列 ITEM_ID 和顺序列 BID_POSITION；索引从 0 开始且连续。增删移元素时可能执行大量 SQL（§8.1.6）。

Bid.java —— 改成双向
@Entity
public class Bid {
    @ManyToOne
    @JoinColumn(name = "ITEM_ID",
        updatable = false, insertable = false)   ← 关键
    @NotNull
    private Item item;
}
为什么不是 @ManyToOne(mappedBy="bids")？

@ManyToOne 根本没有 mappedBy 属性 —— 它永远是关系的「拥有」侧。如果 Bid#item 是拥有侧，Hibernate 存数据时会忽略集合、不写元素索引。所以要把 @JoinColumn 映射两次，并在 @ManyToOne 侧用 updatable=false, insertable=false 禁写。这样 Hibernate 存数据时才会考虑集合侧（含每个元素的索引），而 @ManyToOne 实际上变成只读的，效果等同于有 mappedBy。

两条配套规则

① Hibernate 的 schema 生成器总是依赖 @ManyToOne 侧的 @JoinColumn。所以想要正确的 schema，要在这一侧加 @NotNull 或声明 @JoinColumn(nullable=false)。只要有 @ManyToOne，生成器就会忽略 @OneToMany 侧及其连接列。

② 真实应用里不要用 List 映射这个关联。「在数据库里保序」看着像常见需求，其实用处不大：有时要最高价在前、有时最新出价在前、有时只看某用户的出价、有时只看某时间段 —— 这些操作都不需要持久化的列表索引。而且维护索引可能很昂贵、触发大量 SQL。用 @ManyToOne 映射外键连接列，然后把集合丢掉。

9.2.3　可选的一对多 + 连接表

源码目录 onetomany-jointable

User.java —— 常规的只读反向侧
@Entity @Table(name = "USERS")
public class User {
    @OneToMany(mappedBy = "buyer")
    private Set<Item> boughtItems = new HashSet<>();
}
Item.java —— 实际映射在 mappedBy 那一侧
@Entity
public class Item {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinTable(name = "ITEM_BUYER",
        joinColumns = @JoinColumn(name = "ITEM_ID"),
        inverseJoinColumns = @JoinColumn(nullable = false))  // 默认 BUYER_ID
    private User buyer;
}

Item 未被买下时，ITEM_BUYER 里就没有对应行 —— 关系因此是可选的。schema 里没有任何棘手的可空列。不过仍应写一个过程式约束和 INSERT 触发器：「只有当该 item 的拍卖结束时间已到、且该用户是最高出价者时，才允许插入 buyer。」

9.2.4　可嵌入类中的一对多关联

源码目录 onetomany-embeddable / onetomany-embeddable-jointable

方案 A：@JoinColumn
@Embeddable
public class Address {
    // street / zipcode / city …
    @OneToMany
    @JoinColumn(name = "DELIVERY_ADDRESS_USER_ID",   // 默认 DELIVERIES_ID
                nullable = false)
    private Set<Shipment> deliveries = new HashSet<>();
}

这个外键列在 SHIPMENT 表里。可嵌入组件没有自己的标识符，所以外键列里的值是嵌入了这个 Address 的 User 的标识符。这里声明 nullable=false，所以 Shipment 必须有关联的收货地址。无法双向导航：Shipment 不能引用 Address，因为嵌入组件不能有共享引用。

方案 B：@JoinTable（关联可选且不想要可空列）
@Embeddable
public class Address {
    @OneToMany
    @JoinTable(
        name = "DELIVERIES",                       // 默认 USERS_SHIPMENT
        joinColumns = @JoinColumn(name = "USER_ID"),  // 默认 USERS_ID
        inverseJoinColumns = @JoinColumn(name = "SHIPMENT_ID"))  // 默认 SHIPMENTS_ID
    private Set<Shipment> deliveries = new HashSet<>();
}
两个默认与一条限制

① 既不声明 @JoinTable 也不声明 @JoinColumn 时，可嵌入类里的 @OneToMany 默认走连接表策略。

② 在拥有者实体类里，用 @AttributeOverride 覆盖嵌入类的属性映射（§6.2.3）；想覆盖嵌入类中实体关联的连接表或连接列，用 @AssociationOverride。但不能切换映射策略 —— 用连接表还是连接列，由可嵌入组件类里的映射决定。

9.3多对多与三元关联

作者的经验之谈（非常重要）

「真实系统里我们可能根本不会有多对多关联 —— 我们的经验是，几乎总有其他信息必须附着在关联实例之间的每条链接上。」例如：某个 Item 被加入某个 Category 的时间戳，以及创建该链接的 User。

9.3.1　常规的单向/双向多对多

源码目录 manytomany-bidirectional

@Entity
public class Category {
    @ManyToMany(cascade = CascadeType.PERSIST)
    @JoinTable(
        name = "CATEGORY_ITEM",
        joinColumns = @JoinColumn(name = "CATEGORY_ID"),
        inverseJoinColumns = @JoinColumn(name = "ITEM_ID"))
    private Set<Item> items = new HashSet<>();
}

@Entity
public class Item {
    @ManyToMany(mappedBy = "items")   // 实际上只读
    private Set<Category> categories = new HashSet<>();
}

链接表 CATEGORY_ITEM 有两列，各带外键约束；主键是两列的复合键 —— 同一对 Category/Item 只能链接一次，但同一个 item 可以链到多个类别。

为什么 ALL / REMOVE / orphan removal 对多对多没有意义？

书里把这留作一道自测题，用来检验你是否真的理解了实体与值类型。提示：想想「删一条记录会自动删掉一条相关记录」会发生什么 —— 删掉一个 Category 就会删掉里面的 Item，而那些 Item 还被其他 Category 共享引用着。

能用 List 或 bag 吗Set 与 schema 完美匹配（不可能有重复链接）。bag 意味着重复元素，需要连接表有不同的主键（可用 Hibernate 私有的 @CollectionId，§8.1.5）—— 但如果真要支持重复链接，后面几种策略是更好的选择。
索引集合的限制可以用常规 @ManyToMany 映射 List，但只能在一侧。双向关系里必有一侧被「mapped by」，其值在同步到数据库时被忽略；两侧都是 list 时，只能持久化其中一侧的索引。

9.3.2　多对多 + 中间实体　作者推荐的默认做法

源码目录 manytomany-linkentity

为什么把这作为默认

「我们总是可以把多对多关联表示成指向一个中间类的两个多对一关联。这个模型通常更容易扩展，所以我们倾向于不在应用中使用常规多对多关联。等到链接表不可避免地要加列时再改代码是件很费劲的事 —— 因此在照上一节那样映射 @ManyToMany 之前，请先考虑这个替代方案。」

…/manytomany/linkentity/CategorizedItem.java
@Entity
@Table(name = "CATEGORY_ITEM")
@org.hibernate.annotations.Immutable          ❶ 不可变实体：Hibernate 可优化，如刷新时跳过脏检查
public class CategorizedItem {

    @Embeddable                                ❷ 复合主键封装成静态嵌套可嵌入类（也可外置成独立文件）
    public static class Id implements Serializable {
        @Column(name = "CATEGORY_ID") private Long categoryId;
        @Column(name = "ITEM_ID")     private Long itemId;
        // 无参构造器、有参构造器、equals / hashCode
    }

    @EmbeddedId                                ❸ 把标识符属性及其复合键列映射到实体表
    private Id id = new Id();

    @Column(updatable = false) @NotNull
    private String addedBy;                    ❹ 关于链接的「额外信息」

    @Column(updatable = false) @NotNull @CreationTimestamp
    private LocalDateTime addedOn;             ❺

    @ManyToOne
    @JoinColumn(name = "CATEGORY_ID", insertable = false, updatable = false)   ❻
    private Category category;

    @ManyToOne
    @JoinColumn(name = "ITEM_ID", insertable = false, updatable = false)       ❼
    private Item item;

    public CategorizedItem(String addedByUsername, Category category, Item item) {
        this.addedBy = addedByUsername;
        this.category = category;   this.item = item;
        this.id.categoryId = category.getId();     ❽ 复合键值永远由应用赋值，Hibernate 不生成
        this.id.itemId = item.getId();
        category.addCategorizedItem(this);        ❾ 管理两侧集合，保证引用完整性
        item.addCategorizedItem(this);
    }
}
❻❼ 这个技巧必须理解

category / item 这两个 @ManyToOne 属性已经在标识符里被映射过了。技巧在于把它们设为只读（updatable=false, insertable=false）：Hibernate 写这两列的值时取自 CategorizedItem 的标识符值；与此同时你仍能通过 getItem() / getCategory() 读取和浏览关联实例。如果同一列被映射两次却没有一个设为只读，Hibernate 启动时会报「重复列映射」错误。

// 需要双向导航时，在两侧各映射一个 @OneToMany
@Entity public class Category {
    @OneToMany(mappedBy = "category")
    private Set<CategorizedItem> categorizedItems = new HashSet<>();
}
@Entity public class Item {
    @OneToMany(mappedBy = "item")
    private Set<CategorizedItem> categorizedItems = new HashSet<>();
}
// 创建链接：先各自持久化，再 new 一个 CategorizedItem
categoryRepository.save(someCategory);
categoryRepository.save(otherCategory);
itemRepository.save(someItem);
itemRepository.save(otherItem);

CategorizedItem linkOne = new CategorizedItem("John Smith", someCategory, someItem);
CategorizedItem linkTwo = new CategorizedItem("John Smith", someCategory, otherItem);
categorizedItemRepository.save(linkOne);
categorizedItemRepository.save(linkTwo);
// 断开链接 = 删掉那个 CategorizedItem
优点缺点
中间实体可以双向导航：someCategory.getCategorizedItems() 和 someItem.getCategorizedItems() 都行管理 CategorizedItem 实例（独立保存与删除）的代码更复杂；还需要复合标识符之类的基础设施。小改进：在部分关联上开启 CascadeType.PERSIST 以减少 save() 调用
顺便：什么是三元关联

本例把创建链接的用户存成了一个简单的名字字符串。如果连接表改成有一个 USER_ID 外键列，就变成了三元关系 —— CategorizedItem 会对 Category、Item、User 各有一个 @ManyToOne。

9.3.3　用组件实现三元关联

源码目录 manytomany-ternary　把链接映射成可嵌入组件类，是比中间实体可能更简单的替代方案。

CategorizedItem.java —— 这次是 @Embeddable
@Embeddable
public class CategorizedItem {
    @ManyToOne
    @JoinColumn(name = "ITEM_ID",
        nullable = false, updatable = false)
    private Item item;

    @ManyToOne
    @JoinColumn(name = "USER_ID", updatable = false)
    @NotNull                          ← 关键技巧，见右
    private User addedBy;

    @Column(updatable = false)
    @NotNull
    private LocalDateTime addedOn = LocalDateTime.now();
}

@Entity
public class Category {
    @ElementCollection
    @CollectionTable(name = "CATEGORY_ITEM",
        joinColumns = @JoinColumn(name = "CATEGORY_ID"))
    private Set<CategorizedItem> categorizedItems = new HashSet<>();
}
这个映射并不完美

映射可嵌入类型的 @ElementCollection 时，目标类型中所有 nullable=false 的属性都会成为（复合）主键的一部分。我们希望 CATEGORY_ITEM 的所有列都 NOT NULL，但只有 CATEGORY_ID 和 ITEM_ID 应该进主键。

技巧：对不该进主键的属性用 Bean Validation 的 @NotNull —— 因为是可嵌入类，Hibernate 在实现主键和生成 SQL schema 时会忽略 Bean Validation 注解。

代价：生成的 schema 在 USER_ID 和 ADDEDON 列上不会有恰当的 NOT NULL 约束，需要手工修正。

优点：链接组件的隐式生命周期

创建关联 = 往集合里加一个新的 CategorizedItem；断开链接 = 从集合里移除元素。不需要任何额外的级联设置，Java 代码更简单（虽然行数多一些）。

限制：无法双向导航

可嵌入组件按定义不能有共享引用，所以不能从 Item 导航到 CategorizedItem，Item 里也没有这个链接的映射。改用查询：

@Query("select c from Category c join c.categorizedItems ci " +
       "where ci.item = :itemParameter")
List<Category> findCategoryWithCategorizedItems(
      @Param("itemParameter") Item itemParameter);

9.4使用 Map 的实体关联

Map 的键和值都可以是指向其他实体的引用，这提供了映射多对多与三元关系的又一种策略。

9.4.1　一对多 + 属性作键

源码目录 maps-mapkey

@Entity
public class Item {
    @MapKey(name = "id")              // 用目标实体的某个属性作 map 的键
    @OneToMany(mappedBy = "item")
    private Map<Long, Bid> bids = new HashMap<>();
}

// 遍历时得到 (1, <PK=1 的 Bid 引用>), (2, <PK=2 的 Bid 引用>)…
for (Map.Entry<Long, Bid> entry : item.getBids().entrySet()) {
    assertEquals(entry.getKey(), entry.getValue().getId());
}
底层表毫无特别就是 ITEM 和 BID 表，BID 里有 ITEM_ID 外键列 —— 与 §8.3.1 用普通集合的一对多/多对一完全相同的 schema。动机只是在应用里换一种数据表示方式。
@MapKey 的默认值省略 name 时默认用目标实体的标识符属性，所以上面的 name="id" 是冗余的。
唯一性由你保证map 的键构成一个 set，所以值必须唯一。Bid 主键满足，但 Bid 的其他属性多半不满足 —— Hibernate 不会检查，得你自己确保。
用例主要且罕见的用例是：用条目实体值的某个属性作为 map 的键来遍历，也许只是因为这样渲染数据更方便。

9.4.2　键/值三元关系

源码目录 maps-ternary　键是 Item，值是把该 Item 加入该 Category 的 User。

@Entity
public class Category {
    @ManyToMany(cascade = CascadeType.PERSIST)
    @MapKeyJoinColumn(name = "ITEM_ID")   // 可选；默认列名 ITEMADDEDBY_KEY
    @JoinTable(
        name = "CATEGORY_ITEM",
        joinColumns = @JoinColumn(name = "CATEGORY_ID"),
        inverseJoinColumns = @JoinColumn(name = "USER_ID"))
    private Map<Item, User> itemAddedBy = new HashMap<>();
}

// 三个实体都必须已是持久态，然后放进 map
someCategory.putItemAddedBy(someItem, someUser);
someCategory.putItemAddedBy(otherItem, someUser);
otherCategory.putItemAddedBy(someItem, someUser);
// 断开链接 = 从 map 中移除条目
但要记住

它管理了一个复杂关系、隐藏了一张三列的链接表。但实践中链接表往往会长出新列，如果你的代码依赖 Map API，之后修改全部 Java 代码的代价很高。前面我们有个记录链接创建时间的 ADDEDON 列，为了这个映射不得不把它去掉。

本章小结

  • 复杂实体关联可用一对一、一对多、多对多、三元关联以及基于 Map 的实体关联来映射。
  • 一对一可通过：共享主键、foreign 主键生成器、外键连接列、连接表来实现。选择依据：总有一方先存 → 共享主键；其他情况 → 外键；关联可选 → 连接表。
  • 一对多可考虑：一对多 bag（最佳反向集合）、单向与双向 list 映射（谨慎）、可选一对多 + 连接表、可嵌入类中的一对多。
  • 可以创建单向与双向多对多，以及带中间实体的多对多。
  • 可以用组件构建三元关联，以及用 Map 实现实体关联。
  • 多对多实体关联通常最好表示成：来自一个中间实体类的两个多对一关联，或一个组件集合。
  • 尝试复杂集合映射之前，务必确认你真的需要一个集合。问问自己：会频繁遍历它的元素吗？
  • 本章用到的 Java 结构有时让数据访问更容易，但通常让数据的存储、更新与删除变得复杂。
