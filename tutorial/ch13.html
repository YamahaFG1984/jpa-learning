13.1级联状态转换

默认不启用

实体实例状态变化时，关联实体实例也可能被纳入这次状态转换。这种级联默认是不启用的 —— 每个实体实例有独立的生命周期。但对某些实体间关联，我们希望实现细粒度的生命周期依赖。§8.3 已经讲过 PERSIST、REMOVE、orphanRemoval 与数据库级 ON DELETE；本节讲其余那些较少用到的选项。

13.1.1　可用的级联选项

选项说明（注意每一项都对应一个 EntityManager 或 Session 操作）
CascadeType.PERSIST用 persist() 存储实体实例时，刷新时任何关联实体实例也被持久化
CascadeType.REMOVE用 remove() 删除实体实例时，刷新时任何关联实体实例也被删除
CascadeType.DETACH用 detach() 从上下文逐出实体实例时，任何关联实体实例也被游离
CascadeType.MERGE用 merge() 把瞬时或游离实例合并进上下文时，任何关联的瞬时/游离实例也被合并
CascadeType.REFRESH用 refresh() 刷新持久实例时，任何关联的持久实体实例也被刷新
CascadeType.REPLICATE用 Session#replicate() 把游离实例复制进数据库时，任何关联的游离实例也被复制
CascadeType.ALL为该映射关联启用全部级联选项的简写

org.hibernate.annotations.CascadeType 枚举里还定义了更多选项，但如今唯一有意思的只有 REPLICATE 及 Session#replicate() —— 其他 Session 操作在 EntityManager API 上都有标准化的等价物或替代品，可以忽略。

13.1.2　传递性游离与合并

@Entity
public class Item {
    @OneToMany(mappedBy = "item",
               cascade = {CascadeType.DETACH, CascadeType.MERGE})
    private Set<Bid> bids = new HashSet<>();
}

// ① 加载并初始化集合，然后级联游离
Item item = em.find(Item.class, ITEM_ID);
assertEquals(2, item.getBids().size());   // 访问 getBids() 触发懒初始化
em.detach(item);   // 级联：Item 及集合中所有已加载的 bid 都被逐出上下文
                   // （没加载的 bid 不会被游离；当然也可以直接 close() 游离一切）

// ② 游离态下修改并新增
item.setName("New Name");
Bid bid = new Bid(new BigDecimal("101.00"), item);
item.addBid(bid);

// ③ 在新上下文中合并
Item mergedItem = em.merge(item);
// select i.*, b.* from ITEM i left outer join BID b on i.ID = b.ITEM_ID where i.ID = ?
for (Bid b : mergedItem.getBids()) assertNotNull(b.getId());  // 新 Bid 已被赋予标识符
em.flush();
// update ITEM set NAME = ? where ID = ?
// insert into BID values (?, ?, ?, …)
游离态下务必重写 equals() / hashCode()

因为在处理游离实体状态与集合（§10.3），必须格外注意标识与相等性：

@Entity
public class Bid {
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (o instanceof Bid bid)
            return Objects.equals(id, bid.id)
                && Objects.equals(amount, bid.amount)
                && Objects.equals(item, bid.item);
        return false;
    }
    @Override public int hashCode() { return Objects.hash(id, amount, item); }
}
// 两个 Bid 相等：id 相同、金额相同、且关联同一个 Item
合并时会急切抓取关联 —— 一个容易忽视的行为

只要关联启用了 CascadeType.MERGE，Hibernate 在合并时总是用 JOIN 急切加载实体关联。

对上面这种「bids 已初始化、已游离、已修改」的场景，这是聪明且必要的最优做法。但如果你合并的 Item 带着未初始化的 bids 集合或 seller 代理，Hibernate 同样会用 JOIN 把它们抓过来 —— merge 会在它返回的受管 Item 上把这些关联初始化掉。

CascadeType.MERGE 会让 Hibernate 忽略并实际覆盖任何 FetchType.LAZY 映射（JPA 规范允许这样做）。

merge 的内部流程

先检查持久化上下文中是否已有该标识符值的实体；没有就从数据库加载。Hibernate 足够聪明，知道合并时也会需要被引用的实体，于是在同一条 SQL 里把它们一起取出来。刷新上下文时，它检测合并过程中哪些属性发生了变化。「级联合并 + 集合」是个强大特性 —— 想想没有 Hibernate 时要写多少代码才能实现同样的功能。」

13.1.3　级联刷新

@Entity @Table(name = "USERS")
public class User {
    @OneToMany(cascade = {CascadeType.PERSIST, CascadeType.REFRESH})
    @JoinColumn(name = "USER_ID", nullable = false)
    private Set<BillingDetails> billingDetails = new HashSet<>();
}

// PERSIST：把 BillingDetails 加进一个已持久 User 的集合，它就变持久 —— 简化了存储
// REFRESH：重新加载 User 状态时，Hibernate 也刷新链接到它的每个 BillingDetails
User user = em.find(User.class, USER_ID);
assertEquals(2, user.getBillingDetails().size());   // 遍历或 size() 触发懒集合初始化
// …别人在数据库里改了账单信息…
em.refresh(user);
// select * from CREDITCARD  join BILLINGDETAILS where ID = ?      ← 每个实例一条
// select * from BANKACCOUNT join BILLINGDETAILS where ID = ?
// select * from USERS left outer join BILLINGDETAILS
//                     left outer join CREDITCARD
//                     left outer join BANKACCOUNT where ID = ?    ← 再整体重载集合以发现新增的
这是 Hibernate 「不够聪明」的一处

它先为上下文中被集合引用的每个 BillingDetails 实例执行一条 SQL SELECT，然后又把整个集合重新加载一遍以找出新增的 BillingDetails。Hibernate 显然可以用一条 SELECT 做完。另外：如果这些实例在数据库中已不存在，会抛 EntityNotFoundException。

要复现这个例子必须注意隔离级别

我们想在另一个事务修改了记录之后刷新它。MySQL 的默认事务隔离级别是 REPEATABLE_READ，而大多数其他数据库是 READ_COMMITTED。第一个事务要能看到第二个事务提交的改动，就必须在 JDBC 驱动上改隔离级别：

<property name="javax.persistence.jdbc.url"
  value="jdbc:mysql://localhost:3306/CH13_CASCADE?sessionVariables=transaction_isolation='READ-COMMITTED'&amp;serverTimezone=UTC"/>

因为改动只发生在配置层面，只要 persistence.xml 配置正确，代码在不同数据库上都能继续正常工作。

13.1.4　级联复制

@Entity
public class Item {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "SELLER_ID", nullable = false)
    @org.hibernate.annotations.Cascade(
        org.hibernate.annotations.CascadeType.REPLICATE)   // Hibernate 注解
    private User seller;
}

// ① 从源数据库加载 Item 及其 seller，然后关闭上下文 → 二者都变游离
Item item = em.find(Item.class, ITEM_ID);
assertNotNull(item.getSeller().getUsername());   // 懒初始化 seller

// ② 连到另一个数据库，写入游离数据
otherDatabase.unwrap(Session.class).replicate(item, ReplicationMode.OVERWRITE);
// select ID from ITEM  where ID = ?     ← 先查目标库里是否已存在
// select ID from USERS where ID = ?
otherDatabase.getTransaction().commit();
// update ITEM  set NAME = ?, SELLER_ID = ?, … where ID = ?    ← 已存在 → UPDATE 覆盖
// update USERS set USERNAME = ?, …            where ID = ?
// （目标库若没有这些行，则执行两条 INSERT）

13.2监听与拦截事件

13.2.1　JPA 事件监听器与回调方法

独立的实体监听器类
public class PersistEntityListener {
    @PostPersist
    public void logMessage(Object entityInstance) {   // ← 有一个参数
        User currentUser = CurrentUser.INSTANCE.get();
        Log log = Log.INSTANCE;
        log.save("Entity instance persisted by "
            + currentUser.getUsername() + ": " + entityInstance);
    }
}

@Entity
@EntityListeners(PersistEntityListener.class)   // 可传数组；多个监听器按声明顺序调用
public class Item { … }
或直接写在实体类上
@Entity @Table(name = "USERS")
public class User {
    @PostPersist
    public void logMessage() {            // ← 没有参数，当前实体就是 this
        …log.save("…" + this);
    }
}
上下文信息怎么拿实体监听器是无状态的，由 JPA 引擎自动创建和销毁 —— 因此需要更多上下文信息时会比较困难。书中示例用的是线程局部变量 + 单例这种原始方案（CurrentUser、Log）。
回调注解触发时机
@PostLoad实体实例被加载进持久化上下文之后 —— 无论是按标识符查找、通过导航与代理/集合初始化，还是通过查询。刷新一个已持久实例之后也会调用
@PrePersist对实体实例调 persist() 时立即调用。merge() 发现实体是瞬时的、把瞬时状态拷进持久实例之后也会调用。启用 CascadeType.PERSIST 时，关联实体也会被调用
@PostPersist使实体持久化的数据库操作执行完并已分配标识符值之后。这可能发生在 persist()/merge() 时，也可能晚到上下文刷新时（若标识符生成器不是「预插入」型，§5.2.5）
@PreUpdate / @PostUpdate持久化上下文与数据库同步（即刷新）之前与之后。只有当实体状态确实需要同步时才触发（例如它被认为变脏了）
@PreRemove / @PostRemove调 remove() 或实例被级联删除时触发；以及上下文刷新、数据库记录删除之后
回调方法的六条约束
  1. 实体监听器类必须有隐式或显式的 public 无参构造器；不必实现任何特殊接口。
  2. 监听器类中的回调方法有单个 Object 参数；只为特定实体类型启用时，可以把参数声明为该具体类型。实体类自身的回调方法没有参数。
  3. 访问修饰符任意（不必 public），但不能是 static 或 final，且不返回任何值。
  4. 回调方法抛出未受检的 RuntimeException → Hibernate 中止操作并把当前事务标记为回滚；抛出受检 Exception → Hibernate 把它包装成 RuntimeException 处理。
  5. 同一个类里每个回调注解只能用一次（不能有两个 @PostPersist）；但可以在多个监听器类中、或监听器 + 实体类中同时拦截同一个事件。
  6. 可以在实体超类上加回调方法作用于整个层次。用 @ExcludeSuperclassListeners 为某个子类禁用超类回调；用 @ExcludeDefaultListeners 为某个实体禁用默认监听器。

13.2.2　实现 Hibernate 拦截器（写审计日志）

需求

把数据修改的审计日志写进另一张数据库表：记录 用户、事件的日期时间、发生了什么类型的事件、被改动 Item 的标识符。「审计日志常常用数据库触发器处理。但有时让应用来负责更好 —— 尤其是需要在不同数据库之间保持可移植性时。」

public class AuditLogInterceptor extends EmptyInterceptor {
    private Session currentSession;
    private Long currentUserId;
    private Set<Auditable> inserts = new HashSet<>();
    private Set<Auditable> updates = new HashSet<>();

    public boolean onSave(Object entity, Serializable id, Object[] state,
                           String[] propertyNames, Type[] types) {   // 实体变持久时调用
        if (entity instanceof Auditable aud) inserts.add(aud);
        return false;                                             // state 未被修改
    }

    public boolean onFlushDirty(Object entity, Serializable id, Object[] currentState,
            Object[] previousState, String[] propertyNames, Type[] types) {  // 刷新时发现变脏
        if (entity instanceof Auditable aud) updates.add(aud);
        return false;                                             // currentState 未被修改
    }

    public void postFlush(Iterator iterator) {
        Session tempSession = currentSession.sessionWithOptions()
                                 .connection().openSession();         // 共用事务与连接的临时 Session
        try {
            for (Auditable e : inserts)
                tempSession.persist(new AuditLogRecord("insert", e, currentUserId));
            for (Auditable e : updates)
                tempSession.persist(new AuditLogRecord("update", e, currentUserId));
            tempSession.flush();
        } finally {
            tempSession.close();  inserts.clear();  updates.clear();   // 独立于原 Session 刷新并关闭
        }
    }
}

// 还要给拦截器配上当前 Session 和登录用户 —— 需要一些到 Hibernate API 的类型转换
AuditLogInterceptor interceptor =
    (AuditLogInterceptor) ((SessionImplementor) session).getInterceptor();
interceptor.setCurrentSession(session);
interceptor.setCurrentUserId(CURRENT_USER_ID);

13.2.3　核心事件系统

Hibernate 核心引擎本身就建立在「事件 + 监听器」模型上

需要保存实体实例时，它触发一个事件；监听该类事件的人可以捕获它并负责保存数据。因此 Hibernate 把它的全部核心功能实现为一组默认监听器，处理所有 Hibernate 事件。

Hibernate 的设计是开放的：你可以写并启用自己的监听器 —— 替换已有的默认监听器，或扩展它们并执行副作用/额外流程。替换事件监听器很罕见，那意味着你自己的实现要接管 Hibernate 的一块核心功能。

本质上 Session（及其更窄的表亲 EntityManager）的所有方法都对应一个事件：find() 和 load() 触发 LoadEvent，默认由 DefaultLoadEventListener 处理。

public class SecurityLoadListener extends DefaultLoadEventListener {
    public void onLoad(LoadEvent event, LoadType loadType) {
        boolean authorized = MySecurity.isAuthorized(
                event.getEntityClassName(), event.getEntityId());
        if (!authorized)
            throw new MySecurityException("Unauthorized access");
        super.onLoad(event, loadType);
    }
}
// persistence.xml 中按事件类型启用
<property name="hibernate.ejb.event.load"
   value="com.manning…filtering.SecurityLoadListener"/>

属性名总是以 hibernate.ejb.event 开头，后跟要监听的事件类型（全部类型见 org.hibernate.event.spi.EventType）。属性值可以是逗号分隔的监听器类名列表，Hibernate 按指定顺序逐个调用。

监听器应视为单例

它在多个持久化上下文之间共享，因此不应把任何与事务相关的状态保存为实例变量。所有事件与监听器接口见 org.hibernate.event 包的 Javadoc。

13.3用 Hibernate Envers 做审计与版本化

Envers 是 Hibernate 套件中专注于审计日志与在数据库中保存多版本数据的项目 —— 类似你熟悉的 Subversion、Git 这类版本控制系统。

启用（把 JAR 放到 classpath 上即可，无需额外配置）
@Entity
@org.hibernate.envers.Audited          // 为整个实体启用审计
public class Item {
    @NotNull private String name;

    @OneToMany(mappedBy = "item")
    @org.hibernate.envers.NotAudited    // 排除某个属性
    private Set<Bid> bids = new HashSet<>();

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "SELLER_ID", nullable = false)
    private User seller;                  // seller 会被审计
}
// 还必须在 User 类上也加 @Audited
代价

「一旦启用，因为它基于注解，用起来很容易，让你几乎不费力就能在数据库里保存多版本数据。代价是它会创建大量额外的表（不过你可以控制想审计哪些表）。」

三次事务后，Envers 记下三个变更集
// ① 创建
User user = new User("johndoe");   em.persist(user);
Item item = new Item("Foo", user);  em.persist(item);

// ② 修改
Item item = em.find(Item.class, ITEM_ID);
item.setName("Bar");
item.getSeller().setUsername("doejohn");

// ③ 删除
em.remove(em.find(Item.class, ITEM_ID));
找到修订号：AuditReader 是主 API
AuditReader auditReader = AuditReaderFactory.get(em);

// 有时间戳 → 找该时刻或之前所做变更集的修订号
Number revCreate = auditReader.getRevisionNumberForDate(TIMESTAMP_CREATE);
Number revUpdate = auditReader.getRevisionNumberForDate(TIMESTAMP_UPDATE);
Number revDelete = auditReader.getRevisionNumberForDate(TIMESTAMP_DELETE);

// 没时间戳 → 拿某实体涉及的全部修订号
List<Number> itemRevisions = auditReader.getRevisions(Item.class, ITEM_ID);
assertEquals(3, itemRevisions.size());   // 创建、修改、删除
List<Number> userRevisions = auditReader.getRevisions(User.class, USER_ID);
assertEquals(2, userRevisions.size());   // 创建、修改

// 有修订号 → 拿 Envers 记录该变更集的时间戳
Date ts = auditReader.getRevisionDate(itemRevision);
既不知道时间戳也不知道修订号时：用查询探索审计日志（也适合在 UI 上列出所有变更集）
AuditQuery query = auditReader.createQuery()
    .forRevisionsOfEntity(Item.class, false, false);
List<Object[]> result = query.getResultList();      // 每个元组三个元素 ↓
for (Object[] tuple : result) {
    Item item                      = (Item) tuple[0];                    // 该修订下的实体实例
    DefaultRevisionEntity revision = (DefaultRevisionEntity) tuple[1];   // 修订详情（号 + 时间戳）
    RevisionType revisionType      = (RevisionType) tuple[2];            // 修订类型

    if (revision.getId() == 1) { assertEquals(RevisionType.ADD, revisionType); assertEquals("Foo", item.getName()); }
    else if (revision.getId() == 2) { assertEquals(RevisionType.MOD, revisionType); assertEquals("Bar", item.getName()); }
    else if (revision.getId() == 3) { assertEquals(RevisionType.DEL, revisionType); assertNull(item); }
}
// 修订号是顺序递增的：更高的修订号总是实体实例更近的版本
按修订号访问历史数据
Item item = auditReader.find(Item.class, ITEM_ID, revCreate);
assertEquals("Foo", item.getName());
assertEquals("johndoe", item.getSeller().getUsername());  // seller 自动一起取回

Item modified = auditReader.find(Item.class, ITEM_ID, revUpdate);
assertEquals("Bar", modified.getName());

Item deleted = auditReader.find(Item.class, ITEM_ID, revDelete);
assertNull(deleted);                     // 该修订中 Item 被删除 → 返回 null

User user = auditReader.find(User.class, USER_ID, revDelete);
assertEquals("doejohn", user.getUsername());  // 该修订没改 User → 返回最接近的历史修订
返回的实例不是持久态

AuditReader#find() 像 EntityManager#find() 一样只取回单个实例，但返回的实体实例不受持久化上下文管理。修改一个旧版本的 Item，Hibernate 不会更新数据库。把 AuditReader API 返回的实例视为游离的、只读的。

任意查询（类似原生 Criteria API）与投影
AuditQuery query = auditReader.createQuery()
    .forEntitiesAtRevision(Item.class, revUpdate);   // 限定到某个修订/变更集
query.add(AuditEntity.property("name").like("Ba", MatchMode.START));
query.add(AuditEntity.relatedId("seller").eq(USER_ID));   // 限制条件可含实体关联
query.addOrder(AuditEntity.property("name").desc());       // 排序
query.setFirstResult(0);  query.setMaxResults(10);           // 大结果集分页

// 投影：只取某个版本的 Item#name
query.addProjection(AuditEntity.property("name"));
assertEquals("Bar", (String) query.getSingleResult());
回滚到旧版本：用 replicate() 覆盖现有行
User user = auditReader.find(User.class, USER_ID, revCreate);
em.unwrap(Session.class).replicate(user, ReplicationMode.OVERWRITE);
em.flush();  em.clear();
user = em.find(User.class, USER_ID);
assertEquals("johndoe", user.getUsername());
// Envers 会把这次改动也当作一次 update 记进审计日志 —— 它只是 User 的又一个新修订

13.4动态数据过滤器

问题场景

你不想让当前登录用户看到数据库里的全部数据。通常做法是给查询加条件、动态限制结果；但如果要处理的是「安全」这种横切关注点，就会很麻烦 —— 你得改造应用里的大多数查询。Hibernate 的动态数据过滤器可以把这些限制集中化、隔离出来。

本例业务规则：User 有一个 ranking（整数）属性。用户只能对等级 ≤ 自己的其他用户所出售的商品出价 —— 业务上就是若干个由任意等级数字定义的用户组，用户只能与同级或更低级的人交易。

① 定义　…/dynamic/package-info.java
@org.hibernate.annotations.FilterDef(
    name = "limitByUserRanking",
    parameters = {
        @org.hibernate.annotations.ParamDef(
            name = "currentUserRanking", type = "int")
    })
② 应用到实体类　…/dynamic/Item.java
@Entity
@org.hibernate.annotations.Filter(
    name = "limitByUserRanking",
    condition = """
        :currentUserRanking >= (
                 select u.RANKING from USERS u
                 where u.ID = SELLER_ID
            )""")
public class Item { … }

条件是直接透传给数据库系统的 SQL 表达式，因此可以用任何 SQL 运算符或函数。它必须在记录应当通过过滤时求值为 true。这里用子查询取卖家等级；未限定的列名（如 SELLER_ID）指的是该实体类所映射的表的列。

其他优秀用例：按任意安全相关条件限制数据访问（用户等级、必须属于的用户组、被赋予的角色）；数据带地区编码（如某销售团队的全部业务联系人）；或每个销售人员只处理覆盖自己区域的数据。

本章小结

  • 级联状态转换是持久化引擎中对生命周期事件的预定义反应；除了 PERSIST/REMOVE，还有传递性游离与合并、级联刷新与级联复制。注意 CascadeType.MERGE 会覆盖 FetchType.LAZY。
  • 可以实现事件监听器与拦截器，在 Hibernate 加载和存储数据时加入自定义逻辑：JPA 标准回调（简单但上下文信息少）→ org.hibernate.Interceptor（灵活，大多数时候够用）→ 核心事件 SPI（可替换引擎的任意一块）。
  • 可以用 Hibernate Envers 做审计日志并在数据库中保存多版本数据（像版本控制系统一样），并查询 Envers 取回历史数据；返回的实例是游离只读的。
  • 可以用动态数据过滤器，让 Hibernate 自动把任意 SQL 限制条件追加到它生成的查询上：定义 → 应用 → 启用三步，还能过滤集合访问。但按标识符检索与「to-one」关联不会被过滤。
